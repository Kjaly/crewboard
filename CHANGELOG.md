# Changelog

All notable changes to Crewboard are documented here. This changelog follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

The public history starts with the first public snapshot of the repository (0.3.0, 2026-09-24, without a tag or an npm release); its changes are folded into 0.4.0, the first release snapshot. The 0.1.0 and 0.2.0 entries below describe internal milestones from before that snapshot, under the working name dsh-orchestra; they were never published and have no Git tags.

## [0.4.0] - Unreleased

First public release snapshot. Crewboard is packaged as two npm packages: [`crewboard`](https://www.npmjs.com/package/crewboard), the command-line interface, and [`dsh-crewboard`](https://www.npmjs.com/package/dsh-crewboard), the DeepSeek Harness plugin. Packaging and the trusted-publishing release workflow are implemented; publishing the versions is a maintainer step, and npm availability is verified at release time rather than claimed by this changelog (see [releasing](docs/releasing.md)).

### Added

- **npm packages.** `npm install -g crewboard` installs the CLI as `crewboard` and `orch`; `dsh plugin --profile web add dsh-crewboard` adds the screen to dsh. The CLI bundles the plan engine and has no private runtime dependency. The release workflow builds and publishes both packages from CI with npm trusted publishing when a `v*` tag is pushed.
- **Repository sidebar.** A two-level list of repositories and plans with pinning and hiding, and a **Needs you** queue for work waiting for a person across repositories. Waiting work also shows in the browser tab title, the favicon, and browser notifications.
- **Graph, Work, and Review views.** Review shows plan progress, money and quota, and lets you open a run or a task in detail. The task panel has overview, activity, changes, contract, your actions, and links; a right-click menu on a task offers follow-up and superseding tasks. The current place is kept in the URL, and heavy screens load on demand.
- **Plan drafts as durable jobs.** A draft keeps the worker's answer even when it does not match the draft format, and can be repaired, retried, recovered, or dropped (`crewboard plan draft …`).
- **The orchestrator's check.** Between a finished run and a person's decision, the plan's orchestrator can check the work: `crewboard verify <id>` takes it, `--done --note "…"` hands it to the person with the note above **Accept**, and `--return "findings"` sends it back to the worker in the same worktree. **Orchestrator checks finished work** is set per repository or plan and is on by default while the plan has a chat (`crewboard verify --setting`); `crewboard wait --for check` follows its steps. Routine checked work can then be accepted and merged by the orchestrator (`accept --auto`/`merge --auto`, `orchestra_close`); decisions, disputed or negative results, conflicts and `<human_review>` stay with the person.
- **The orchestrator's own work and prepared decisions.** A `root` task is work the orchestrator does itself — integration on a stand, starting processes, the owner's database: `crewboard start <id>` shows it «in work by the orchestrator», `crewboard verify <id> --done --note "…" [--report <file>]` sends it to review with a report shown where a worker's is, and no worker is ever launched for it. A decision reaches **Needs you** only once its dependencies are accepted and the orchestrator prepared it with `verify --done` (while the orchestrator check is on); **Accept in batch** names decisions and root tasks the orchestrator has not checked. `crewboard task set <id> --kind` changes the kind of an open task.
- **Run ledger.** Paged, seekable steps of a run with links to individual steps.
- **Closing a task that is no longer needed.** `crewboard drop <id> --reason "…"` (human only, with a confirmation) and **Close as not needed…** in the task menu close a task for good: it becomes «dropped», keeps the reason in its history, never becomes ready again and leaves the critical path. A plan with a dropped task is refused by older builds instead of being misread.
- **Unfinished runs.** A run whose worker stopped with uncommitted work and no result line ends `incomplete` instead of going to review: **Needs you** says why, and **Continue** (or `crewboard continue <id>`) relaunches it in the same worktree with the direction to finish and report. A worker that instead ends its turn with a result line while its copy still holds uncommitted work gets one extra turn in the same run — «your work is not committed: N files, commit it, then report again» — for Claude and Codex; if it reports again still dirty, the run ends `incomplete` for that reason too, rather than reaching review uncommitted. The worker rules now say once, up front, to commit on the task branch before the final report. A contract that assigns the commit to the orchestrator with `<commit_owner>orchestrator</commit_owner>` is the exception: the worker is told to leave the worktree intact and does not commit, the orchestrator commits and reports in the same copy, and routine checked work can then be auto-accepted and merged under the usual gates.
- **One contract template for every way a task is created.** Approving a plan draft, a follow-up or a superseding task, `crewboard task add --template` (a skeleton to fill in) and the orchestrator's `orchestra_task_upsert` (`result`, `checks`, `context`, `outOfScope`, `sources`) all write the same sections in the same order — context, result, checks, not in scope, sources, report — in the person's language. The checks section is the `<checks>` block the verdict reads, and the report section asks for the `Result:` line, so work from a draft no longer reads as disputed for want of it. Approval maps a task's acceptance checks into that block and keeps its sources; the draft's open questions become decision tasks titled as the question, listed under **Open questions to you**. A worker task without a contract shows **needs contract** and is not ready to start; `crewboard run` refuses it with the command to attach one. `run` and the orchestrator's tools warn, without refusing, about a contract with no checks or no result line. `orchestra_task_upsert` takes a task `class`, and its status no longer offers `accepted` or `rejected`: closing routine work goes through `orchestra_close`, and human decisions stay with the person.
- **Accepted is not merged.** Accepting leaves the work on the task's branch; Crewboard detects when that work reaches the base branch — by a merge, a fast-forward or a squash, also one resolved by hand (see docs/en/review.md for the rule) — and records the task as merged; it merges when a person asks, or when the orchestrator auto-merges routine checked work (below). Until then the task is **Accepted, not merged** in **Needs you**, the Work board, Review, `crewboard status` and `crewboard attention`, and its panel (and `crewboard accept`) gives the exact commands. A dependency counts as done only once merged: a dependent task shows «waiting for X to be merged» and `crewboard run` refuses with the commands, unless a person passes `--allow-unmerged`. Files a worker left without a commit are named in the verdict and in the accept confirmation, since the branch does not contain them.
- **Merge from Crewboard, conflicts before acceptance.** `crewboard merge <id> [--squash|--no-ff] [--yes] [--json]` and **Merge** / **Squash and merge** in the task panel merge an accepted task into its base — a person asks, or the orchestrator uses `--auto` for routine checked work under the gates. They first check that the base branch is checked out and clean and the copy holds nothing uncommitted, try the merge with `git merge-tree` (no files change) and refuse a conflict with the paths; then they record the merge commit on the task and clean up the copy like `worktree gc`. A task in review whose branch would conflict with its base or with another task in review says so in its panel, the Review queue and `crewboard status` («conflicts with main in src/a.ts»), with a ready Send back text. New copies record the branch they were made from.
- **A task's base is chosen, not caught by accident.** A launch takes the repository's default base — its `origin/HEAD`, else `main` or `master` — never whatever branch a shared main checkout happens to have checked out; a reused copy keeps the base it already has. When the main checkout is on another branch at launch time, the launch still branches from the default base and says so in one line. `crewboard repo default-base [<branch>|--clear]` and `crewboard plan default-base [<branch>|--clear]` override it per repository and per plan, with the same fields in the task panel's settings; `crewboard run <id> --base <branch>` lets a person choose one on purpose, once, from an interactive terminal — an agent's `--base` is refused. The base is shown in the task panel header and in `crewboard task show`, and is the one merge, conflicts and «bring the branch up to date» texts use. A copy whose recorded base no longer matches the repository's default shows that once, with the command to rebase onto it or to remove the copy and relaunch from it.
- **Work landed by hand stops waiting for a merge.** An accepted task whose copy holds uncommitted work counts as merged when every changed or added file (the journal folder `docs/tmp/` aside) is byte-identical at the tip of the base and every deleted file is absent there; the task feed says «merged … by content». When the work is in the base but no longer byte for byte, a person records it with `crewboard mark-merged <id> --reason "…"` or **Mark as merged…** in the task panel (human only, with a confirmation, no agent tool; git is not touched and a detached HEAD is fine): the reason stays in the feed, the task leaves **Accepted, not merged** and its dependents may start. A base that is the HEAD commit of a detached checkout is named «the current commit of <path> (detached)» instead of a bare hash.
- **Everything about a task in one command.** `crewboard task show <id> [--plan id] [--json]` prints a task's kind, class, status and worker; its worktree, branch, base and diffstat against the base; the merge state (merged; accepted, not merged with the commands and the paths a merge would conflict on; conflicts in review); the last run's outcome and why; the report's first lines and where the whole report is; the verdict, the orchestrator's check and note, the notes and decisions, the contract's checks block, dependencies and dependents. `--json` is the task panel's detail plus these facts, and the orchestrator's new `orchestra_task` tool returns the same structure, so a review no longer combines `status`, `events`, `attention`, the contract and git.
- **CLI version preflight.** Claude Code is checked against the minimum version of the model before a run; Opus 5.5 declares 2.1.280, and the API-only bare mode sets the effective floor at 2.1.281.
- **Runners for OpenCode, Cursor Agent, Gemini CLI and Grok CLI.** Every CLI Crewboard discovers can now run tasks: `opencode/<provider>/<model>`, `cursor/<model>`, `gemini/<model>` and `grok/<model>` workers toggle, preset, route and launch like Claude and Codex. The four share one adapter shape — one process per turn, the CLI's own stream parsed into Crewboard's events (steps, tools, file changes, final answer, usage and cost when the CLI reports them), cancel through the process group, failure reasons; adding the next CLI is a table row plus a parser, not a new backend. OpenCode (`opencode run --format json`, sessions via `--session`, effort via `--variant`, read-only via the `plan` agent, `--dir` pinning the run to the task's copy) is verified live; Cursor Agent (`cursor-agent --print --output-format stream-json`, resume via `--resume`, `--mode plan` for read-only) is verified against the installed CLI's help and fakes — no account is signed in on the development machine; Grok (`--output-format streaming-json`, `--prompt-file`, `--sandbox read-only`) and Gemini (one-shot `--output-format json`, prompt on stdin) are verified against the older tool's adapters, current docs and fakes only — neither is installed here, and a Gemini draft gets a throwaway worktree rather than trusting its docs-only `plan` mode. **Add models** and `crewboard workers models` list `opencode models` and `cursor-agent --list-models`, with built-in rows for Gemini and Grok; the «Crewboard does not run tasks on X yet» note now applies only to a CLI without a runner.
- **A worker's effort reaches its run.** The effort registered for a worker (`crewboard workers add … --effort high`) is passed on every run: Claude Code gets `--effort`, Codex `-c model_reasoning_effort=…`, OpenCode `--variant`, Grok `--reasoning-effort`; Devin, dsh, Cursor Agent and Gemini CLI take none and ignore it. A worker without an effort runs at the CLI's default. An effort the CLI does not accept is refused at preflight with the levels it takes, even with preflight skipped. One model can be registered at several efforts as separate workers (`claude/sonnet-5-high`, `claude/sonnet-5-medium`) and used in presets and routing like any worker. The effort follows the worker's name wherever workers are listed («Claude Sonnet 5 · high»), and each run records it next to its model for the cost and review screens. Draft runs now also launch with the worker's registered model and effort instead of a model read from its id.
- **The verdict and the orchestrator's check where you decide.** Every worker's task in review says where its check stands — waiting for it, being checked, checked, or «No orchestrator check — off for this plan (no orchestrator chat)» / «turned off for this plan / repository» — on the graph card, in Work, in **Needs you**, in the task panel (with a link to the setting), in `crewboard status` and in `crewboard attention`. The verdict with its short reason shows in the same places. Every accept confirmation, single or in batch, on the screen and in `crewboard accept`, starts with one line about the check, and `crewboard run` and **Start** say once when the check is off for the plan, with the command that turns it on; the default of the setting is unchanged. For a blocked task the panel's main action is **Answer the worker**, a relaunch with your answer. A result whose report declares a deviation from the contract reads «Result received · deviation declared» in amber and is not pre-selected in a batch, and changed files outside the paths a contract names in a `<paths>` block are listed as a fact.
- **Crewboard runs the contract's checks itself.** **Run checks here** on the task panel and `crewboard verify <id> --run-checks` (a person or the orchestrator) run each command of the contract's `<checks>` block in the task's worktree, one after another, with the recipe's environment and its timeout per command — only the contract's commands, nothing from the report. Each command's full output goes to a file; the command, exit code, duration, last 20 lines and file are stored as `.orchestration/runs/<run>/checks.json`, next to the run's evidence and apart from the worker's claim. The panel and `crewboard task show` show «Checks run by Crewboard: 3/3 passed» or which failed with the tail, and a red mismatch when the worker claims a result and Crewboard saw a check fail; the verdict itself is not rewritten. A contract without checks says so. A `<checks>` (or `<paths>`) block now opens and closes only at a line that is exactly the tag: an inline mention of `<checks>` in the contract's prose, a code span or fenced code is no longer read as the start of the block, and with several blocks the last one counts — the run warning, the verdict, `task show` and the Crewboard run all read the same commands.
- **A damaged plan can be restored.** Every plan save keeps the version it replaced (`plan.json.prev`, `plans/<id>.json.prev`); `crewboard plan restore [--plan <id>]` brings it back after a person confirms, and a plan that fails to parse points to it. `plan.lock` records the process, host and time: a lock whose process is gone is taken over at once, and a busy plan names who holds it.
- **Every failed attempt says what happened and what to do next.** A failed run records a reason code next to its text — `rate_limited` (with the reset time when known), `auth_expired`, `interrupted`, `disk_full`, `worker_error` — read from what Claude, Codex, Devin and dsh report; a failed worktree setup (`setup_failed`) and a red baseline (`baseline_red`) are kept on the task with their output file. The reason is an optional field, so older builds still read the plan. The task panel's **Last attempt** block says how the attempt ended, why, when, and offers the one move that fits — **Try again**, **Log in** (with the command), **Show output**, **Continue** — with **Start** as the secondary button; `crewboard status` shows the same on the task's row and `lastAttempt` in `--json`. A worker's failure quotes its own `Error:` line instead of the first bytes of its stderr.
- **Quiet runs are marked.** A running task with no step for 5 minutes shows «no steps for N min» on its card and in `crewboard status` (`stalledMin` in `--json`).
- **Starting again on a copy with uncommitted changes asks first.** The screen and `crewboard run` ask a person to continue with the changes or reset the copy (`--keep-changes` / `--reset-copy`); an agent is refused with both commands named. **Continue** and relaunches carry the changes as before.
- **The orchestrator hears every decision, and Send back can rerun at once.** The host wakes the dsh chat bound to a plan — every plan with a chat, not only the one open on the screen — once per change for a check that is due, work waiting for a person, and each human decision: accept, send back with its reason, a decision answered, drop, merge, mark as merged. Each task carries its latest decision as `lastDecision` `{by, at, verdict, reason}` in the orchestrator's `orchestra_plan` snapshot, in `orchestra_task` and in `crewboard status --json`. A send back's reason now goes into the prompt of the task's next run, after the contract in the part that changes per run, whoever starts it. **Send back and rerun** in the task panel and `crewboard reject <id> --reason "…" --rerun [-a <worker>]` send back and start that run at once in the same worktree, with the previous run's worker unless a person picks another from the preset; the panel says where the reason goes. The earlier run stays in the panel as a folded «Run 1 (returned)» block, and the **Changes** tab marks each file `A`/`M`/`D` with `+`/`−` line counts.
- **One number for what waits on you, with the reason next to each item.** Every count of waiting work — the sidebar's **Needs you**, the tab title and favicon, the icon badge, toasts, the **Waiting for you** chip, Review's band and `crewboard attention` — comes from one model and says its scope: «in this plan 7 · all 13» (`attention`: «in this plan · in this repository»). **Needs you** groups its rows by repository and plan with a summary («6 tasks wait for review · 1 decision»), tags each row with its reason — review, check off, blocked, decision, failed, not merged — shows the first five rows of a group and «N more», and keeps the full title in the tooltip. Notifications, in the app, the browser and macOS, are grouped by plan and reason, one per change instead of one per task or alarm; a browser notification or a toast opens that plan's review queue. Notifications stay in the browser and macOS, with no external channel.
- **A new repository opens where the first task starts.** A repository added with **+** opens on the welcome screen, and a click on a repository without a plan opens it too; **Quiet** only holds repositories that had work and none for a week. With no repository listed, the screen asks for a folder path and adds it in place. An empty plan offers **Add task** (a title and, optionally, when it is done; the contract comes from the template) and **Draft from spec**. **From chat** asks for the plan's goal before it creates the plan, and the example tour's **Done** returns to the welcome screen.
- **The CLI's help starts with what a newcomer needs.** `crewboard` (no arguments), `--help` and `help` now print a short **start here** page — `init`, `task add --template`, `run`, `status`, `accept`/`merge`, and how to see everything (`crewboard help all`, the earlier full reference). `--version` prints the installed version; an unknown command that is a close typo of a real one is named («Unknown command: statuz — did you mean status?»); writing to a closed pipe (`crewboard status | head`) exits `0` quietly instead of printing a stack. `crewboard plan draft show <id>` prints a readable draft — goal, tasks with their class and dependencies, open questions — instead of raw JSON; `--json` keeps the old output. `crewboard status` now prints a one-line summary and only the open tasks by default; `--all` prints every task, as before. Before `crewboard accept <id>` asks `[y/N]`, one line gives the verdict, the orchestrator's check state and the merge state, so a person does not have to run `status` or `task show` first. A command that needs a person, run by an agent without a terminal, now says «if you are a person, run it in a terminal».
- **Workers from dsh and from your subscriptions.** Every model configured in dsh's **Settings → Models** is listed in Crewboard's settings as a worker «<Model> · via dsh», grouped by dsh provider, read from dsh's model catalog and refreshed when dsh's configuration changes; keys stay in dsh. Such a worker is `dsh/<provider>/<model>` — enabled, routed, put in presets and named with `-a` like any worker, without registering — and the run selects that provider in dsh; `dsh/deepseek-flash` stays an alias of `dsh/deepseek-official/deepseek-flash`. A dsh model removed from dsh stays in the routes and presets that name it and is marked **not in dsh**. For Claude, Codex and Devin, **Add models** (after **Check access** says the CLI is signed in) creates one worker per chosen model and effort from the CLI's own model list; the CLI has `crewboard workers models <kind>` and `crewboard workers add-models <kind> --models … [--effort …]`. Devin can now run one model as `devin/<model>`. **Used in** names every list a worker is in: the routing and each preset («Claude preset · code #1», «routing · research #2»).
- **Documentation** in English and Russian: getting started, plugin setup, CLI reference, workers, review, costs, and troubleshooting.
- **Heavy checks take turns.** `crewboard slot -- <command…>` waits for a free machine-wide check slot, then runs `<command>` with its exit code and output unchanged, printing `waiting for a check slot (N ahead)` while it waits; `crewboard slot --set <n>` sets the slot count (default: a quarter of the machine's cores, at least one) and a bare `crewboard slot` shows it. The lock lives at `~/.config/crewboard/slots/`, one file per held slot with its process, host and time, like `plan.lock`; a crashed holder's slot is taken over at once. The baseline and `crewboard verify <id> --run-checks` already go through a slot, so several worktrees preparing at once and several checked runs no longer race each other for CPU; a worker's rules now ask it to run its own long commands through `crewboard slot` too.
- **Cost across a day, a sprint or a worker.** `crewboard cost [--all-plans] [--all-repos] [--since <date>] [--until <date>] [--by worker|task|plan|class|effort|day] [--csv|--json]` groups runs by any of those slices instead of only by worker; `--json` rows carry `taskId`, `planId`, `class` and `effort` next to `worker` and `model`, cash and the API-rate estimate stay separate as before, and a subscription's quota is shown per quota window (`quotaWindows`, keyed by provider, account and window) instead of summed across windows that mean different things. Draft and repair attempts, which run outside any task, are their own **Planning** line, never blended into a worker's or a task's totals. Codex's token counts are now priced too, from the same published per-model rates Claude's are, so a Codex run under a subscription gets an API-rate estimate instead of staying unknown; the Claude price table now also covers Sonnet 5, Fable 5.1 and Opus 5.5, so the reworked Claude preset's cost shows up correctly — Opus 5.5 has its own row rather than inheriting Opus 5's price, and the lookup matches a model id exactly, or by its base id once a dated snapshot suffix is stripped, so an unpriced minor version stays unknown instead of silently taking an older model's rate. `--csv` prints one row per slice with a stable header.

### Changed

- **Settings → Workers in three sections.** Every worker is listed once: **Subscriptions** (one block per CLI with its status — signed in, sign-in needed, not installed — its sign-in command, **Check access** and **Add models**; a CLI that is not signed in shows no model table; a model at several efforts is one row with a chip and an **Enabled** switch per effort), **Via dsh (API)** (dsh's catalog by provider, «Keys and models live in dsh.», **Open dsh settings**; a model gone from dsh is **Blocked in dsh** with its switch disabled; with no dsh models at all, the built-in DeepSeek V4 Flash route is one «waiting for a key in dsh» line instead) and **Other / imported · N**, folded: duplicates found by transport, model and effort rather than by the alias table (**Keep one**, **Remove the rest**), an older tool's unused profiles (**Add as worker**, **Remove**) and stale ids (**Remove** takes them out of the routing and presets). Billing and section follow the transport, never the id, so Gemini CLI or Grok CLI profiles are no longer «API». The switch column is **Enabled**; **Used in** shows chips that open the preset and class they name; a preset entry for a switched-off or missing worker stays listed as «not available on this machine» with a link back to the worker. The CLI checks run when the screen opens. `crewboard workers` prints the same three groups.
- **Provider blocks fold to one line.** Each CLI under **Subscriptions** and each dsh provider under **Via dsh (API)** folds to its name, status, «N models · M in presets» and main action (**Check access** or **Add models**); a click on the line opens it. A provider whose models the routing or a preset uses starts open, the others folded, and each viewer's choice is remembered in the browser; **Expand all** / **Fold all** sit at each section's head. A CLI Crewboard has no runner for (OpenCode today, and any other discovered CLI) starts folded and says «Crewboard does not run tasks on OpenCode yet — models listed for reference»: its models have no **Enabled** switch, their menu keeps only **Remove**, and no preset, routing, launch or onboarding picker offers them; a list that still names one marks it «does not run on this machine». `crewboard workers` prints one summary line per provider, and `--all` every model.

- **The minimap names its live lanes.** The graph's corner minimap labels each live lane (short, truncated) and dims History and folded ones, while the lane holding the selected task keeps its name and stays undimmed even there. A click on a name scrolls the canvas to that lane and unfolds it, the way going to a task already does.
- `crewboard status --json` gives a task's check as `check: {state, source}` instead of a bare state; `attention --json` rows carry `check` and `verdict` too.
- The waiting count in the tab title, the icon badge and the sidebar now counts failed or stalled runs and accepted work not merged yet, and a background plan by its waiting tasks, so they agree with **Needs you**; before, each counted slightly differently. The macOS channel says «N tasks wait for review · N decisions in “plan”» instead of one banner per run alarm. `attention --json` rows carry `reason` and `planTitle` (task rows) or `reasons` (background plan rows).
- **The orchestrator's prompt describes what Crewboard really does.** The dsh chat's system prompt is rewritten as goals and criteria instead of a numbered procedure: after it acts it ends its turn, since the host wakes it with `[crewboard] …` lines; it works through the `orchestra_*` tools, and the wake lines now name those tools (`orchestra_verify action=done`) instead of `orch verify` commands; it says how drafts become plans, that acceptance and merging belong to the person, and states the preset rule once (the tool descriptions no longer repeat it). The chat's opening briefing names the language of the person's settings for notes and reports, and contracts written by `orchestra_task_upsert` now follow that setting too. `orchestra_decision` takes `context` and `options` and writes them as the decision's brief, with the options as a checklist in the decision panel. `orchestra_verify action=checks` runs the contract's checks like `crewboard verify <id> --run-checks`. `orchestra_steer` on a run that already ended says how it ended (`runState`) and what to do instead. `orchestra_plan` gives the preset's routing once instead of three times. The `repo` argument accepts another spelling of a known repository (a trailing `/`, `/tmp` against `/private/tmp`), and an unknown path is answered with `crewboard repo add <path>`. Every product fact the prompt states is pinned by a test.
- **The default preset uses the workers you have.** The built-in preset is now named **Default: workers that pass checks** (it was «All workers»): after the class's order it tries every other installed worker, and the first that passes preflight runs; an agent may name any of them. A worker passed over is named in the `crewboard run` output and in the task feed — «claude/opus skipped: not logged in → codex/…». «No worker is available for “Code”» lists the installed workers that could do it and the command `crewboard workers route <class> <worker>`. The task panel says «Will run: X (by the preset)» instead of «No worker assigned», and a person's own pick outside the preset is a neutral **Hand-picked** chip instead of the red **Outside preset**. The remaining «Orchestra» words in messages read «Crewboard».

- **Renamed to Crewboard.** Machine settings move to `~/.config/crewboard/`; an existing `~/.config/dsh-orchestra/` is copied there on first use and left unchanged. `CREWBOARD_*` environment variables replace `ORCH_*`, which are still read. The plugin's settings row is `crewboard`; a `repos` list under the old `dsh-orchestra` id is still read.
- **A task's own worker is honoured.** `crewboard run` without `-a` uses the task's worker and refuses the run, with the reason, when that worker is disabled or fails preflight, instead of falling back to another worker. A worker outside the plan's preset runs only when a person chooses it in a terminal or on the screen, and leaves a note in the task feed; an agent's choice outside the preset is refused.
- An idle plan graph no longer rewrites the page, and dictionaries load as separate assets. The CLI's Russian interface texts load from their own file only when the interface speaks Russian, keeping the installed `crewboard` package smaller.
- **The screen opens fast.** When the host starts, the screen gets every repository's plan graph and statuses first — read without git and without writing — and merge detection, verdicts and conflicts follow in the next snapshot (15 repositories with 60-task plans: the first full graph in about 0.8 s instead of about 14 s). Whether accepted work reached its base, content comparison of copies, verdicts and the events of finished runs are remembered by commits, evidence and run, so a refresh of an unchanged repository runs no `git merge-tree` and about 11 git calls instead of about 150. The screen asks for drafts, draft jobs, presets, worktrees and task detail once per change instead of on every snapshot. Drafts follow a stamp in the snapshot, so a running draft job is no longer polled. A request already in flight is shared, the first read of `/state` included. The badge and toasts ignore the quick first paint and wait for the full snapshot. `node scripts/bench-first-load.mjs` measures it on a generated fixture.
- **Long command output goes to a file.** A failed worktree preparation, a red baseline and a conflicting update of a copy no longer put the whole command output into the message: it is written to `.orchestration/output/<task>/`, and the message names the file with its size and shows the last 20 lines (the host's JSON refusal carries them as `output` fields). `crewboard worktree list` and the task panel name a red baseline's file; `worktree gc` removes the files with the copy.
- **Worker prompts put the steady part first.** Every worker prompt — a launch, a relaunch, **Continue** — is the worker rules, then the contract, then what changes per run, so a prompt cache can reuse the start. The rules also ask the worker to send long check output to a file and read back only the failing part or the tail.
- **Drafting never writes to the checkout, and picks a worker that can run.** A draft worker reads the repository without write access: Claude Code in plan permission mode, Codex in its read-only sandbox, dsh and Devin in a temporary detached worktree outside the checkout that is removed afterwards. The worker is picked like a run's (preflight, then the `research` preset order): the spec picker shows «The draft will be written by: X» with a choice and why a worker was skipped, and the CLI prints it. A failed attempt shows the first line of the worker's error with a hint (log in, enable, update); **Repair** is now **Try again** (`crewboard plan draft retry`, `repair` still works), and an automatic pick that failed is not kept for the retry.

### Fixed

- Failure texts follow the interface language. Core now emits codes with parameters — the stalled and other run alarms, failure reasons, a failed recipe step and its timeout, the runner's stop and late-direction notes, a refused split — and the screen and the CLI say them from their dictionaries; feeds written by older builds in Russian still display, in the reader's language. A usage limit reads «Usage limit reached» for every worker, not only Claude.
- A relaunch never works on a half-merged copy. When bringing a reused copy up to the base conflicts, the undo of that merge is now checked: it is retried briefly (another git process may hold `index.lock` on a loaded machine), and if the copy is still mid-merge or has conflict markers in its files, `run`, `continue`, `verify --return` and a relaunch stop with one sentence that names the copy and the command that cleans it, instead of running the baseline or a worker on that tree. `crewboard merge` likewise says so, with the command, when git refuses to undo a failed merge in the main checkout, instead of reporting the checkout as unchanged. The last lines a refusal shows of a failed step leave out a test runner's crash dump (stack frames, code frames, vitest's `Serialized Error: {…}`), so the errors above it stay visible; the file keeps everything.
- A full disk, a denied permission or a read-only disk on a state file is one sentence with the path in the CLI and on the screen, not a Node stack; a plan save that fails leaves the plan and no temporary file. `crewboard status` and `attention` (and the screen) still answer when the runs they record cannot be written. A mistyped status in `crewboard task set --status` lists the statuses that exist.
- Going to a task in a folded lane — from **Needs you**, the sidebar, search, a link, the task menu or a notification — unfolds that lane (and opens its group in the sidebar's lane tree), then selects the task and centres it on the graph; the task no longer stays hidden behind the lane's header. The unfold is remembered like one made by hand, and folding the lane again keeps the selection.
- A card pinned by hand on the graph no longer drifts into a neighbouring lane's band when a lane above it folds or the live-first order reshuffles the stack: its position is kept relative to its own lane's top, not to the canvas as a whole.
- `crewboard worktree gc` without `--yes` removes nothing: it used to remove merged, clean accepted copies through its re-check without saying so. `--yes` lists what it removed, or `Nothing removed: N kept as …`.
- `crewboard cost` shows money charged (`cash $X`) and the API-rate estimate (`estimate ≈$Y`) separately instead of adding them into one figure; the JSON totals carry `cashUsd` and `apiEquivalentUsd` instead of `usd`, and a plan without runs says so.
- `crewboard wait --tasks` returns `0` at once when every listed task is already where the wait looks, instead of waiting for a transition that already happened; the default timeout is 30 minutes instead of none.
- `crewboard status` without `--all` now hides an accepted task only once it is merged, instead of hiding all accepted work regardless of its merge state; a task still waiting on a merge stays listed, and the summary line calls out the count: «6 of 231 open · 1 accepted, not merged».
- The plugin's browser half is registered under the package name, and the bundle patch imports the plugin by that name.
- The bundled CLI ships its run supervisors next to its entry point.
- Orchestra tool output stays lossless JSON.
- An honest report is no longer disputed: the result line is read from the first lines of the answer or right under a report heading (`## Отчёт`, `## Report`), with list, quote, bold and code marks ignored, and Russian check outcomes («прошёл», «зелёный», «пройдены», «9 тестов», `ok`, `✓`) count as run.
- A result line with a free-text positive claim is accepted: «Result:»/«Результат:» followed by a plain sentence (in Russian, Ukrainian, English, German, French, Spanish, Portuguese, Italian or Polish) counts when its first sentence has a whole positive word and no negation, hedge or failure word; exact keys such as «получен»/`received` work as before.
- A decision has no verdict: its panel shows the checklist and **Where to look** without worker or task-class lines, and `crewboard accept` asks to close it instead of naming `claim_missing`. Verdict reasons in the CLI are words, not codes.
- Batch acceptance never takes risky work by default: **Accept in batch** is the one entry point (the review queue opens the same sheet), pre-selects only clean results, groups negative, disputed and unchecked work under **Open first** without ticks, and the confirmation counts «1 clean, 9 at risk». Review queue rows show their verdict.
- A Claude Code run no longer ends while the worker waits for its own background work: the session stays open until that work finishes and the worker's follow-up turn ends (bounded to an hour). Every worker is told to run long checks in the foreground.
- A Claude Code run that hit the usage limit or ended its last turn with `is_error: true` fails with Claude's message (and, for a limit, the reset time and "start again after the reset") instead of going to review as finished work.
- One worker per worktree even after a run's supervisor dies: the worker runs in its own process group recorded in the run's state, Crewboard stops an orphaned worker and refuses a new start while it lives, and the run ends failed with the reason "the run's supervisor exited; its worker was stopped".
- Activity of a finished run shows its steps instead of "this run has not done anything"; `crewboard events` shows the worker's warnings and `crewboard status` marks a task whose last run failed.
- A closed task starts no worker: `crewboard run`, `orchestra_run`, `steer --relaunch` and `continue` refuse a task that is accepted (also with a negative verdict) or superseded, with the reason in the CLI's language.
- Ctrl+D or Ctrl+C at a confirmation (`accept`, `reject`, `supersede`, `plan approve`, `worktree gc --force`, `verify`) means no: it prints the same «Cancelled.» line as answering `n` and exits 1, without an `AbortError` stack.
- CI and release workflows use `actions/checkout@v7`, `actions/setup-node@v7` and `pnpm/action-setup@v6`, which run on Node.js 24.
- A worker running a long foreground command is not a failure. `crewboard status`, the task panel and the card now say «command running N min — pnpm test…» (Claude, Codex and dsh, which pair a command's start with its result; Devin's events do not, so it is never read as in flight) while one is in flight, and «quiet for N min» once it goes quiet — both information, not an alarm. **Needs you** now lists a running task only once a command outlasts 30 minutes or a quiet spell outlasts 20, tagged «may be stuck» (Stop, Give direction), or once its worker process is gone, tagged «worker gone»; a run that actually failed still reads «failed». The thresholds live in one place (`packages/core/src/watch/rules.ts`); `crewboard attention`, the sidebar and notifications say it the same way.
- The macOS notifier no longer fires «N запуск упал или завис» just because a worker is running a command: it now filters every run alarm through the same rule **Needs you** uses (a command in flight, or a short quiet spell, is information, not an alarm) and remembers each alarm it has already said for a run, so one that flickers in and out — a command finishing and another starting, both crossing «may be stuck» — is said once, not on every poll. The favicon's red dot uses the same rule, so it agrees with **Needs you** on what counts as a failure.
- **Crewboard's names in dsh's own interface never show empty.** The sidebar entry's name, its hover title, the Settings section name, and the right-pane tab's captured title now come from a tiny built-in table carried in the always-loaded client bundle, in both languages, chosen by dsh's active language the moment it is known — never the blank text `dsh` used to read from these slots' `label`/`title` callbacks while Crewboard's own, separately loaded dictionary was still on its way in. The two sidebar list entries also re-register themselves once the active dictionary lands or the language changes, so dsh reads the confirmed text as soon as it is available instead of only at its own next unrelated re-render.
- **A new user's first run is clear.** When no worker can run, `crewboard run` (and the screen's Start) groups the refusal by provider — which CLIs are installed but not signed in, with the sign-in command, which are missing, and to add a DeepSeek key in dsh — then points at `crewboard preflight`; the raw per-model preflight failures print only with `--verbose`, instead of one line per registered model. `crewboard preflight` with no worker profile saved yet checks the built-in and routed workers instead of printing nothing and exiting `0`; it reports per provider and exits non-zero only when none of them can run. `crewboard run` refuses a contract that is still `task add --template`'s skeleton, or whose Result or Checks section is empty, with the path to fill in — `--force` starts it as is. The one-time import of an older tool's config now reads only `~/.config/porch/config.json` under the current `HOME`; a `PORCH_CONFIG` environment variable inherited from another shell no longer pulls a stranger's profiles into a fresh one. `crewboard workers import-porch <path>` imports one on purpose, from any path; every profile it brings in is tagged `origin: porch-import` and, like a worker whose backend this build cannot actually launch (opencode, grok-build, gemini-cli today), is never picked by the default preset's automatic fallback — only chosen by a person naming its id.

## Internal milestones before the public snapshot

### [0.2.0] - 2026-09-23 (internal)

#### Added

- **Screens:** a live plan graph, board, console, economics view, and timeline in dsh. The graph has search, a minimap, lenses, camera navigation, folded completed lanes, and task details with changes, runs, and reports. Repositories and plans remain navigable when another plan needs attention.
- **CLI:** commands to inspect events, traces, costs, attention, workers, and worktrees; wait for a human decision or a finished worker; manage multiple plans and plan chats; and configure routing and presets. Claude Code, Codex, Devin and dsh use direct backends.
- **Acceptance and verdict:** a review queue, in-app notifications, batch acceptance, and a verdict that relates the worker's result claim to known checks, changed files, and run outcome. Evidence stays with finished runs. Accept, return, and supersede remain human decisions, with native confirmation where the dsh host supports it.
- **Presets:** a configurable worker registry and named class-order presets, selectable per repository or per plan. The screen and CLI show the effective selection and refuse disabled workers; a worker named by hand outside the preset runs and leaves a note in the task feed.
- **Languages:** English and Russian interface dictionaries for the screen, host messages, and CLI. The screen follows dsh's active language without a reload.
- **Plan drafts:** a worker or the chat agent drafts a plan graph from a specification; the human reviews its findings and approves it into a new plan. A dependency cycle or a missing dependency blocks approval.
- **Worktree cleanup:** a preview and guarded cleanup in the CLI and screen, plus cleanup after acceptance. Automatic paths retain running, unaccepted, dirty, unmerged, and the three most recently accepted task worktrees; a retained worktree has a visible reason.

#### Changed

- Removed the vendored porch runtime. Devin runs directly over ACP, profiles and routes use the Orchestra profile store, and Codex quota comes from `codex app-server`. Older runs remain readable from their saved artifacts.
- The dsh host and browser client now resolve optional dsh services through scoped accessors, so unavailable services degrade their own integration instead of breaking the screen.
- Plans can be bound to dsh chats, split into new plans, and selected within a repository. Runs can be relaunched with context or from a trace step.

### [0.1.0] - 2026-09-22 (internal)

#### Added

- The first plan engine: validated plan files, dependency and ready-state derivation, revision-checked atomic writes, and quarantine of corrupt plans.
- The `orch` CLI for creating plans and tasks, launching and supervising workers, and reviewing results with human-only acceptance.
- Worker adapters for dsh ACP, isolated task worktrees, preflight checks, normalized event feeds, supervision signals, run trajectories, and usage accounting.
- The first dsh plugin host, live snapshot API and SSE feed, orchestration tools, sidebar entry, and plan screen foundation.
