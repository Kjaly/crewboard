# Ведущий

[English](../en/lead.md) | **Русский**

Ведущий — это чат, с которым вы разговариваете, подключённый к Crewboard по MCP: Claude Code, Codex, dsh или любой другой MCP-клиент. Он превращает то, что вы хотите, в цель и поручения, отвечает исполнителям, поднимает к вам только то, что не может решить сам, и закрывает работу. Какой клиент ведёт, Crewboard узнаёт из самого MCP-подключения и показывает на экране; новый чат ведущего может подхватить цель через `crewboard_adopt_goal`.

## Инструменты

| Инструмент | Что делает |
| --- | --- |
| `crewboard_start_goal` | Ставит цель, о которой договорились с владельцем. Возвращает `goalId`. |
| `crewboard_agents` | Возвращает `{ agents, presets }`: доступных агентов с возможностями и включённые пресеты. |
| `crewboard_assign` | Отдаёт часть работы исполнителю: название, критерии, вид результата (`local`, `branch`, `answer`, `decision`), необязательную `schema` объекта результата, `preset` или провайдер (имя агента из `crewboard_agents`), при желании модель и `effort` (из списка `efforts` агента; если он пуст, поле не передаётся), родителя и зависимости `after`, а в `quote` — реплику владельца, из которой поручение родилось. |
| `crewboard_track` | Записывает один внешний узел, не запуская работу. Возвращает `assignmentId`. |
| `crewboard_track_batch` | Записывает 1–100 внешних узлов в `nodes`; `key` и `parentKey` связывают родителей внутри пакета. Возвращает их ключи и `assignmentId`. |
| `crewboard_track_update` | Обновляет строку прогресса `text` внешнего узла и необязательное поле `phase`. |
| `crewboard_track_finish` | Завершает внешний узел с `outcome` (`success` или `failure`) и `summary`. Сначала нужно завершить открытые дочерние узлы. |
| `crewboard_inbox` | Возвращает всё, что исполнители и владелец прислали и что ведущий ещё не подтвердил. Следующий вызов подтверждает прошлую порцию. |
| `crewboard_answer` | Отвечает на вопрос исполнителя, тот продолжает работу. |
| `crewboard_escalate` | Передаёт вопрос исполнителя владельцу с объяснением в `why`. |
| `crewboard_steer` | Добавляет уточнение к идущей работе. |
| `crewboard_return` | Возвращает итог с замечанием. |
| `crewboard_close` | Закрывает работу, которая выполнила критерии. |
| `crewboard_cancel` | Отменяет поручение и всё, что под ним, и останавливает запуски под управлением Crewboard. Внешние процессы нужно остановить через исходный инструмент. |
| `crewboard_decide_request` | Решает по просьбе владельца с экрана: согласие выполняет её, отказ требует причины, которую владелец прочитает. |
| `crewboard_goals` | Список целей проекта со статусом корня и счётчиками работы. |
| `crewboard_status` | Цель деревом: статус каждого поручения и чем оно занято сейчас. |
| `crewboard_adopt_goal` | Подхватывает цель, которую начал другой чат. |

В каждом вызове есть `project` — абсолютный путь к репозиторию, где работает ведущий. Crewboard берёт корень этого Git-репозитория.

## Как выбрать пресет

В `crewboard_assign` необязательное поле `branch` задаёт новую ветку для результата `branch`, а `writableRoots` — существующие абсолютные каталоги внутри зарегистрированных проектов для записи исполнителем Codex в режиме workspace-write. Для работы только на чтение разрешения игнорируются.

Перед назначением прочитайте `crewboard_agents`: пользователь может заменить или выключить любой [пресет](workers.md#пресеты). Встроенные варианты: `cheap` (DeepSeek) для рутины, `normal` (Codex `gpt-6.1-sol`, medium) для обычной разработки, `hard` (та же модель, high) для сложных рассуждений и `review` (Claude opus) для независимой проверки. Передайте `preset` вместо `provider` в `crewboard_assign`; явные `model`/`effort` имеют приоритет. Поле `note`, если задано, подсказывает ведущему, когда брать пресет.

## Работа, запущенная вне Crewboard

Ведущий может запустить работу для цели через Workflow, Agent, porch или другой инструмент в обход `crewboard_assign`. Отразите её внешними узлами, чтобы владелец видел эту работу в общем дереве цели. Регистрируйте её при запуске или когда обнаружили уже идущий запуск. Обычное поручение запустит ещё одного исполнителя; для работы, запущенной в другом месте, используйте учёт внешних запусков.

В каждом вызове учёта передавайте `project` и `goalId`:

1. **Зарегистрируйте работу.** Вызовите `crewboard_track` с `title` и `kind`: `workflow` для Workflow, `agent` для Agent, `delegate` для делегирования через porch или `other`. Если известны, добавьте `model`, `phase` (фазу или роль) и `externalId`, чтобы следующий ведущий нашёл исходный запуск. По умолчанию родитель — цель; задайте `parentId` существующего поручения или внешнего узла для вложенности. Для Workflow с десятью агентами вызовите `crewboard_track_batch` с `nodes`: дайте Workflow уникальный `key`, а каждому агенту — этот `parentKey`. У одного узла указывайте либо `parentId`, либо `parentKey`. Сохраните полученные `assignmentId` для обновлений.
2. **Обновляйте прогресс.** Проверяйте состояние в исходном инструменте, затем вызывайте `crewboard_track_update` с `assignmentId`, `text` и при необходимости `phase` при смене фазы, появлении препятствия или получении результатов. Пишите, чем работа занята и что ей нужно дальше. Crewboard знает только то, что записал ведущий: он не опрашивает внешний инструмент и не импортирует его логи автоматически.
3. **Зафиксируйте исход.** Проверьте внешний результат, затем вызовите `crewboard_track_finish` с `assignmentId`, `outcome: "success"` или `"failure"` и `summary`. Укажите, где найти результат, что проверено и что осталось сделать; при провале объясните причину. Завершите отдельных агентов до их Workflow. Оба исхода завершают учёт узла; провал всё равно нужно оценить по критериям цели. Если работу нужно остановить, сделайте это через исходный инструмент, убедитесь, что она остановилась, и запишите исход и причину.

Crewboard показывает эти узлы, но не управляет их процессами: он никогда не запускает, не перезапускает и не останавливает их. Аварийная остановка и просьбы об управлении исполнителем не управляют внешними запусками. Ведущий выполняет такие действия через Workflow, Agent, porch или тот инструмент, который запустил работу. Отмена цели или родителя может пометить внешние дочерние узлы как отменённые на экране, пока их процессы продолжают работать; остановите их отдельно в источнике. Для самого внешнего узла используйте `crewboard_track_update` и `crewboard_track_finish`, а не инструменты управления исполнителем.

Спустя сутки без обновления прогресса открытый узел помечается как устаревший. Это означает, что состояние нужно проверить, а не что процесс остановился или завершился с ошибкой. Проверьте исходный инструмент и обновите или завершите узел. Только `crewboard_track_update` этого узла обновляет его актуальность; чтение статуса или обновление других узлов этого не делает. Открытые внешние узлы, в том числе устаревшие, учитываются как незавершённая работа и не дают появиться `goal_idle`. Перед закрытием цели разберитесь с каждым внешним узлом и проверьте его итог по критериям цели.

## Как ведущий узнаёт новости

Ведущий держит в фоне такую команду:

```sh
crewboard wait --project /path/to/repo
```

Без `--timeout` она ждёт новости и завершается с кодом 0. Повторите `--project`, чтобы ждать несколько репозиториев: команда выведет проекты, в которых есть новости. При указанном `--timeout` она завершается с кодом 2, если срок истёк без новостей. Временно недоступный сервер опрашивается повторно; если он долго не отвечает, команда завершается с кодом 1. После завершения ведущий читает `crewboard_inbox`, действует и снова запускает ожидание. События остаются во входящих, пока ведущий снова не вызовет `crewboard_inbox`, поэтому чат ведущего, оборвавшийся до действий, их не теряет: их получит следующий ведущий. Пока ведущий ждёт, экран считает его на связи.

## Вопросы

Исполнитель, который не может продолжать, заканчивает запуск вопросом. Ведущий отвечает через `crewboard_answer`, а если решить может только владелец, передаёт вопрос через `crewboard_escalate` и говорит вам об этом в чате. Ваш ответ с экрана доходит и до исполнителя, и до входящих ведущего.

## Итоги

Исполнитель заканчивает итогом. Узел показывается как «Ждёт ведущего»: ход за ним. Ведущий закрывает работу по критериям или возвращает её с замечанием. Возвращённая работа продолжается в той же рабочей копии, замечание попадает в контекст.

Если следующим этапам нужен результат как данные, передайте JSON Schema объекта в `crewboard_assign.schema`. Например, добавьте такое поле к поручению на ревью:

```json
{
  "schema": {
    "type": "object",
    "properties": {
      "verdict": { "type": "string", "enum": ["approve", "changes"] },
      "findings": { "type": "array", "items": { "type": "string" } }
    },
    "required": ["verdict", "findings"],
    "additionalProperties": false
  }
}
```

Crewboard проверяет схему при назначении и ограничивает размер схемы и результата. Codex и Claude получают её через поддержку структурированного ответа в CLI, остальные агенты — в промпте. Вопросы и разбиение на части продолжают работать. Успешное событие `reported` сохраняет текстовый итог и добавляет проверенный объект в `result`, например `{"verdict":"approve","findings":[]}`. Отсутствующий, невалидный или слишком большой результат даёт `schemaError`; проверьте это поле и при необходимости верните работу с замечанием.

Данные приходят ведущему через `crewboard_inbox` и `crewboard_status`. Поручения с `after` получают структурированные результаты зависимостей в контексте; исполнитель, продолжающий работу после split, получает результаты своих частей. Проверка схемы проверяет форму данных, а соответствие работы критериям по-прежнему проверяет ведущий. Панель узла показывает последний отчёт, ошибку схемы при её наличии и сворачиваемый JSON.

Когда критерии цели выполнены, ведущий закрывает саму цель через `crewboard_close`, передав `assignmentId = goalId` и итог. Если цель больше не нужна, он вызывает `crewboard_cancel` с тем же id. Событие `goal_idle` во входящих напоминает, что вся работа завершена: нужно закрыть цель или дать новое поручение.

## Просьбы владельца

С экрана можно попросить что-то сделать с узлом: уточнить, остановить, передать другому провайдеру, начать раньше, переоткрыть или обсудить. Каждая просьба приходит ведущему во входящие как `owner_requested`. Ведущий решает через `crewboard_decide_request`. Согласие выполняет действие. Отказ требует причины, и экран показывает её на узле. Решение ведущего окончательное. Если вы не согласны, скажите ему в чате.

Передачу можно попросить и для работы в очереди. Согласие меняет агента/модель/effort, оставляя работу в очереди с прежними зависимостями; запуск не начинается. При передаче `effort: null` снимает override поручения, в том числе у того же агента: следующий запуск возьмёт умолчание агента или CLI. Если `effort` не передан, у того же агента сохраняется текущий выбор. Снимки прошлых запусков и настройки ожидающего запуска остаются раздельными.

Одно действие не ждёт ведущего: «Аварийная остановка» на работе под управлением Crewboard. Она сразу останавливает управляемые запуски, в том числе вложенные, а ведущий узнаёт о ней из входящих. Внешние процессы нужно остановить через исходный инструмент.

## Несколько чатов, одна цель

Цель живёт дольше чата, который её начал. Новый чат Claude Code может подхватить её через `crewboard_adopt_goal`, и тогда «История» покажет оба разговора по порядку. Цель, чей ведущий молчит больше суток, показывается «На паузе», пока её не подхватит ведущий.

Зависимости `after` должны уже существовать в той же цели и не быть отменены. При последующей отмене зависимости ведущий получает событие `blocked_dependency` и может отменить ожидающее поручение или применить `start_now`.

Для независимого ревью передайте `reviewOf` с id уже отчитавшегося поручения `branch` и `resultKind: answer`. Ревьюер работает только на чтение в его копии и получает диапазон коммитов, критерии и отчёт. Результат — JSON с `verdict` (`approve` или `changes`) и массивом `findings` (`severity`, `file`, `line`, `problem`, `scenario`). В статусе и на экране видны версия и актуальность. `crewboard_return` с `reviewId` передаёт находки исполнителю; после исправлений назначьте новое ревью. Закрытие предупреждает об устаревшем ревью или `changes`.
