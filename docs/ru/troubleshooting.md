# Если что-то не работает

[Документация](../README.md) · [English](../en/troubleshooting.md) | **Русский**

Если описанное здесь не совпадает с тем, что вы видите, пожалуйста, [откройте issue](https://github.com/Kjaly/crewboard/issues): команда, её вывод и версии (`npm ls -g crewboard`, `node --version`, `dsh --version`).

## `crewboard: command not found`

Глобальный каталог npm с программами не в `PATH`, или установка шла под другой версией Node. Проверьте `npm prefix -g` и `npm ls -g crewboard`. Если пользуетесь менеджером версий Node, ставьте пакет под той версией, которую запускаете.

## «Не git-репозиторий»

Команды работают внутри Git-репозитория. Сначала перейдите в него; подойдёт любой подкаталог.

## «Плана нет: выполни `crewboard init`»

В репозитории ещё нет плана: выполните `crewboard init` (если вы вызвали программу как `orch`, сообщение назовёт `orch init`). Если запрошенного плана нет, а другие есть, сообщение их перечислит; выберите нужный через `crewboard plan use <id>` или флаг `--plan <id>`.

## Запуск не стартует

Сообщение называет причину. Самые частые:

| Сообщение | Что делать |
| --- | --- |
| «Задаче … нужен контракт…» | Создайте контракт из шаблона: `crewboard task set <id> --template`, допишите результат и проверки; или подключите свой: `crewboard task set <id> --contract <файл>`, или запустите с `--contract <файл>`. |
| «Предупреждение: в контракте … нет проверок» / «… не просит строку результата» | Запуск идёт, но отчёт не с чем сверить или он получит «спорно». Добавьте блок `<checks>` и раздел отчёта со строкой `Результат: получен \| отрицательный \| заблокирован`. |
| «Контракт не найден…» | Путь считается от корня репозитория — проверьте его. |
| «Задача ждёт: …» | Зависимость ещё не принята. См. `crewboard status`. |
| «Это решение человека…» | Задача вида `decision` закрывается через `crewboard accept`, а не запуском. |
| «Воркер … отключён на этой машине» | Включите его (`crewboard workers enable <id>`) или выберите другого через `-a`. |
| «Preflight для … не пройден» со списком `✗` | Исправьте то, что в списке: установите CLI, войдите, обновите — или выберите другого воркера. Повторить проверку: `crewboard preflight -a <воркер>`. |
| «Для класса … нет доступного воркера» | Ни один воркер, которого может взять действующий пресет, не прошёл проверку. Сообщение перечисляет установленных воркеров, которые могли бы сделать эту работу: готовых, но не входящих в сохранённый пресет, и остановленных проверкой — с причиной, — и команду, которая направит к одному из них класс: `crewboard workers route <класс> <воркер>`. Войдите в аккаунт, выберите другой пресет или направьте класс. |
| «Базовый прогон красный…» | Команда `baseline` рецепта упала в рабочей копии задачи, поэтому задача не ушла воркеру. Сообщение показывает последние строки, полный вывод — в названном в нём файле. Исправьте основную ветку или рецепт: следующий запуск снова прогонит baseline в той же копии. Панель задачи сохраняет это как **Последнюю попытку** (см. ниже). |
| «Подготовка worktree упала: шаг рецепта упал: …» | Упал шаг `setup` рецепта; сообщение называет шаг и показывает последние строки, полный вывод — в названном файле. Панель задачи сохраняет это как **Последнюю попытку**. |
| «В копии … остались незакоммиченные изменения прошлого запуска» | См. [Новый запуск на копии с изменениями](#новый-запуск-на-копии-с-изменениями). |

Сообщения идут на языке интерфейса: `--lang`, иначе локаль; на экране — язык dsh.

## «waiting for a check slot (N ahead)»

Baseline, `crewboard verify <id> --run-checks` или собственная долгая команда воркера через `crewboard slot -- <команда…>` ждут свободного общего для машины слота проверки — сразу несколько рабочих копий или воркеров что-то тестируют, а число слотов исчерпано. Команда печатает строку и ждёт; ничего не сломано, и как только слот освободится, команда выполнится с тем же кодом выхода и выводом. `crewboard slot` показывает текущее число слотов, `crewboard slot --set <n>` меняет его (по умолчанию — четверть ядер машины, но не меньше одного). Если слот не освобождается долго, проверьте `~/.config/crewboard/slots/` на упавший процесс, всё ещё держащий слот: держателя без живого процесса Crewboard забирает сразу же, так что это должно случаться редко.

## Запуск упал

Упавший запуск не уходит на приёмку: задача возвращается в «готова». Каждая упавшая попытка сохраняет код причины рядом с текстом, а панель задачи показывает её блоком **Последняя попытка** во вкладке «Обзор»: чем закончилась попытка, причина словами, когда и одно подходящее действие; **Запустить** остаётся второстепенной кнопкой. `crewboard status` пишет то же в строке задачи (`последняя попытка упала: … → …`, в `--json` — `lastAttempt`), а `crewboard attention --alarms` называет причину.

| Причина (код) | Что случилось | Что делать |
| --- | --- | --- |
| Лимит исчерпан — сброс в ЧЧ:ММ (`rate_limited`) | Подписка воркера отказала в ходе из-за лимита: последний `result` Claude с `is_error: true`, Codex сообщил о лимите или API ответил 429. Ничего не сделано. | **Повторить** после сброса: `crewboard run <id>`. |
| Воркер не залогинен или его вход истёк (`auth_expired`) | CLI воркера разлогинен, токен истёк или API-ключ отклонён. | Для Codex и Devin **«Войти»** сама ничего не запускает: копирует `codex login` или `devin auth login` для терминала, затем **«Повторить»**. Для dsh проверьте API-ключ в dsh: Settings → Models. Для автоматического запуска Claude действующая API-only защита требует рабочего `ANTHROPIC_API_KEY` и официального endpoint Anthropic — повторный подписочный вход это не исправляет. CLI может всё ещё печатать устаревшую подсказку `claude auth login`, потому что сообщение об ошибке не обновлено; не считайте повторный подписочный вход решением. |
| Супервизор запуска исчез (`interrupted`) | Процесс, следивший за запуском, умер (убит, машина уснула, кончился диск). С pid: Crewboard нашёл воркера, который ещё работал в копии, и остановил его, или тот уже завершился. | Проверьте копию и **Повторить**. |
| На диске закончилось место (`disk_full`) | Запись упала с ENOSPC — у воркера, у его супервизора или при подготовке копии. | Освободите место на диске и **Повторить**. |
| Подготовка копии упала: `<шаг>` (`setup_failed`) | Упал шаг `setup` рецепта (или `git worktree add`); воркер не запускался. | **Показать вывод** — последние строки и файл с полным выводом. Исправьте рецепт или окружение и **Запустить**. |
| Базовый прогон красный: `<команда>` (`baseline_red`) | Команда `baseline` рецепта упала в копии; задача не ушла воркеру. | **Показать вывод** — последние строки и файл. Исправьте основную ветку или рецепт и **Запустить**; baseline снова прогонится в той же копии. |
| Воркер упал (`worker_error`) | Всё остальное. Блок приводит собственную строку `Error:` воркера, а не первые байты его вывода. | Прочитайте строку и Activity запуска, затем **Повторить** или запустите другим воркером. |

Запуск, который закончился, не сдав работу, — не сбой: его **Последняя попытка** — «Закончилась недоделанной» с кнопкой **Продолжить** (`crewboard continue <id>`). Остановленный вами запуск — «Остановлена» с кнопкой **Повторить**.

Воркер, выполняющий долгую команду, сам по себе не сбой: карточка и `crewboard status` показывают «команда выполняется N мин — pnpm test…», пока команда идёт (Claude, Codex и dsh, которые связывают старт команды с её результатом; события Devin так не читаются, поэтому для него команда «в процессе» не показывается), или «тишина N мин», когда воркер замолчал, — и то и другое информация, не тревога. В «Ждут вас» работающая задача попадает, только если команда идёт дольше 30 минут или тишина длится дольше 20, с меткой «возможно, зависла» (кнопки **Остановить** и **Дать направление**), либо если процесс воркера исчез — с меткой «воркер пропал»; реально упавший запуск по-прежнему помечен «упал». **Остановить** в панели задачи завершает её.

Пока жив воркер запуска, чей супервизор исчез, новый запуск отклоняется («… его воркер (pid N) всё ещё работает в копии»), чтобы в одну копию никогда не писали два воркера. Crewboard останавливает его (SIGTERM, через 5 с SIGKILL); запустите снова, когда он завершится.

Activity завершённого запуска показывает его шаги из журнала событий запуска. Если в эту ленту они не попали, Activity отправляет в журнал запуска; она никогда не утверждает, что запуск ничего не сделал.

## Новый запуск на копии с изменениями

Если прошлый запуск оставил в копии задачи незакоммиченные изменения, новый запуск сначала спрашивает: **Продолжить с изменениями** оставляет их следующему воркеру, **Сбросить копию** отбрасывает незакоммиченные изменения и неотслеживаемые файлы (коммиты воркера и игнорируемые файлы, например зависимости, остаются). В терминале `crewboard run <id>` задаёт тот же вопрос; `--keep-changes` или `--reset-copy` отвечают на него заранее. Выбор за человеком: агенту или команде без интерактивного терминала — отказ с обеими командами. **Продолжить**, перезапуск и `steer --relaunch` по замыслу несут изменения прошлого запуска и ничего не спрашивают.

## Запустился не тот воркер, которого я назначил, — или запуск отклонён вместо другого воркера

Воркер, указанный через `-a` или записанный в задаче, никогда не подменяется другим. Если он не может работать, запуск отклоняется. Автоматически выбранный воркер записывается в задачу, так что и следующие запуски пойдут с ним. Сменить его: `crewboard task set <id> --worker <другой>` или `crewboard run <id> -a <другой>`. См. [как выбирается воркер](workers.md#как-выбирается-воркер).

## Claude Code «старее …, требуемой моделью …»

Модели нужен более новый Claude Code. Выполните `claude update`, затем `crewboard preflight -a <воркер>`. См. [минимальная версия CLI](workers.md#минимальная-версия-cli).

## `accept` отвечает «Эту команду выполняет только человек в интерактивном терминале»

Ручная приёмка требует интерактивного терминала. Для обычной проверенной работы оркестратор может использовать `crewboard accept <id> --auto`, затем `crewboard merge <id> --auto`. Решения, спорные результаты и контракты с `<human_review>` остаются человеку. `reject`, `supersede`, `plan approve` и `worktree gc --force` также требуют человека.

## Экран не появляется в dsh

- Проверьте, что плагин установлен в тот профиль, который вы запускаете: `dsh plugin --profile web list`.
- Запустите профиль web (`dsh web`) и найдите **Orchestration**: иконка графа (три связанные точки) в левой колонке, подсказка при наведении — Orchestration.
- Экрану нужен запущенный хост dsh; CLI — нет.
- **Проверьте в своём dsh**, загружает ли ваша версия клиентские части плагинов: браузерная часть плагина рассчитана на веб-клиент.

## «Нет подключённых репозиториев»

Плагину нечего показывать. Нажмите **+** рядом с **Репозитории** и вставьте путь к папке или выполните `crewboard repo add` внутри репозитория. Настройка плагина `repos` и `CREWBOARD_REPOS=/абсолютный/путь/один:/абсолютный/путь/два` тоже работают; относительные пути пропускаются. См. [подключение плагина](plugin-setup.md#подключите-репозитории).

## «Настройки воркеров повреждены»

Экран нашёл `~/.config/crewboard/profiles.json` нечитаемым или без какого-то класса в `routing.classes`. Репозитории при этом видны. Класс без списка работает на порядке воркеров по умолчанию, пока вы снова не сохраните порядок в **Настройки → Воркеры**; с нечитаемым файлом выбор воркера и пресеты не работают, пока файл не исправлен или не удалён (тогда Crewboard запишет значения по умолчанию).

## План, созданный в терминале, не виден на экране

Места нет ни в одном из списков, которые читает экран. Команда плана сообщает об этом после своего вывода и называет исправление: выполните `crewboard repo add` в этом репозитории или рабочей копии. `crewboard repo list` показывает все места, которые видит экран, и откуда они. Копия задачи Crewboard (`<репозиторий>-orch-<задача>`) не показывается намеренно.

## В затратах «Ожидаются данные расхода» или «Недоступно»

У воркеров dsh расход появляется после того, как dsh учтёт сессию, — обычно при следующем старте `dsh web`. У других воркеров источник может вовсе не сообщать это число. См. [затраты](costs.md).

## Рабочая копия не удаляется

Очистка сохраняет непринятые, запущенные, изменённые и неслитые копии, а также три последние принятые. `crewboard worktree gc` показывает причину для каждой копии. Чтобы удалить одну копию с изменениями, выполните сами `crewboard worktree gc --force <id>`.

## Когда что-то пошло не так

### План повреждён: «plan.json повреждён и не читается»

Файл плана, испорченный вручную или сбоем, остаётся на месте, а рядом сохраняется его копия (`plan.json.corrupt-…`). Каждое сохранение оставляет заменённую версию как `plan.json.prev` (`plans/<id>.json.prev` для других планов), поэтому, если такая версия есть, сообщение предлагает путь назад:

```sh
crewboard plan restore --plan <id>
```

Выполняет её только человек в терминале, после подтверждения с ревизией, временем и числом задач возвращаемой версии. Нынешний файл становится предыдущей версией, так что повторный `plan restore` отменяет первый. Всего, что сохранено после той версии, в ней нет — проверьте `crewboard status`. Если предыдущей версии нет, команда так и скажет и ничего не изменит.

### «План занят: … держит процесс …»

Сохранения берут `.orchestration/plan.lock`, в котором записаны номер процесса, хост и время. Блокировку процесса, которого уже нет, команда забирает сразу. Живую ждёт несколько секунд, затем останавливается и называет держателя. Дождитесь его или остановите и повторите команду. Блокировку с другого хоста или от старой версии Crewboard команда забирает, когда ей больше десяти секунд.

### «На диске нет места для …», «Нет прав на запись …», «… на диске только для чтения»

Crewboard не смог записать файл состояния в `.orchestration/` и называет его. Сохранение плана в этом случае ничего не пишет: план остаётся прежним. Освободите место, исправьте владельца или права папки или работайте там, где репозиторий доступен на запись, и повторите команду. `crewboard status`, `attention` и `events` на таком диске всё равно отвечают: завершившиеся запуски видны и записываются следующей командой, которая сможет писать.

## Старая установка `orch`

Вручную переносить ничего не нужно. `orch` работает по-прежнему — это та же программа. При первом запуске `~/.config/dsh-orchestra/` копируется в `~/.config/crewboard/` (оригинал остаётся), переменные окружения `ORCH_*` по-прежнему читаются, а плагин, настроенный под старым идентификатором `dsh-orchestra`, сохраняет свой список `repos`. Данные планов в `.orchestration/` не меняются.
