# Если что-то не работает

[Документация](../README.md) · [English](../en/troubleshooting.md) | **Русский**

Если описанное здесь не совпадает с тем, что вы видите, пожалуйста, [откройте issue](https://github.com/Kjaly/crewboard/issues): команда, её вывод и версии (`npm ls -g crewboard`, `node --version`, `dsh --version`).

## `crewboard: command not found`

Глобальный каталог npm с программами не в `PATH`, или установка шла под другой версией Node. Проверьте `npm prefix -g` и `npm ls -g crewboard`. Если пользуетесь менеджером версий Node, ставьте пакет под той версией, которую запускаете.

## «Не git-репозиторий»

Команды работают внутри Git-репозитория. Сначала перейдите в него; подойдёт любой подкаталог.

## «Плана нет: выполни `crewboard init`»

В репозитории ещё нет плана: выполните `crewboard init` (если вы вызвали программу как `orch`, сообщение назовёт `orch init`). Если запрошенного плана нет, а другие есть, сообщение их перечислит; выберите нужный через `crewboard plan use <id>` или флаг `--plan <id>`.

## Запуск не стартует

Сообщение называет причину. Самые частые:

| Сообщение | Что делать |
| --- | --- |
| «Нет контракта…» | Добавьте контракт: `crewboard task set <id> --contract <файл>` или запуск с `--contract <файл>`. |
| «Контракт не найден…» | Путь считается от корня репозитория — проверьте его. |
| «Задача ждёт: …» | Зависимость ещё не принята. См. `crewboard status`. |
| «Это решение человека…» | Задача вида `decision` закрывается через `crewboard accept`, а не запуском. |
| «Воркер … отключён на этой машине» | Включите его (`crewboard workers enable <id>`) или выберите другого через `-a`. |
| «Preflight для … не пройден» со списком `✗` | Исправьте то, что в списке: установите CLI, войдите, обновите — или выберите другого воркера. Повторить проверку: `crewboard preflight -a <воркер>`. |
| «Для класса … нет доступного воркера» | Ни один воркер из списка класса не прошёл проверку. Посмотрите `crewboard workers` и `crewboard presets list`: в действующем пресете список может быть пуст, а все воркеры в нём — отключены или не проходят проверку. |
| «Базовый прогон красный…» | Команда `baseline` рецепта упала в рабочей копии задачи, поэтому задача не ушла воркеру. Исправьте основную ветку или рецепт: следующий запуск снова прогонит baseline в той же копии. |
| «Подготовка worktree упала…» | Упал шаг `setup` рецепта; его вывод идёт следом за сообщением. |

## Запуск упал

Упавший запуск не уходит на приёмку: задача возвращается в «готова», `crewboard status` помечает её «последний запуск упал», а тревога (`crewboard attention --alarms`, панель задачи) называет причину:

| Причина | Что случилось и что делать |
| --- | --- |
| «Лимит Claude исчерпан — сброс в ЧЧ:ММ» | Claude Code отказал в ходе из-за лимита подписки (последний `result` с `is_error: true`). Ничего не сделано. Запустите задачу снова после сброса: `crewboard run <id>`. |
| другой текст после запуска Claude | Claude Code закончил последний ход с `is_error: true`; текст — ошибка самого Claude. |
| «супервизор запуска исчез; его воркер (pid N) остановлен» | Процесс, следивший за запуском, умер (убит, машина уснула, кончился диск). Crewboard нашёл воркера, который ещё работал в копии, и остановил его. Проверьте копию перед новым запуском. |
| «супервизор запуска исчез; его воркер (pid N) уже не работал» | То же, но воркер к этому времени уже завершился. Запуск, начатый прежней версией Crewboard, которая воркера не записывала, сообщает только «супервизор запуска исчез». |

Пока жив воркер запуска, чей супервизор исчез, новый запуск отклоняется («… его воркер (pid N) всё ещё работает в копии»), чтобы в одну копию никогда не писали два воркера. Crewboard останавливает его (SIGTERM, через 5 с SIGKILL); запустите снова, когда он завершится.

Activity завершённого запуска показывает его шаги из журнала событий запуска. Если в эту ленту они не попали, Activity отправляет в журнал запуска; она никогда не утверждает, что запуск ничего не сделал.

## Запустился не тот воркер, которого я назначил, — или запуск отклонён вместо другого воркера

Воркер, указанный через `-a` или записанный в задаче, никогда не подменяется другим. Если он не может работать, запуск отклоняется. Автоматически выбранный воркер записывается в задачу, так что и следующие запуски пойдут с ним. Сменить его: `crewboard task set <id> --worker <другой>` или `crewboard run <id> -a <другой>`. См. [как выбирается воркер](workers.md#как-выбирается-воркер).

## Claude Code «старее …, требуемой моделью …»

Модели нужен более новый Claude Code. Выполните `claude update`, затем `crewboard preflight -a <воркер>`. См. [минимальная версия CLI](workers.md#минимальная-версия-cli).

## `accept` отвечает «Эту команду выполняет только человек в интерактивном терминале»

Так и задумано. `accept`, `reject`, `supersede`, `plan approve` и `worktree gc --force` требуют интерактивного терминала и ответа `y`. Выполняйте их сами, а не через агента или конвейер.

## Экран не появляется в dsh

- Проверьте, что плагин установлен в тот профиль, который вы запускаете: `dsh plugin --profile web list`.
- Запустите профиль web (`dsh web`) и найдите **Orchestration**: иконка графа (три связанные точки) в левой колонке, подсказка при наведении — Orchestration.
- Экрану нужен запущенный хост dsh; CLI — нет.
- **Проверьте в своём dsh**, загружает ли ваша версия клиентские части плагинов: браузерная часть плагина рассчитана на веб-клиент.

## «Нет подключённых репозиториев»

Плагину нечего показывать. Нажмите **+** рядом с **Репозитории** и вставьте путь к папке или выполните `crewboard repo add` внутри репозитория. Настройка плагина `repos` и `CREWBOARD_REPOS=/абсолютный/путь/один:/абсолютный/путь/два` тоже работают; относительные пути пропускаются. См. [подключение плагина](plugin-setup.md#подключите-репозитории).

## «Настройки воркеров повреждены»

Экран нашёл `~/.config/crewboard/profiles.json` нечитаемым или без какого-то класса в `routing.classes`. Репозитории при этом видны. Класс без списка работает на порядке воркеров по умолчанию, пока вы снова не сохраните порядок в **Настройки → Воркеры**; с нечитаемым файлом выбор воркера и пресеты не работают, пока файл не исправлен или не удалён (тогда Crewboard запишет значения по умолчанию).

## План, созданный в терминале, не виден на экране

Места нет ни в одном из списков, которые читает экран. Команда плана сообщает об этом после своего вывода и называет исправление: выполните `crewboard repo add` в этом репозитории или рабочей копии. `crewboard repo list` показывает все места, которые видит экран, и откуда они. Копия задачи Crewboard (`<репозиторий>-orch-<задача>`) не показывается намеренно.

## В затратах «Ожидаются данные расхода» или «Недоступно»

У воркеров dsh расход появляется после того, как dsh учтёт сессию, — обычно при следующем старте `dsh web`. У других воркеров источник может вовсе не сообщать это число. См. [затраты](costs.md).

## Рабочая копия не удаляется

Очистка сохраняет непринятые, запущенные, изменённые и неслитые копии, а также три последние принятые. `crewboard worktree gc` показывает причину для каждой копии. Чтобы удалить одну копию с изменениями, выполните сами `crewboard worktree gc --force <id>`.

## Старая установка `orch`

Вручную переносить ничего не нужно. `orch` работает по-прежнему — это та же программа. При первом запуске `~/.config/dsh-orchestra/` копируется в `~/.config/crewboard/` (оригинал остаётся), переменные окружения `ORCH_*` по-прежнему читаются, а плагин, настроенный под старым идентификатором `dsh-orchestra`, сохраняет свой список `repos`. Данные планов в `.orchestration/` не меняются.
