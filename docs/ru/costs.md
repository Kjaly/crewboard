# Затраты

[Документация](../README.md) · [English](../en/costs.md) | **Русский**

Воркеры оплачиваются по-разному: одни за токены через API, другие по подписке, третьи по промо. Crewboard записывает то, что на самом деле сообщает источник каждого запуска, и не смешивает эти виды чисел. Оценка не превращается в списание, а отсутствующее число не показывается нулём.

![Журнал запусков: два запуска с воркером, моделью, учтёнными расходами API, оценкой по тарифам API и недоступной стоимостью](../assets/run-ledger.png)

*Два запуска: у одного учтены расходы API, у другого — оценка по тарифам API, а одно из чисел недоступно.*

## Что означает каждое число

| На экране | В `crewboard cost --json` | Что это |
| --- | --- | --- |
| **«Учтённые расходы API»** | `cashUsd` | Деньги, которые источник записал как списанные за запуск: записи учёта dsh для воркеров dsh или сумма, которую сообщил сам воркер с оплатой через API. |
| **«Эквивалент по тарифам API»** с пометкой **«Оценка, не счёт»** | `apiEquivalentUsd` | Сколько стоили бы токены запуска по тарифам API: для воркеров по подписке (Codex и исторические запуски Claude Code) и для текущего запуска Claude по API-ключу, чей CLI сообщает клиентскую оценку `total_cost_usd`. **Это не счёт и не списанные с вас деньги**, а способ сравнить воркеров. |
| **«Изменение квоты подписки»**, **«Квота потрачена»** | `quotaMeasurements`, `quotaDeltaPct` | Какую часть окна подписки израсходовал запуск — по замерам до и после. |
| **«Токены»** — вход, выход, чтение и запись кэша | `tokens` | Число токенов, если источник его сообщает. |
| **«Ожидаются данные расхода»** | `pending: true`, `availability.*: "pending"` | Источник ещё не учёл запуск. В итоги он не входит. |
| **«Неполные данные»** | `availability.*: "partial"` | Измерена только часть запуска. |
| **«Недоступно»** | `availability.*: "unavailable"` | Источник не даёт этого числа. Оно неизвестно, а не равно нулю. |
| **«Не применимо»** | `availability.cash: "notApplicable"` | Деньги здесь неприменимы: запуск по подписке не оплачивается поштучно. |
| **«Общее окно квоты; расход запуска не выделен»** | `attribution: "shared"` | В то же время то же окно квоты расходовала другая работа, поэтому изменение нельзя приписать этому запуску. В итоги оно не входит. |

Число записей в кэш остаётся отсутствующим, если CLI его не сообщает. Сводные итоги включают только сообщённые значения и при наличии хотя бы одного показывают `cacheWriteCoverage` (`knownRuns`, `partialRuns`, `totalRuns`). Смешанное покрытие вызовов и старые state-файлы с положительной суммой помечаются как неполные. Явно сообщённый ноль считается известным нулём. Завершённый запуск dsh без записи в биллинге остаётся в ожидании денежного учёта до заполнения данных.

## `crewboard cost`

`crewboard cost` печатает по строке на воркера: запуски, минуты, деньги, токены, квоту и запуски, которые ещё ждут учёта. Например (цифры условные):

```text
dsh/deepseek-flash: 2 запуск(ов) · 14 мин · деньги $0.21 · токены 310.4k вход / 12.9k выход / 280.0k кэш
claude/opus: 3 запуск(ов) · 25 мин · оценка ≈$4.8 · токены 1.2k вход / 40.1k выход / 2100.0k кэш
codex/gpt-6-sol: 1 запуск(ов) · 9 мин · деньги: нет данных · квота +3%
```

Деньги идут двумя величинами, которые не складываются, как и на экране: `деньги` — что списано за запуски по API, `оценка ≈` — сколько запуски по подписке стоили бы по API-ценам. Если у воркера есть и то и другое, показаны обе. В `crewboard cost --json` итоги по воркерам (`totals`) содержат `cashUsd` и `apiEquivalentUsd` (каждое — только если запуски его сообщили), а у каждого запуска есть `billingMode` (`api`, `subscription`, `promotional`, `unknown`), `cashUsd` или `apiEquivalentUsd` с источником и запись `availability` для каждой метрики.

Черновики и починки (`crewboard plan draft …`) выполняются вне какой-либо задачи, поэтому они никогда не попадают в итоги воркера или задачи выше; вместо этого они всегда печатаются отдельной строкой **«Planning»**, посчитанной так же.

## Срезы: день, спринт или воркер

```text
crewboard cost [--all-plans] [--all-repos] [--since <дата>] [--until <дата>]
               [--by worker|task|plan|class|effort|day] [--csv|--json]
```

- `--by worker|task|plan|class|effort|day` группирует запуски по этому признаку вместо только воркера; строка **«Planning»** остаётся отдельной от любой группировки.
- `--all-plans` охватывает все планы текущего репозитория вместо только открытого; `--plan <id>` и `--all-plans` нельзя сочетать.
- `--all-repos` охватывает все репозитории, которые знает экран (тот же список, что у `crewboard attention --all`), каждый со своим текущим планом, или все планы каждого вместе с `--all-plans`.
- `--since <дата>` / `--until <дата>` оставляют запуски (и попытки черновика), чей старт попадает в этот диапазон; голая дата `ГГГГ-ММ-ДД` означает весь день — `--since` начинается с его первого мгновения, `--until` заканчивается после последнего.
- `--csv` содержит только срезы воркеров и строку Planning; это не полный итог затрат. Заголовок: `key,runs,minutes,cashUsd,apiEquivalentUsd,quotaWindows,tokensInput,tokensOutput,tokensCacheRead,tokensReasoning,pendingRuns`. В `--json` также есть отдельные данные сессий `orchestrator`.

В выводе есть отдельный раздел **Orchestrator** и поле JSON `orchestrator`. Читаются только явно привязанные ID dsh-сессий из `.orchestration/chats.json`; без привязки данные недоступны, без записи счёта статус ожидающий. Это полный срок жизни сессии, который исключён из итогов воркеров, задач, планов и Planning. Повторная привязка одной сессии считается один раз. Для каждого поля указана своя полнота: отсутствующее поле неизвестно, явный ноль известен. JSON сессии сохраняет число найденных вызовов, источник `dsh_bill_records` и наблюдённые денежные данные со статусом known/partial/unavailable; сумма известна только если каждая запись имеет числовой конечный неотрицательный USD и помечена как тарифицированная. Cache write означает лишь наличие значения в записи, а не подтверждённую активность кэша провайдера. Фильтр дат отбирает привязки по `boundAt`, но не фильтрует записи счёта сессии; область фильтра по привязкам указывается даже при пустой выборке.

Для явно указанного rollout Codex: `crewboard cost --codex-rollout <точный-путь>` выдаёт JSON-диагностику по событиям `event_msg` с токенами и метаданным модели из `turn_context`. Поиск чатов не выполняется, тексты диалога не копируются. Первый накопительный снимок остаётся нераспределённым; последующие приращения относятся к текущей модели, сбросы начинают новый сегмент, деньги и квота недоступны. Последний ход и накопительные итоги разделены. Флаг нельзя сочетать с `--json`, `--csv`, `--plan`, `--all-plans`, `--all-repos`, `--since`, `--until` и `--by`; как и сама диагностика, он не указан в `crewboard help all`.

Квота подписки в срезах (`--by …` и `--csv`) показывается по окну квоты: 5-часовое окно и недельное окно — разные области, и складывать их изменения было бы неверно для обоих. В тексте и CSV каждый срез перечисляет все окна, которых коснулся, `<окно> +<процент>%`; в JSON это `quotaWindows: [{ provider, accountKey, windowId, deltaPct }, …]`. Обычный `crewboard cost` без флагов срезов по-прежнему печатает один `quotaDeltaPct` на воркера, который может сложить несколько окон одного запуска (и нескольких запусков) в одно `квота +N%`; читайте это как грубый итог, а не как значение одного окна.

## Откуда берутся числа

- **Воркеры dsh.** Плагин учёта dsh пишет записи в `$DSH_HOME/dsh-bill/records.jsonl` (по умолчанию `~/.dsh`). Crewboard читает оттуда токены и доллары сессии запуска. dsh дописывает сессии из журналов при старте `dsh web`, поэтому свежий запуск может ждать учёта до следующего старта; CLI пишет «ждут учёта dsh-bill (перезапусти dsh web)». Если хотя бы у одной записи сессии нет цены, сумма остаётся неизвестной. **Проверьте в своём dsh**, что плагин учёта включён.
- **Claude Code.** Автоматические запуски Claude работают только по API-ключу (см. [воркеры](workers.md#автоматизация-claude-подписки-и-безопасность-аккаунта)); собственный `total_cost_usd` CLI — клиентская оценка, записываемая в `apiEquivalentUsd` с источником `claude_cli_estimate`, никогда в `cashUsd` — деньги остаются недоступными или ожидающими. Токены берутся из журналов Claude Code для рабочей копии запуска в `~/.claude/projects/` и оцениваются по опубликованным тарифам API. Чтение недельной квоты подписки (`~/.claude/usage/rate-limits.jsonl`, если на вашей машине что-то его пишет, например скрипт строки состояния) не изменилось и теперь служит историческим запускам по подписке; новые запуски Claude для квоты не замеряются.
- **Codex.** Квота читается через `codex app-server` до и после запуска. Если прочитать её не удалось, проверка показывает «квота неизвестна», а запуск всё равно стартует. Сначала используется собственная заявленная стоимость Codex; без неё число токенов оценивается по опубликованным тарифам для модели — так же, как у Claude Code. Модель вне списка остаётся неизвестной, а не $0.
- **Devin.** Запуски записываются с неизвестным способом оплаты, если Devin не сообщает стоимость.

Замер квоты не входит в итоги и тогда, когда окно сбросилось во время запуска.

## На экране

Экран **«Итоги»** сводит данные по плану: время плана, время воркеров, ожидание вас, потраченные деньги, потраченную квоту и токены. Если открыть запуск, виден его журнал шагов с расходом по времени и по шагам, и у каждого значения — одно из состояний выше.

Оценки по тарифам API годятся для сравнения воркеров и планов, но это не счёт.
