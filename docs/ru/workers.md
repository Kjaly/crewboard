# Воркеры

### Кто коммитит изменения воркера

По умолчанию воркер коммитит работу в ветке задачи перед отчётом. Для Codex в отдельной Git worktree Crewboard даёт его песочнице запись в Git metadata этого репозитория и в общую директорию слотов проверок, чтобы работали `git commit` и `crewboard slot`. Если коммит делает оркестратор, контракт должен содержать отдельную строку `<commit_owner>orchestrator</commit_owner>`. Тогда Crewboard просит воркера сохранить рабочую копию, не требует от него коммита и передаёт отчёт на проверку оркестратору даже при незакоммиченных файлах. Оркестратор проверяет результат, исправляет при необходимости и коммитит в той же worktree до `verify --done`. Обычную проверенную работу оркестратор может принять и слить; слияние требует чистой копии.

Если запуск отмечен как incomplete с сохранёнными изменениями из-за требования коммита или нераспознанной строки результата, `crewboard verify <id> --takeover --note "причина"` передаёт копию оркестратору в состояние **проверяется** без нового запуска. Сам запуск остаётся incomplete. Оркестратор проверяет и коммитит работу в копии, выполняет обязательные проверки на этом коммите, затем передаёт свой положительный отчёт через `crewboard verify <id> --done --note "…" --report <файл>`. Автоматическая приёмка всё так же требует чистый коммит и зелёные проверки. Команда не применяется к запускам без сохранённых изменений или доказательств.

[Документация](../README.md) · [English](../en/workers.md) | **Русский**

Воркер — это CLI кодового агента, который Crewboard запускает для задачи: Claude Code, Codex, Devin или агент dsh (например, DeepSeek). Воркеры разных провайдеров могут брать задачи одного плана. Работа, которую небезопасно отдавать воркеру, — интеграция на стенде, запуск процессов, база владельца, — это задача `root`: её делает сам оркестратор, и Crewboard никогда не запускает для неё воркера (см. [справочник CLI](cli.md#собственная-работа-оркестратора)).

## Автоматизация Claude, подписки и безопасность аккаунта

Crewboard выбирает консервативную **API-only политику для автоматических воркеров Claude**. Подписочная или неизвестная авторизация блокируется; запуск не должен незаметно переходить на платный API. Это правило продукта, а не утверждение о запрете всех подписочных CLI-сценариев. В [обновлении справки Agent SDK](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan) объявленные изменения биллинга приостановлены.

**Защита реализована:** ревизия политики anthropic-api-only-2026-09-28; активируется обновлением Crewboard. Первый поддерживаемый путь — штатный Claude Code не ниже 2.1.281 с поддержкой bare-режима, явный ANTHROPIC_API_KEY и прямой API Anthropic. Неизвестные переопределения авторизации, заголовков и маршрута блокируются. Другие коммерческие способы могут не поддерживаться адаптером, не нарушая условий Anthropic. Наличие ключа не доказывает его действительность или баланс.

Ориентируйтесь на безопасную причину отказа в preflight Crewboard: настройте поддерживаемый канал или выберите другого воркера. Не вставляйте ключи, токены, cookie и идентификаторы аккаунта в отчёты. Рабочие копии и история сохраняются; интерактивный Claude Code вне Crewboard не затрагивается. Счёт API, оценки CLI и квота подписки учитываются раздельно.

См. [датированную запись источников и ограничений реализации](../notes/2026-09-28-anthropic-automation-policy.md). Причина сообщённого ограничения аккаунта не установлена; гарантия доступности аккаунта не даётся.

## Какие CLI поддерживаются

| Вид | CLI | Что проверяется перед запуском |
| --- | --- | --- |
| `claude` | Claude Code, `claude` | API-only политика, версия/поддержка bare и явный ключ API в окружении; подписочный вход не используется. Для модели с известной минимальной версией сравнивается версия Claude Code (см. [ниже](#минимальная-версия-cli)). |
| `codex` | Codex CLI, `codex` | `codex --version`; `codex login status` должен показывать выполненный вход; квота подписки должна быть израсходована меньше чем на 90 %, если её удаётся прочитать через `codex app-server`. |
| `devin` | Devin CLI, `devin` | `devin --version` должен показывать выпуск `3000.x`; `devin auth status` — выполненный вход. |
| `opencode` | OpenCode, `opencode` | `opencode --version`; `opencode auth list` должен показывать подключённого провайдера модели (`<провайдер>/<модель>`). |
| `cursor` | Cursor Agent, `cursor-agent` | `cursor-agent --version`; `cursor-agent status` не должен показывать «Not logged in». |
| `gemini` | Gemini CLI, `gemini` | `gemini --version`. У Gemini CLI нет команды статуса входа, поэтому проверка читает его хранилища учётных данных (`GEMINI_API_KEY`/`GOOGLE_API_KEY`/`GOOGLE_APPLICATION_CREDENTIALS`, `~/.gemini/.env`, `security.auth.selectedType` в `~/.gemini/settings.json`, `~/.gemini/oauth_creds.json`, файл gcloud ADC) и сообщает, что нашлось. Промах — только предупреждение: вход, хранящийся только в keychain ОС, прочитать нельзя, а незалогиненный запуск сам покажет ошибку авторизации. На установленном CLI не проверено. |
| `grok` | Grok CLI, `grok` | `grok version`; `grok models` должен завершаться успешно — список моделей аккаунта требует входа (обе команды по docs.x.ai/build/cli/reference). CLI на машине разработки не установлен — проверка покрыта только фейками. |
| `dsh` | dsh, `dsh` | `dsh --version`; `dsh --profile acp --dump-config` должен выполняться без ошибок. Для модели маршрута DeepSeek в dsh ключ DeepSeek API (`DEEPSEEK_API_KEY`) должен быть в окружении, в хранилище ключей dsh (**Settings → Models**) или в `$DSH_HOME/.env`; проверяется только наличие ключа, не его значение. Ключ другого провайдера — забота dsh, он не проверяется. Модель Anthropic, направленная через dsh, отклоняется политикой API-only для Claude (ниже), а не запускается. |

Каждому воркеру нужен свой установленный CLI с выполненным входом; учётными записями и ключами Crewboard не занимается. Preflight запускает ту же программу, что и запуск, в том числе заданную через `CREWBOARD_<KIND>_COMMAND` (`CREWBOARD_CURSOR_COMMAND` переопределяет имя `cursor-agent`). Экран приветствия пишет «готов» только после того, как эта проверка прошла. Проверить воркера:

```sh
crewboard preflight -a claude/opus
crewboard preflight            # все включённые профили
```

Успешная проверка кэшируется на пять минут в `.orchestration/preflight-cache.json`; неудачная повторяется при следующем запуске.

## Реестр

`crewboard workers` показывает воркеров [в трёх секциях](#экран-воркеры-три-секции) и порядок по классам. При первом использовании реестр `~/.config/crewboard/workers.json` создаётся с такими записями:

| Воркер | Модель | Оплата |
| --- | --- | --- |
| `dsh/deepseek-flash` | DeepSeek V4 Flash через dsh | API |
| `claude/opus`, `claude/fable` | Claude Opus 5, Claude Fable 5.1 | API (ключ Claude API) |
| `codex/gpt-6-astra`, `codex/gpt-6.1-sol`, `codex/gpt-6-sol`, `codex/gpt-6-luna` | модели Codex GPT-6 | подписка |
| `codex/gpt-5.6-sol`, `codex/gpt-5.6-terra`, `codex/gpt-5.6-luna` | модели Codex GPT-5.6 | подписка |

Работают и короткие псевдонимы, например `codex` для `codex/gpt-6-astra` и `claude-opus` для `claude/opus`. Идентификатор вида `claude/<модель>` или `codex/<модель>` можно использовать без регистрации, например `-a claude/opus-5-5`. Devin вызывается как `devin` с моделью из профиля Devin или как `devin/<модель>`, если добавлен для одной модели (см. [ниже](#подписки-добавить-модели)). Модели, которые даёт dsh, в реестре не хранятся вовсе: см. [модели из dsh](#модели-из-dsh).

Добавить, изменить или удалить воркера:

```sh
crewboard workers add claude/sonnet --kind claude --model sonnet --label "Claude Sonnet"
crewboard workers disable claude/sonnet --reason "на этой машине нет доступа"
crewboard workers enable claude/sonnet
crewboard workers rm claude/sonnet
```

**Отключённый** воркер остаётся в реестре, но на этой машине не запускается никогда — ни при автоматическом выборе, ни как воркер задачи, ни через `-a`.

## Экран «Воркеры»: три секции

**Settings → Crewboard → Воркеры** показывает каждого воркера ровно один раз, в одной из трёх секций. Секцию решает транспорт, на котором воркер работает, — не его id. Оплата тоже следует за транспортом, с одним исключением: автоматические запуски Claude Code работают только по API, поэтому блок Claude по-прежнему стоит под устаревшим заголовком **Подписки**, а его оплата читается как **API**. Три секции: **Подписки** (CLI с выполненным входом: Codex, Devin и другие), **Через dsh (API)** и **Другое / импортированное**.

1. **Подписки** — по блоку на CLI: Claude, Codex и Devin всегда, а также любой другой CLI по подписке, на котором работает профиль из старого инструмента (OpenCode, Cursor Agent, Gemini CLI, Grok CLI), — как только его воркер где-то используется. Блок показывает состояние CLI — **вход выполнен**, **нужен вход** или **не установлен** — по локальной проверке, которая идёт при открытии экрана и снова по **Проверить доступ**, команду входа и, после входа, **Добавить модели**. CLI без входа или без установки не показывает таблицу моделей — только состояние и действие. Модель, зарегистрированная с несколькими усилиями, — **одна строка** с чипом на каждое усилие; каждый чип по-прежнему отдельный воркер со своим **Где используется** и своим переключателем **Включён**. У каждого CLI этого блока есть раннер — OpenCode, Cursor Agent, Gemini CLI и Grok CLI запускают задачи, как и остальные три. Если когда-либо появится CLI без раннера, его блок скажет «Crewboard пока не запускает задачи на X — модели показаны для справки», у его моделей не будет переключателя **Включён**, и ни один выбор их не предложит — список, где такой воркер ещё стоит, помечает его «не запускается на этой машине».
2. **Через dsh (API)** — модели каталога dsh по провайдерам dsh ([модели из dsh](#модели-из-dsh)), под строкой «Ключи и модели — в dsh.» и кнопкой **Открыть настройки dsh**. Модель, которой больше нет в dsh, помечена **Заблокирован в dsh**, её переключатель недоступен. Если моделей нет: «Моделей нет. Настройте их в dsh → Settings → Models.», а встроенный маршрут `dsh/deepseek-flash` показан одной строкой «Встроенный маршрут DeepSeek V4 Flash ждёт ключа в dsh.» вместо заблокированной строки; встроенный пресет пропускает его при запуске, пока dsh не покажет модель. Id остаётся прежним, старые планы и пресеты с ним работают.
3. **Другое / импортированное · N** — свёрнуто по умолчанию, с пояснением «Появилось само при подключении CLI или dsh. Не требуется для работы — можно оставить свёрнутым.» N — число записей:
   - **дубликаты**: воркеры с тем же транспортом, моделью и усилием, что у другого, какие бы у них ни были id, — `claude-code` и `claude-sonnet`, оба «Claude Sonnet 5 · high». В своей секции остаётся зарегистрированная копия, иначе не импортированная, иначе та, что стоит в каком-то списке. Выберите, какую оставить, в **Оставить один** и нажмите **Убрать остальные**; остальные уходят и из всех списков, где стоят.
   - **импортированные**: профиль из старого инструмента (`origin: porch-import`), который не стоит ни в одном списке. **Добавить как воркер** делает его вашим — он переходит в секцию своего CLI, и пресет по умолчанию может его выбрать, — а **Убрать** удаляет.
   - **устаревшие id**: id, который называет класс, пресет или переключатель, но который ничем не задан на этой машине, например `codex-reserve`. **Убрать** вычёркивает его из маршрутизации, переключателей и всех сохранённых пресетов.

Колонка переключателей — **Включён**: может ли оркестратор брать этого воркера. **Где используется** — компактные чипы «маршрутизация · код №2» или «Claude · ревью №1»; чип открывает этот пресет и показывает его класс. Запись пресета, которая указывает на выключенного, заблокированного или неизвестного воркера либо на воркера CLI без входа, остаётся в списке с пометкой **недоступен на этой машине** и ссылкой на строку воркера.

Каждый блок провайдера — CLI в **Подписках** и провайдер dsh в **Через dsh (API)** — сворачивается в одну строку: имя, состояние, «N моделей · M в пресетах» и главное действие (**Проверить доступ**, после входа — **Добавить модели**); щелчок по строке его раскрывает. Провайдер, чьи модели стоят в маршрутизации или пресете, открыт с самого начала, остальные свёрнуты; ваш выбор для каждого провайдера запоминается в этом браузере. В заголовке каждой секции — **Развернуть все** / **Свернуть все**.

`crewboard workers` печатает те же три группы, по строке-сводке на провайдера, и затем порядок по классам; `crewboard workers --all` перечисляет под провайдером все модели — усилия модели одной строкой.

## Подписки: добавить модели

Claude, Codex, Devin, OpenCode, Cursor Agent, Gemini CLI и Grok CLI работают по подписке или аккаунту самого человека: каждый CLI входит в аккаунт на машине (`claude auth login`, `codex login`, `devin auth login`, `opencode auth login`, `cursor-agent login`, `grok login`; у Gemini CLI вход выполняется внутри `gemini` — *Sign in with Google* — или через `GEMINI_API_KEY`, команды входа у него нет), а Crewboard аккаунтом не занимается. Автоматические запуски Claude — исключение: они не используют подписочный вход, а требуют явного `ANTHROPIC_API_KEY` и официального endpoint Anthropic (см. [автоматизацию Claude](#автоматизация-claude-подписки-и-безопасность-аккаунта)); `claude auth login` в блоке Claude предназначен для интерактивной работы вне Crewboard. В настройках у каждого из них есть блок в секции **Подписки** с кнопкой **Проверить доступ**; когда проверка показывает, что вход выполнен, кнопка **Добавить модели** показывает модели этого CLI. Отметьте модели и — там, где CLI его принимает — усилия: Crewboard добавит по воркеру на каждую модель и усилие — тех же воркеров, что создаёт `crewboard workers add … --effort`, — без правки файлов. Воркер с уже существующим id остаётся как был, поэтому изменённое вами имя сохраняется.

Откуда берётся список:

| CLI | Список моделей |
| --- | --- |
| Codex | `codex debug models --bundled`: каталог, встроенный в установленный Codex, читается без сети; вместе с ним — усилия, которые принимает каждая модель. |
| Devin | `devin models list --format json`: модели аккаунта, в который выполнен вход. Devin не принимает усилие, поэтому каждая модель — один воркер `devin/<модель>`. |
| Claude | У Claude Code нет команды со списком моделей, поэтому Crewboard перечисляет текущие: `claude-fable-5-1`, `claude-opus-5-5`, `claude-sonnet-5`, `claude-haiku-4-5`. Любая другая модель по-прежнему добавляется через `crewboard workers add`. |
| OpenCode | `opencode models`: по строке `<провайдер>/<модель>`. |
| Cursor Agent | `cursor-agent --list-models`: модели аккаунта, в который выполнен вход. |
| Gemini CLI | Команда списка на установленном CLI не проверена (здесь не установлен), поэтому Crewboard перечисляет задокументированные алиасы `--model` — `auto` (умолчание CLI), `pro`, `flash`, `flash-lite`; конкретная версия вроде `gemini-3-pro-preview` тоже добавляется через `crewboard workers add`. |
| Grok CLI | `grok models` задокументирована, но её вывод на установленном CLI не проверен, поэтому Crewboard перечисляет `grok-4.7`; любая другая модель добавляется через `crewboard workers add`. |

То же из CLI:

```sh
crewboard workers models codex
crewboard workers models opencode
crewboard workers add-models claude --models claude-sonnet-5,claude-opus-5-5 --effort high,medium
crewboard workers add-models devin --models swe-2-high
crewboard workers add-models opencode --models deepseek/deepseek-flash --effort high
```

Идентификаторы строятся как `<вид>/<модель>[-<усилие>]`, у Claude без префикса `claude-`: `claude/sonnet-5-high`, `codex/gpt-6-astra-medium`, `devin/swe-2-high`, `opencode/deepseek/deepseek-flash-high`. Id модели OpenCode сохраняет форму `<провайдер>/<модель>` внутри id воркера.

## Как запускаются эти CLI (rb1)

OpenCode, Cursor Agent и Grok CLI работают как Codex: по процессу на ход, а отложенное или прерывающее направление продолжает сессию (OpenCode `--session`, Cursor Agent `--resume`) или — для Grok, у которого проверенного флага возобновления нет — начинает новый одноходовой. Gemini CLI намеренно работает одноходово: каждый ход — `gemini --output-format json` с промптом на stdin (конвейерный, не-TTY stdin включает headless-режим в исходниках — задокументированная форма `cat file | gemini`), и направление всегда ждёт конца идущего хода. Его `stream-json` по документации существует, но не используется — один объект на выходе самый маленький контракт, который можно честно держать на CLI, которого здесь нет. Добавить следующий CLI любой из двух форм — это строка в таблице раннера плюс парсер его потока, а не новый бэкенд.

- OpenCode: `opencode run --pure --format json --auto --agent build|plan -m <провайдер>/<модель> [--variant <усилие>] [--session <id>] --dir <cwd>` — проверено вживую на 1.18.30.
- Cursor Agent: `cursor-agent --print --output-format stream-json --stream-partial-output --force|--mode plan [--model <модель>] [--resume <chatId>]` — проверено вживую по `--help` версии 2026.01.23; реальный запуск с входом на машине разработки невозможен (входа нет), поэтому форма потока покрыта фейками.
- Grok CLI: `grok --output-format streaming-json --verbatim --always-approve|--sandbox read-only -m <модель> [--reasoning-effort <усилие>] --prompt-file <файл>` — проверено только по адаптеру старого инструмента (пробовано на Grok Build 0.2.112) и фейкам; CLI здесь не установлен.
- Gemini CLI: `gemini --output-format json --approval-mode yolo|plan -e none --allowed-mcp-server-names "" [--model <модель>]` с промптом на stdin — проверено только по актуальной документации CLI и исходникам upstream; здесь не установлен. Его режим `plan` подтверждён только документацией, поэтому черновик (которому нельзя писать) получает одноразовый worktree вместо доверия к флагу.

## Модели из dsh

Каждая модель, доступная по API, приходит из dsh: провайдеры и их ключи хранит dsh, а Crewboard только называет провайдера и модель. Настройки показывают каждую модель, настроенную в **Settings → Models** в dsh, как воркера «<Модель> · через dsh», сгруппированного по провайдеру dsh. Список следует за конфигурацией dsh: провайдер или модель, добавленные или убранные там, появляются или исчезают в настройках Crewboard без перезапуска. Ключи Crewboard не читает и не хранит.

Идентификатор воркера модели dsh — `dsh/<провайдер>/<модель>`, например `dsh/deepseek-official/deepseek-v4-pro` или `dsh/openrouter/qwen/qwen-4`; в имени модели тоже может быть `/`. Регистрировать его не нужно: его можно включать и выключать, ставить в порядок классов и в пресеты, называть через `-a` — как любого воркера. Старый вид `dsh/<модель>` остаётся псевдонимом модели маршрута DeepSeek в dsh (`deepseek-official`): `dsh/deepseek-flash` — тот же воркер, что `dsh/deepseek-official/deepseek-flash`, и показывается одной строкой под старым id, поэтому маршруты, пресеты и планы, где он указан, продолжают работать.

Модель, убранная из dsh, не выпадает из маршрутов и пресетов. Если кто-то из них всё ещё её называет, настройки оставляют её строку с пометкой **Заблокирован в dsh**, а её переключатель недоступен; её запуски падают с ошибкой dsh, пока модель не вернётся в dsh или пока вы не уберёте её из списков. Провайдер, который не смог отдать список моделей, назван под списком, и его модели не помечаются пропавшими.

Каталог моделей dsh попадает в Crewboard через хост dsh (его контроллер сессий). У CLI его нет: `crewboard workers` показывает в группе **Через dsh (API)** только сохранённых воркеров dsh и названных в списках и ничего не утверждает о моделях, которых в dsh больше нет; `-a dsh/<провайдер>/<модель>` в CLI работает так же.

Профили воркеров (модель, транспорт, отображаемое имя, усилие, признак включения), псевдонимы и общий порядок машины хранятся в `~/.config/crewboard/profiles.json`. Если файла нет, первый запуск копирует `~/.config/dsh-orchestra/` или импортирует старую конфигурацию porch (`~/.config/porch/config.json` или файл из `PORCH_CONFIG`), не меняя источник.

## Усилие

У воркера может быть **усилие** (effort) — насколько глубоко думает модель. Crewboard передаёт его CLI при каждом запуске этого воркера:

| Тип | Как попадает в CLI | Допустимые значения |
| --- | --- | --- |
| `claude` | `claude --effort <уровень>` | `low`, `medium`, `high`, `xhigh`, `max` |
| `codex` | `codex exec -c model_reasoning_effort="<уровень>"` | `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`, `ultra`, `persistent` (какие из них учитываются, решает модель) |
| `opencode` | `opencode run --variant <уровень>` | `minimal`, `low`, `medium`, `high`, `max` — общий набор; варианты зависят от провайдера, у провайдера их может быть больше |
| `grok` | `grok --reasoning-effort <уровень>` | `low`, `medium`, `high` (подтверждено документацией, здесь не установлен) |
| `devin`, `dsh`, `cursor`, `gemini` | не передаётся: эти CLI не принимают флаг усилия | — |

Воркер без усилия работает со значением CLI по умолчанию — для Codex это `model_reasoning_effort` из `~/.codex/config.toml`. Усилие, которое CLI не примет, отклоняется до запуска, со списком допустимых значений:

```text
✗ effort: Claude Code не принимает усилие «minimal»; допустимо: low, medium, high, xhigh, max
```

Чтобы использовать одну модель с разным усилием, зарегистрируйте её по разу на каждое. Это отдельные воркеры со своими идентификаторами; порядок классов, пресеты и назначения работают с ними как с любыми другими:

```sh
crewboard workers add claude/sonnet-5-high --kind claude --model claude-sonnet-5 --label "Claude Sonnet 5" --effort high
crewboard workers add claude/sonnet-5-medium --kind claude --model claude-sonnet-5 --label "Claude Sonnet 5" --effort medium
crewboard presets add sonnet --label "Sonnet по классам" \
  --code claude/sonnet-5-medium --design claude/sonnet-5-high --review claude/sonnet-5-high --research claude/sonnet-5-medium
```

Везде, где перечислены воркеры, — в `crewboard workers`, настройках, выборе пресета и строке воркера в панели задачи — усилие стоит после имени: «Claude Sonnet 5 · high». Каждый запуск записывает своё усилие рядом с моделью, поэтому экраны расходов и ревью показывают, с каким усилием он шёл. Воркер Devin или dsh, зарегистрированный с усилием, показывается без него: до запуска оно не доходит.

## Классы и порядок

У каждой задачи есть класс: `code`, `design`, `review` или `research`. Он задаётся флагом `--class`; без него вид `review` или `research` даёт одноимённый класс, всё остальное — `code`.

У каждого класса — упорядоченный список воркеров. Общий порядок машины — это встроенный пресет **«По умолчанию: воркеры, прошедшие проверку»**:

```sh
crewboard workers route review codex/gpt-6-sol,claude/opus
```

Встроенный пресет сначала пробует список класса, затем всех остальных воркеров реестра: запускается первый, кто проходит предварительную проверку. Поэтому машина, где вошли только в Codex, всё равно запускает задачи `code`, а агент при этом пресете может назвать любого установленного воркера. Пропущенный воркер назван в выводе `crewboard run` и в ленте задачи, например `claude/opus пропущен: не залогинен → codex/gpt-6-luna`. Сохранённый пресет — ровно его списки: пустой список в нём значит, что задачи этого класса автоматически не запускаются.

## Пресеты

Пресет — именованный порядок для всех четырёх классов. С его помощью можно сказать, например, «в этом репозитории — только воркеры по подписке»:

```sh
crewboard presets add subs --label "Подписки" \
  --code claude/opus,codex --design codex/gpt-6-sol --review codex --research claude/fable
crewboard repo preset subs       # для этого репозитория
crewboard plan preset subs       # только для текущего плана
crewboard plan preset --clear    # план снова следует репозиторию
crewboard presets list           # действующий пресет и откуда он взят
```

Действующий пресет выбирается так:

1. пресет плана;
2. пресет репозитория (`.orchestration/preset.json`);
3. **«По умолчанию: воркеры, прошедшие проверку»** — общий порядок машины, затем все остальные установленные воркеры.

Отключённые воркеры и неизвестные идентификаторы убираются из любого действующего пресета. После удаления пресета все репозитории и планы, где он был выбран, возвращаются к пресету по умолчанию.

## Как выбирается воркер

Пресет — решение владельца. Кто может выбрать воркера, зависит от того, кто спрашивает:

- **Человек** — на экране dsh или в интерактивном терминале — может назначить любого воркера, даже вне пресета. У такой задачи появляется метка «выбрано вручную».
- **Агент** — оркестрирующий агент, который вызывает CLI без терминала, или агент в чате через инструменты Crewboard — может назвать только воркера, которого действующий пресет разрешает для класса задачи. Иначе отказ (код выхода 2) со списком разрешённых воркеров. Обычно агенту вообще не стоит называть воркера: пусть решает пресет. Если действительно нужен другой, агент спрашивает человека.

При запуске задачи (`crewboard run <задача>` или «Запустить» на экране):

1. **`-a <воркер>`**, если указан, переназначает задачу (по правилу выше).
2. **Назначенный воркер задачи**, если он есть. Назначение человека работает и вне пресета. Назначение агента работает, только пока текущий пресет его разрешает; после смены пресета решает пресет, а в ленте задачи появляется запись об этом.
3. **Пресет**: список действующего пресета для класса задачи, по порядку. Запускается первый воркер, у которого есть профиль и который прошёл проверку. Выбор пресета не записывается как воркер задачи.

Названный воркер проверяется так же, как автоматический — отключён ли он, есть ли профиль, прошёл ли проверку, — и при неудаче запуск **отклоняется** с причиной; молча подставить другого Crewboard не станет. `crewboard task set <id> --worker auto` снимает назначение, и снова решает пресет.

Каждый запуск записывает фактического воркера, модель, усилие, провайдера и кто его выбрал (пресет, человек или агент), поэтому журнал показывает, кто выполнял каждую попытку, даже если назначение потом сменилось.

## Минимальная версия CLI

Некоторым моделям нужен свежий CLI. Claude Opus 5.5 (`opus-5-5`) объявляет минимум Claude Code **2.1.280**, а каждому автоматическому запуску Claude нужен ещё и bare-режим API-only, поэтому действующий минимум — **2.1.281** (применяется больший из двух). Запись в реестре может задать собственный минимум полем `minCliVersion` в `workers.json`.

Если минимум задан, проверка сравнивает его с `claude --version`. Например, со старым Claude Code:

```text
✗ claude/opus-5-5
   ✓ binary: 2.1.216 (Claude Code)
   ✗ version: Claude Code 2.1.216 старее 2.1.281, требуемой моделью opus-5-5 → обновить CLI (claude update)
```

Автоматическому запуску также нужны поддержка `--bare` и API-key политика из [автоматизации Claude](#автоматизация-claude-подписки-и-безопасность-аккаунта). Минимальная версия проверяется перед каждым запуском и командой `crewboard preflight -a <воркер>`. `crewboard preflight` без `-a` проверяет все включённые профили, но минимальные версии не применяет.

## Воркеры dsh

Воркер dsh запускает агента dsh по ACP: `-a dsh` — модель dsh по умолчанию, `-a dsh/<провайдер>/<модель>` — модель любого провайдера dsh (см. [модели из dsh](#модели-из-dsh)), `-a dsh/<модель>` — модель маршрута DeepSeek в dsh, например `dsh/deepseek-flash`. Запуск выбирает этого провайдера и модель в процессе `dsh --profile acp`, который читает тех же провайдеров, что и экран dsh. Нужен рабочий профиль `acp` в dsh. Стоимость берётся из собственных записей учёта dsh — см. [затраты](costs.md). **Проверьте в своём dsh**, что `dsh --profile acp --dump-config` выполняется, прежде чем полагаться на воркеров dsh.
