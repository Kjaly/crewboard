# Справочник CLI

[Документация](../README.md) · [English](../en/cli.md) | **Русский**

`crewboard` и `orch` — одна и та же программа; при установке CLI появляются оба имени. Справка и сообщения используют то имя, которым вы её вызвали. Страница сверена с `crewboard help all` и исходным кодом команд версии 0.4.0.

Команды запускаются внутри Git-репозитория; план ищется от его корня. Вне репозитория команда остановится с сообщением «Не git-репозиторий».

## Общие флаги

| Флаг | Что означает |
| --- | --- |
| без аргументов, `--help`, `-h`, `help` | Показать короткую страницу «с чего начать»: `init`, `task add --template`, `run`, `status`, `accept`/`merge` — пять команд, которые нужны новичку, плюс `crewboard help all`. |
| `help all` | Показать полный справочник команд (то, что раньше печаталось на `--help`). |
| `--version` | Показать установленную версию и выйти. |
| `--lang en\|ru` | Язык интерфейса для этого вызова. Без флага русский выбирается, если `LC_ALL` или `LANG` начинается с `ru`, иначе английский. Часть сообщений движка плана пока только на русском. |
| `--plan <id>` | Работать не с текущим планом, а с указанным. Понимают `status`, `wait`, `task`, `accept`, `reject`, `supersede`, `drop`, `verify`, `start`, `decision`, `run`, `events`, `trace`, `steer`, `stop`, `attention`, `cost` и `worktree`. Если текущий план в архиве, команда, которая меняет план, без `--plan` отклоняется. |

Коды выхода: `0` — успех, `1` — ошибка или отказ, `2` — ошибка в вызове. У `wait` код `2` означает, что истекло время ожидания. Неизвестная команда, близкая к существующей, печатает подсказку («Неизвестная команда: statuz — может, вы имели в виду status?»), затем короткую страницу. Запись в закрытый канал (`crewboard status | head`) тихо завершается кодом `0` вместо стека.

Команда, которую может выполнить только человек (`mark-merged`, `drop`, `plan restore`, `reject`, `supersede`, `verify --setting off`), отклонённая из-за отсутствия терминала, отвечает: «Эта команда нужна человеку: если вы человек — запустите её в терминале».

## Планы

| Команда | Что делает |
| --- | --- |
| `crewboard init [--goal "…"]` | Создаёт план `main` в `.orchestration/plan.json`, добавляет `.orchestration/` в `.git/info/exclude` и вносит корень репозитория (или рабочей копии) в [список репозиториев Crewboard](#репозитории-на-экране), чтобы экран показал план. Отказывает, если план уже есть. |
| `crewboard plan list` | Список планов: `●` текущий, `○` активный, `·` в архиве, с числом задач. |
| `crewboard plan new <id> --goal "…"` | Создаёт план и делает его текущим. Вносит место в список репозиториев Crewboard, как `init`. |
| `crewboard plan use <id>` | Делает план текущим. Архивный план можно сделать текущим, чтобы читать его; чтобы менять его, нужен `--plan <id>`. |
| `crewboard plan rename <id> --goal "…"` | Меняет цель плана. |
| `crewboard plan restore [--plan <id>]` | Только человек, с подтверждением: возвращает версию плана до последнего сохранения (`plan.json.prev`). См. [если что-то не работает](troubleshooting.md#когда-что-то-пошло-не-так). |
| `crewboard plan archive <id>` / `unarchive <id>` | Убирает завершённый план из списка активных или возвращает его. |
| `crewboard plan split <id> --from <план> --goal "…" --tasks a,b` | Переносит перечисленные задачи из `<план>` в новый план `<id>`. |
| `crewboard plan preset <id>` / `plan preset --clear` | Выбирает пресет воркеров для текущего плана или возвращает выбор репозитория. См. [воркеры](workers.md). |
| `crewboard chat unbind <план>` | Отвязывает план от чата dsh. |
| `crewboard status [--all] [--json] [--plan id]` | Без `--all`: короткая сводка («Открыто 2 из 3 · 1 принята, не слита») и только открытые задачи — закрытые, заменённые и отброшенные не мешаются, а принятая задача остаётся в списке лишь пока не слита; подсказка на `--all`, когда что-то скрыто. `--all` печатает все задачи, как раньше всегда. Задачи и их состояния, что их блокирует, что можно запускать, критический путь и действующий пресет. Принятая задача, чья ветка ещё не слита, помечена «принята, не слита», задача, которая её ждёт, — «ждёт слияния X». `--json` всегда перечисляет все задачи и добавляет `unmerged` (id) и у задач — `unmerged` и `waitingMerge`. Задача на приёмке, чья ветка даст конфликт с базой или с другой задачей на приёмке, помечена «⚠ конфликт с main в src/a.ts»; раздел «Конфликты на приёмке» перечисляет их с готовой командой `reject … --reason`, а `--json` добавляет `conflicts` и `sendBack` ([приёмка](review.md#конфликты-до-приёмки)). В `--json` у каждой задачи с решением есть `lastDecision`: `{by, at, verdict, reason}` ([приёмка](review.md#оркестратор-слышит-ваши-решения)). |

Значки в `status`: `·` отложена, `○` готова, `●` выполняется, `◐` на приёмке, `✓` принята, `✗` закрыта, `⏸` заблокирована, `⊘` заменена или закрыта как ненужная.

### Черновики планов

Воркер может составить черновик плана по спецификации; вы его проверяете и утверждаете как новый план.

Воркер черновика выбирается так же, как воркер запуска: указанный через `-a` должен пройти preflight, иначе черновик не запускается; без `-a` перебирается пресет `research` по порядку, и черновик пишет первый воркер, прошедший preflight. CLI печатает `Черновик напишет: <воркер>` и для каждого пропущенного — первую непрошедшую проверку.

Воркер черновика читает репозиторий, но изменить его не может:

| Бэкенд | Как |
| --- | --- |
| Claude Code | Работает в рабочей копии с `--permission-mode plan`: правки файлов и команды отклоняются. |
| Codex | Работает в рабочей копии в песочнице только для чтения (`-s read-only`). |
| dsh, Devin | Режима только для чтения нет: работают во временном отсоединённом git worktree от `HEAD` вне рабочей копии, который удаляется после попытки. Незакоммиченных изменений в этой копии нет (сама спецификация — в промпте). В папке, которая не git-репозиторий, эти воркеры черновик не пишут — выберите Claude или Codex через `-a`. |

Если попытка не удалась, задание хранит первую строку ошибки воркера, а `job` печатает её с подсказкой, когда причина узнаваема (войти, включить воркера, обновить его CLI). Автоматически выбранный воркер за заданием не закрепляется: `retry` выбирает заново и пропускает воркера, который перестал проходить preflight; указанный через `-a` воркер остаётся за заданием.

| Команда | Что делает |
| --- | --- |
| `crewboard plan draft --from <файл> [-a <воркер>] [--wait] [--skip-preflight]` | Запускает задание черновика. Без `-a` берётся первый воркер `research`, прошедший preflight. `--wait` дожидается конца. |
| `crewboard plan draft jobs` | Список заданий и их состояния. |
| `crewboard plan draft job <задание> [--wait]` | Показывает одно задание или следит за ним. |
| `crewboard plan draft retry <задание> [-a <воркер>] [--wait]` | Повторить: воркер исправляет ответ, не совпавший с форматом черновика, или заново выполняет запрос после сбоя. `repair` — прежнее имя той же команды. |
| `crewboard plan draft drop <задание>` | Отбрасывает задание; промпты и ответы остаются в `.orchestration/draft-runs/`. |
| `crewboard plan draft recover` | Подхватывает задания, процесс которых прервался. |
| `crewboard plan drafts` | Список сохранённых черновиков. |
| `crewboard plan draft show <id> [--json]` | Показывает цель черновика, его задачи (с классом и зависимостями) и открытые вопросы, затем замечания к нему. `--json` печатает сырой объект черновика. |
| `crewboard plan approve <id>` | Только человек: превращает черновик в план, новый план становится текущим. Цикл зависимостей или отсутствующая зависимость не дают утвердить. |
| `crewboard plan discard <id>` | Удаляет черновик. |

## Задачи и решения

```text
crewboard task add <id> --title "…" [--kind implement|review|research|decision|root] [--lane "…"]
                   [--deps a,b] [--worker <профиль>] [--contract <файл> | --template] [--class code|design|review|research] [--backlog]
crewboard task set <id> [--title "…"] [--lane "…"] [--deps a,b] [--worker <профиль>] [--contract <файл> | --template]
                   [--class …] [--status backlog|ready] [--kind implement|review|research|decision|root]
crewboard task show <id> [--plan id] [--json]
```

| Флаг | Что означает |
| --- | --- |
| `--kind` | `implement` (по умолчанию), `review`, `research`, `decision` или `root`. Задачу `decision` закрывает только человек, запускать её нельзя. Задача `root` — собственная работа оркестратора: интеграция на стенде, запуск процессов, база владельца; воркер для неё не запускается никогда (см. [ниже](#собственная-работа-оркестратора)). `task set --kind` меняет тип открытой задачи; у принятой или вытесненной тип не меняется. |
| `--class` | Какой порядок воркеров применять: `code`, `design`, `review`, `research`. Без флага виды `review` и `research` получают одноимённый класс, остальные — `code`. |
| `--deps a,b` | Задачи, которые должны быть приняты раньше. `task set --deps ""` очищает список. |
| `--worker` | Собственный воркер задачи; используется вместо порядка класса. См. [воркеры](workers.md#как-выбирается-воркер). |
| `--contract` | Путь к контракту от корня репозитория. Без него запуск невозможен: задача воркера, добавленная без контракта, помечена **нужен контракт** в `status` (`"needsContract": true` в `--json`) и на экране, не считается готовой к запуску, а `run` отказывает с командой, как подключить контракт. |
| `--template` | Записать заготовку контракта по единому шаблону в `.orchestration/contracts/<план>/<id>.md` и подключить её; результат и проверки допишите до запуска. См. [Напишите контракт](getting-started.md#2-напишите-контракт). `task set --template` делает то же для задачи без контракта. Не для задач `decision` и `root`: им контракт не нужен. |
| `--lane` | Произвольная метка группы для экрана. |
| `--backlog` / `--status` | Отложить задачу или сделать её готовой. `--status` принимает только `backlog` и `ready`. |

`crewboard task show <id>` печатает всё об одной задаче, чтобы для приёмки не сводить вместе `status`, `events`, `attention`, файл контракта и git. **Агентам можно**; команда ничего не меняет, кроме того, что, как и `status`, записывает закончившиеся запуски и слияния. Разделы:

| Раздел | Что показывает |
| --- | --- |
| Заголовок | Название, вид, класс, статус, воркер; зависимости, задачи, которым она нужна, и чего ждёт заблокированная задача (работы или слияния). |
| Рабочая копия | Путь, ветка и база; файлы, изменённые относительно базы, со строками `+`/`−` (закоммиченные и незакоммиченные правки копии; ветка, если копии уже нет; доказательства запуска, если git не отвечает); файлы без коммита. Если записанная база разошлась с [базой по умолчанию](#базовая-ветка) репозитория, предупреждение называет обе и команду, которая приводит копию в порядок. |
| Слияние | Слита в базу (когда, каким коммитом); принята, но не слита — с точными командами, `crewboard merge <id>` и путями, где слияние даст конфликт; на приёмке — её конфликты с базой и другими задачами на приёмке ([Приёмка](review.md#конфликты-до-приёмки)). |
| Последний запуск | Запуск, воркер, исход и время; почему остановился недоделанный запуск или последняя проблема упавшего. |
| Отчёт | Первые строки отчёта и где он целиком: `evidence.json` запуска, сохранённый отчёт оркестратора или `crewboard events <id>`. |
| Вердикт | Результат, отрицательный или спорный — и почему; сколько проверок контракта отчёт воркера называет выполненными; проверки, которые запустил сам Crewboard (прошло из скольких, каждая упавшая с файлом вывода и последними строками), или команда, которая их запускает; расхождение. |
| Проверка оркестратора | Нужна, идёт или проверено, кем и когда, с заметкой. |
| Заметки и решения | Последние заметки: комментарии людей, приёмка, возвраты, слияния. |
| Контракт | Путь к контракту и его блок `<checks>`. |

`--json` печатает структуру целиком: детали задачи из панели на экране (те же поля и значения, включая события и текст контракта) плюс `planId`, `diffstat`, `mergeState` (`merged`, `unmerged` с `commands` и `conflicts`, `in_review` с `conflicts` или `none`), `lastRun` с `reason`, `reportFile` и `checks`. Инструмент оркестратора `orchestra_task` возвращает ту же структуру. Несуществующая задача — отказ одной фразой (выход `1`).

Содержательные решения остаются за человеком. Обычные проверенные задачи поддерживают `accept --auto` и `merge --auto` без терминала.

| Команда | Что делает |
| --- | --- |
| `crewboard accept <id> [--auto]` | Перед вопросом — одна строка с вердиктом, состоянием проверки оркестратора и состоянием слияния (нет конфликтов, или какие пути дадут конфликт), чтобы не пришлось сначала запускать `status` или `task show`. Затем сам вопрос: принимает результат, и если вердикт отрицательный или спорный или в копии есть файлы без коммита (в ветке их нет), вопрос об этом скажет. После приёмки рабочая копия удаляется, если так настроена очистка. Пока ветка не слита, команда печатает точные команды, чтобы закоммитить оставшееся и слить, и называет `crewboard merge`; зависящие задачи ждут слияния ([приёмка](review.md#после-приёмки-слияние)). |
| `crewboard merge <id> [--squash\|--no-ff] [--yes] [--auto] [--into branch] [--json]` | Сливает принятую, но не слитую задачу в её базу в основном репозитории. Сначала проверяет, что базовая ветка выбрана и чиста, в копии нет незакоммиченного и слияние не даст конфликта (`git merge-tree`, файлы не меняются); конфликт — отказ со списком путей. `--no-ff` (по умолчанию) — коммит слияния, называющий ветку задачи, `--squash` — один коммит. Записывает слияние в задачу и убирает копию, как `worktree gc`. `--yes` пропускает вопрос; `--auto` разрешает слияние принятой и проверенной задачи без терминала; `--into` указывает ветку плана, если записанная база ошибочна; `--json` печатает результат (`ok`, `into`, `strategy`, `commit`, `copy`) или отказ (`error`, `message`, `paths`) ([приёмка](review.md#слияние-из-crewboard)). |
| `crewboard mark-merged <id> --reason "…"` | Отмечает принятую, но не слитую задачу слитой, когда её работа попала в базу так, что Crewboard этого не видит: перенесена в основную копию руками и потом поправлена следующими задачами или слита в другом клоне. Только человек и с подтверждением; без интерактивного терминала — отказ. Git не трогается, detached HEAD не мешает. Причина остаётся в ленте задачи, задача уходит из «Принята, не слита», и зависящие задачи могут стартовать. Работа, перенесённая байт в байт, ничего не требует: она считается слитой по содержимому. На экране — **«Отметить слитой…»** в панели задачи ([приёмка](review.md#работа-перенесённая-руками)). |
| `crewboard reject <id> --reason "…" [--rerun [-a <воркер>] [--skip-preflight]]` | Возвращает задачу с причиной; её можно запустить снова, а причина уходит в промпт следующего запуска после контракта. `--rerun` сразу начинает этот запуск в той же рабочей копии — на воркере прошлого запуска или на том, что назван в `-a`, — одним подтверждением на оба шага; решение, root-задача и задача без запусков получают отказ до того, как что-то возвращено ([приёмка](review.md#вернуть-и-перезапустить)). |
| `crewboard supersede <id> --by <id>` | Закрывает задачу, потому что победил другой вариант. |
| `crewboard drop <id> --reason "…"` | Закрывает задачу, которая больше не нужна. Только человек и с подтверждением, как `accept` и `reject`. Статус задачи — **dropped** («закрыта как ненужная»): причина остаётся в истории, задача больше не становится готовой, уходит с критического пути и не запускается. `task set --status` её не открывает. Выполняющуюся задачу сначала остановите; принятую, заменённую или уже закрытую команда не трогает. На экране — пункт **Закрыть как ненужную…** в меню задачи. |

Проверка оркестратором — **агентам разрешено**. Она стоит между законченным запуском и вашим решением; см. [проверку оркестратором](review.md#проверка-оркестратором).

| Команда | Что делает |
| --- | --- |
| `crewboard verify <id>` | Берёт законченную задачу на проверку. На уже проверенной задаче ничего не меняет и печатает сводку: задача остаётся у человека. |
| `crewboard verify <id> --reopen` | Забирает проверенную задачу у человека, чтобы проверить её заново. |
| `crewboard verify <id> --done --note "…" [--confirm]` | Проверено. Сводка обязательна. Сначала печатает вердикт, который увидит человек, и число изменённых файлов; если вердикт спорный или файлы не изменены, просит подтверждения — `y` в терминале, иначе `--confirm`. Обычную проверенную работу оркестратор может затем принять и слить сам; решения, root-задачи, спорные или отрицательные результаты, конфликты и `<human_review>` по-прежнему ждут человека со сводкой над кнопкой **«Принять»**. |
| `crewboard verify <id> --takeover --note "…"` | Забирает сохранённую незакоммиченную работу незавершённого запуска на проверку оркестратора, без нового запуска: запуск остаётся `incomplete`, задача переходит в состояние **«проверяется»**, а оркестратор коммитит копию и передаёт положительный отчёт через `--done --report`. Подходит только незавершённый запуск с сохранёнными изменениями (`left_uncommitted` или `no_claim`); запуск, окончившийся без ответа, так не забирается. |
| `crewboard verify <id> --attest --verdict result\|negative\|disputed --report <файл> --note "…"` | Записывает отдельное суждение оркестратора рядом с отчётом воркера. В основном `Result:` утверждении файла-доказательства должно быть значение, соответствующее вердикту: `Result: received` (или другое положительное) для `result`, `Result: negative`/`Result: blocked` для `negative`. У `disputed` есть ограничение разбора: голое `Result: disputed` не распознаётся (см. [известные ограничения](../audits/2026-09-28/documentation.md#known-limitations)). Для положительной аттестации нужны чистая закоммиченная копия и успешные текущие квитанции всех обязательных проверок контракта на текущем HEAD и ревизии контракта; запись привязывает запуск, хеш доказательства, HEAD и ревизию контракта. См. [независимую аттестацию результата](review.md#независимая-аттестация-результата-воркера). |
| `crewboard verify <id> --return "замечания" [--skip-preflight]` | Возвращает работу воркеру с замечаниями: новый запуск в той же рабочей копии. |
| `crewboard verify <id> --run-checks` | Crewboard сам запускает `<checks>` контракта в рабочей копии задачи — по одной команде, с окружением рецепта и таймаутом на команду, — печатает исход каждой с файлом вывода (и последние строки упавшей) и записывает результат рядом с доказательствами запуска, отдельно от заявления воркера. Печатает расхождение, если воркер заявляет результат, а проверка упала. Код выхода `1`, если проверка упала. Ничего из отчёта не запускается; контракт без проверок так и говорит ([Приёмка](review.md#проверки-запущенные-crewboard)). |
| `crewboard verify --setting on\|off\|default [--scope plan\|repo]` | Включает или выключает проверку для плана (по умолчанию) или репозитория либо сбрасывает сохранённое значение. По умолчанию проверка включена, пока у плана есть чат. `off` просит подтверждения человека. |

Все формы `verify` принимают `--plan <id>`. Обычные `verify` и `--attest` работают с законченной задачей на разборе; `--takeover` — с готовой задачей, у которой незавершённый запуск сохранил незакоммиченную работу; `--done`/`--report` также завершают root-задачу и готовят решение (см. [собственную работу оркестратора](#собственная-работа-оркестратора)).

Пакетной приёмки в CLI нет: `accept` принимает одну задачу, и его вопрос называет задачу, которую оркестратор не проверил. Принять несколько задач разом можно на экране («Принять пакетом») — он заранее отмечает только чистую работу и перед вопросом называет root-задачи без проверки оркестратора; решений в пакете не бывает: решение подтверждается по одному — в панели задачи или записанным из чата ответом через `crewboard decision answer`. На решении `accept` предлагает закрыть его: у решения нет вердикта. Отрицательный или спорный вердикт назван словами, а не кодом.

### Собственная работа оркестратора

Задача `root` — работа, которую оркестратор делает сам, а человек потом принимает. `crewboard run` от неё отказывается и называет эти команды — **агентам разрешено**:

| Команда | Что делает |
| --- | --- |
| `crewboard start <id>` | Берёт готовую root-задачу в работу: на графе, во вкладке «Работа» и в панели задачи она видна как «в работе у оркестратора». Пока она в работе, в «Ждут вас» её нет. |
| `crewboard verify <id> --done --note "…" [--report <файл>]` | Сделано: задача уходит на приёмку с пометкой «проверено оркестратором». `--report` — markdown-файл, который хранится с задачей и показывается там же, где отчёт воркера: первая строка `Результат: получен`, `отрицательный` или `заблокирован`, затем выполненные проверки, доказательства (коммиты, логи, команды) и как воспроизвести. Без `--report` отчётом служит сводка. |

Возвращённая root-задача снова готова к работе, причина — в её заметках; её начинают заново.

Решения готовятся так же: `crewboard verify <id> --done --note "…" [--report <файл>]` на решении записывает варианты и рекомендацию. Когда проверка оркестратором включена (по умолчанию — пока у плана есть чат), решение попадает в «Очередь разбора», только когда его зависимости приняты **и** оно подготовлено; до этого экран пишет, что его готовит оркестратор. Когда проверка выключена — план ведут руками из CLI, без чата, — решение ждёт человека сразу после приёмки зависимостей, как раньше.

Ещё две команды для решения **разрешены агентам** — они записывают то, что человек уже сказал, и ничего у него не спрашивают:

| Команда | Что делает |
| --- | --- |
| `crewboard decision answer <id> --answer "…" --basis "…"` | Записывает ответ, который человек уже дал в чате: `answer` — что он ответил, `basis` — сообщение, на которое запись опирается. Решение закрывается принятым, зависимые задачи разблокируются — повторный Accept в панели не нужен. Оба поля обязательны; задача должна быть решением без незавершённого запуска. Повтор записанного ответа ничего не меняет; другой ответ на закрытое решение отклонён — сначала верните его в подготовку. Это не `accept --auto` и не доказательство подлинности сообщения: за точность основания отвечает оркестратор; чужие чаты он не читает. |
| `crewboard decision prepare <id> --reason "…"` | Возвращает открытое решение оркестратору на подготовку по поручению человека «изучи и предложи»: отметки проверки и работы снимаются, и вопрос уходит из очереди человека до нового `verify --done`. Бриф, заметки и прошлый отчёт остаются в истории (его путь — в записи возврата); зависимые задачи остаются заблокированными; закрытое решение отклоняется. |

## Запуски

| Команда | Что делает |
| --- | --- |
| `crewboard run <id> [-a <профиль>] [--scope s] [--contract f] [--base <ветка>] [--skip-preflight]` | Запускает воркера в рабочей копии задачи. `-a` выбирает воркера и записывает его в задачу. `--contract` заменяет контракт задачи на этот запуск. `--scope` подставляется вместо `{scope}` в базовую проверку рецепта (см. [рецепт рабочей копии](#рецепт-рабочей-копии)). `--skip-preflight` пропускает проверку доступности. Для dsh: `-a dsh` или `-a dsh/<модель>`, например `dsh/deepseek-flash`. Задачу, чья зависимость принята, но не слита, команда не запускает и называет команды слияния; `--allow-unmerged` запускает всё равно — только человек в интерактивном терминале, и в копии этой работы не будет. Если прошлый запуск оставил в копии незакоммиченные изменения, человека спрашивают — продолжить с ними или сбросить копию; `--keep-changes` / `--reset-copy` отвечают заранее, агенту — отказ с обеими командами. `--base` осознанно задаёт базу копии — только человек, из интерактивного терминала; без него новая копия берёт [базу по умолчанию](#базовая-ветка) репозитория, а не то, что случайно выбрано в основной копии, и запуск говорит об этом один раз, если они разошлись. Запрос агента на `--base` отклоняется. |
| `crewboard events <id>` | Лента событий последнего запуска задачи, включая ваши поправки. |
| `crewboard trace <id> [--json]` | Ходы, время модели, вызовы инструментов и поправки последнего запуска. |
| `crewboard steer <id> (--message "…" \| --file f) [--mode auto\|queue\|interrupt] [--relaunch] [--skip-preflight]` | Отправляет поправку работающему воркеру. `queue` ждёт конца текущего хода и становится следующим ходом; `auto` и `interrupt` доходят до воркера во время хода (Claude Code берёт поправку на следующем шаге, Codex перезапускает ход с ней). Каждая поправка заканчивается как подтверждённая или недоставленная с причиной. Если запуск уже закончился, `--relaunch` начинает новый запуск с этой поправкой. |
| `crewboard continue <id>` | Продолжает запуск, закончившийся недоделанным — без отчёта и с незакоммиченной работой (см. [Недоделанные запуски](review.md#недоделанные-запуски)): новый запуск в той же рабочей копии с указанием доделать работу, закоммитить её и отчитаться. Отказ, если последний запуск не закончился недоделанным. |
| `crewboard stop <id>` | Останавливает последний запуск. Запуск Claude Code или Codex, чей последний ход уже успешно закончился (воркер выдал финальный отчёт), завершается как выполненный и уходит на ревью; запуск, остановленный посреди хода, отменяется. |
| `crewboard attention [--all] [--json] [--alarms]` | Что ждёт человека — тот же список, что «Ждут вас» на экране: задачи на проверке (и проверил ли их оркестратор), решения, упавшие или зависшие запуски и другие планы, которые ждут. Текст начинается с единого числа ожидания и его области — «Ждут вас: в этом плане 4 · в этом репозитории 5 — 3 задачи ждут ревью · 1 решение» (`--all`: «всего N»), это то же число, что на экране ([Приёмка](review.md#что-ждёт-вас)), — затем строки сгруппированы по видам; принятое, но не слитое (`unmerged`, команда слияния — в `hint`); в `--json` у каждого пункта есть `kind` (`review`, `decision`, `unmerged`, `attention`, `plan`), а также `root`, `planId`, `taskId` и для тревог — `runId`; у строки задачи есть причина `reason` (`review`, `checkOff`, `blocked`, `decision`, `failed`, `unmerged`) и `planTitle`, у строки фонового плана — `reasons` с числом по каждой причине. Строки плана-примера появляются, только когда спрошен сам пример (открытый план репозитория или `--plan` с его id); они идут последними, помечены `example` и не считаются. `--all` их не показывает. `--all` — по всем репозиториям, которые показывает экран (работает из любой папки). `--alarms` — только тревоги запусков (упал, завис, повторяется), как команда работала раньше. «Всё спокойно.» — только когда ничего не ждёт. |
| `crewboard cost [--json]` | Итоги по воркерам: запуски, минуты, списанные деньги (`деньги $X`) и оценка по API-ценам (`оценка ≈$Y`) рядом, без общей суммы, токены, квота. Для плана без запусков — `В плане <id> запусков нет.` См. [затраты](costs.md). |
| `crewboard wait [--for decision\|finished\|check\|any] [--tasks a,b] [--interval 15s] [--timeout 30m] [--json]` | Ждёт, пока задачу решат, запуск закончится или случится шаг проверки оркестратором (`check`). Ждёт следующего изменения; с `--tasks`, если все перечисленные задачи уже там (запуск закончен, проверка сделана, решение принято или задача закрыта), сразу выходит с `0` и печатает их с пометкой `уже` (в JSON — `"already": true`). Выход `0` — событие, `2` — время вышло (30 минут, если `--timeout` не задан), `1` — ошибка. Длительности: `ms`, `s`, `m`, `h`; число без единиц — секунды. Предназначена для фонового запуска оркестрирующим агентом; заодно обновляет состояние воркеров, когда экран dsh закрыт. |

Запуск отклоняется, если задача заблокирована, уже выполняется, принята или заменена, является решением или root-задачей, не имеет контракта или ни один воркер не прошёл проверку. Контракт без блока `<checks>` или без строки результата запуск не останавливает: после запуска `run` печатает предупреждение о каждом. Сообщение называет причину, а отказ длиннее одной строки (красный базовый прогон с хвостом вывода, список проверок) заканчивается строкой `✗ <id> не запущена: <причина>`, так что последняя строка вывода — всегда причина.

## Базовая ветка

У репозитория есть **база по умолчанию**: его `origin/HEAD`, иначе `main` или `master` — а не та ветка, что случайно выбрана в общей основной копии. Запуск берёт её для каждой новой копии и записывает в задачу; повторно используемая копия сохраняет свою уже записанную базу. Если в момент запуска в основной копии выбрана другая ветка, задача всё равно ветвится от базы по умолчанию, и запуск говорит об этом одной строкой — чтобы выбранную в основной копии ветку не приняли за то, куда пойдёт работа. Именно с этой базой сравнивают слияние, конфликты и «обновление ветки».

| Команда | Что делает |
| --- | --- |
| `crewboard repo default-base [<ветка>\|--clear]` | Без значения показывает действующую базу по умолчанию и её источник. С веткой — переопределяет для этого репозитория. `--clear` возвращает к собственной базе репозитория. |
| `crewboard plan default-base [<ветка>\|--clear]` | То же самое, но только для текущего плана; переопределяет настройку репозитория. |
| `crewboard run <id> --base <ветка>` | Человек осознанно выбирает базу задачи, один раз, из интерактивного терминала. Запрос агента на `--base` отклоняется. |

Копия, чья записанная база разошлась с текущей базой по умолчанию репозитория — человек выбрал её осознанно, либо база по умолчанию с тех пор сменилась, — показывает это один раз в панели задачи и в `crewboard task show`, с командой, которая обновит ветку до новой базы или уберёт копию для перезапуска от неё.

## Репозитории на экране

Экран показывает репозитории из трёх списков, объединяя их без повторов: воркспейсы dsh, настройка плагина `repos` (вместе с `CREWBOARD_REPOS`) и собственный список Crewboard в `~/.config/crewboard/repos.json`. CLI пишет только в последний. `crewboard init` и `crewboard plan new` вносят место, где работают; вручную список ведут эти команды:

| Команда | Что делает |
| --- | --- |
| `crewboard repo add [путь]` | Вносит этот репозиторий или репозиторий по `пути` в список Crewboard. `~` раскрывается; вложенная папка вносится как корень своего репозитория, рабочая копия — как свой корень. Отказывает, если папка не Git-репозиторий и не рабочая копия. |
| `crewboard repo list` | Все места, которые показывает экран, и откуда они: `воркспейс dsh`, `настройка repos плагина`, `список Crewboard` или `рабочая копия <репозиторий>`. Папка, которой больше нет, помечена `нет на диске`. |
| `crewboard repo rm <путь>` | Убирает путь из списка Crewboard. Файлы, планы и рабочие копии остаются на диске. Путь, которого больше нет, убирается так же. Воркспейс dsh или путь из `repos` здесь не убрать; сообщение говорит, где это сделать. |

Рабочие копии находятся сами: для каждого репозитория из списков экран выполняет `git worktree list` и показывает каждую копию, где есть план (`.orchestration/`), — под репозиторием, с пометкой **рабочая копия**. Собственные копии задач Crewboard (`<репозиторий>-orch-<задача>`, рядом с репозиторием) никогда не показываются отдельными планами, даже если в них появился файл плана: это рабочее место воркера над задачей, а не отдельное место.

Если команда работает с планом, которого экран не показывает, после своего вывода она печатает одно предупреждение с командой, которая это исправит (`crewboard repo add`). Предупреждение появляется, только если установлен dsh (есть `~/.dsh`), и никогда — в копии задачи.

## Окружение

| Команда | Что делает |
| --- | --- |
| `crewboard preflight [-a <профиль>] [--probe] [--json]` | Проверяет, что CLI воркеров установлены и вход выполнен. Без `-a` проверяются все включённые профили. С `-a` проверяется ещё и минимальная версия Claude Code для модели. `--probe` отправляет пробный запрос, где это поддерживается. Выход `1`, если проверка не прошла. |
| `crewboard worktree prepare <id> [--scope s]` | Создаёт или переиспользует рабочую копию задачи и выполняет рецепт, не запуская воркера. |
| `crewboard worktree list` | Рабочие копии задач: чистые или изменённые, приняты или нет, и последний базовый прогон. |
| `crewboard worktree gc` | Предпросмотр: какие копии можно удалить, какие остаются и почему, с размерами. Ничего не удаляет. |
| `crewboard worktree gc --yes` | Удаляет подходящие копии. Непринятые, запущенные, изменённые, неслитые и три последние принятые остаются. Удаление — через `git worktree remove` без force. Печатает каждую убранную копию или `Ничего не убрано: оставлено N — …` с причинами. |
| `crewboard worktree gc --force <id>` | Только человек: удаляет одну копию, даже если в ней есть изменения. |
| `crewboard slot -- <команда…>` | Ждёт свободный [слот проверки](#слоты-проверки), затем выполняет `<команду>`: код выхода и вывод не меняются. |
| `crewboard slot --set <n>` | Задаёт число слотов проверки на машине. |
| `crewboard slot` | Показывает число слотов проверки на машине (настроенное или по умолчанию). |

### Рецепт рабочей копии

Новая рабочая копия — это чистый checkout `HEAD`. Необязательный `.orchestration/recipes.json` готовит её до запуска воркера:

```json
{
  "setup": ["pnpm install --frozen-lockfile", { "copy": ".env.local" }],
  "env": { "unset": ["NODE_OPTIONS"] },
  "baseline": "pnpm test {scope}",
  "timeoutSec": 300
}
```

Шаги `setup` — это команды оболочки или `{ "copy": "<путь>" }`, чтобы скопировать файл или папку из основного checkout, например неотслеживаемый `.env.local`. `env.unset` убирает переменные из окружения шагов. `baseline` — проверка, которая должна пройти, прежде чем задача уйдёт воркеру: красная базовая проверка отменяет запуск. У каждого шага свой лимит `timeoutSec` (по умолчанию 300). Уже существующая копия перематывается (fast-forward) на `HEAD` репозитория, если в ней нет незакоммиченных изменений. Её `setup` выполняется повторно, только если он так и не завершился. `baseline` прогоняется снова, если последний прогон не был зелёным, шёл с другой командой или копия тогда ещё не содержала текущий `HEAD` репозитория. Собственные коммиты воркера изменением не считаются. Поэтому красный или неизвестный базовый прогон, например в копии, созданной старой версией, всегда повторяется до старта воркера. Последний результат (коммит, команда, зелёный или красный, время) показывают `crewboard worktree list` и панель задачи.

Вывод упавшего шага не кладётся в сообщение целиком. Crewboard пишет его в `.orchestration/output/<задача>/<время>-<вид>.log` (`baseline`, `prepare` или `refresh` для конфликта при обновлении копии), а сообщение называет файл, его размер и показывает последние 20 строк. У задачи хранятся 10 последних таких файлов; `worktree gc` удаляет их вместе с копией. `crewboard worktree list` и панель задачи называют файл красного базового прогона, а JSON-отказ хоста несёт его полями `output: { path, bytes, tail }`.

### Слоты проверки

Когда одновременно готовится несколько рабочих копий или сразу несколько запусков воркеров гоняют тесты, их базовые прогоны, `verify --run-checks` и собственные тестовые команды воркеров вместе могут разогнать нагрузку машины и превратить короткий тест в дёрганый таймаут. Слот проверки — это общий для всей машины лимит на число таких тяжёлых команд одновременно: он один на все рабочие копии, планы и репозитории машины, а не на репозиторий.

Базовый прогон (выше) и `crewboard verify <id> --run-checks` сами ждут свободный слот; воркеру же говорят (в его правилах, рядом с «запускай долгие проверки на переднем плане») пропускать свои собственные долгие команды (тесты, сборки, нагрузочные прогоны) через `crewboard slot -- <команда…>`, например `crewboard slot -- pnpm test`. `slot` ждёт свободный слот, печатая, пока ждёт, `waiting for a check slot (N ahead)`, затем выполняет `<команду>` с тем же кодом выхода и выводом.

Число слотов по умолчанию — четверть ядер машины, но не меньше одного; `crewboard slot --set <n>` меняет его, а `crewboard slot` без аргументов показывает текущее значение. `CREWBOARD_CHECK_SLOTS` переопределяет его для одного вызова. Блокировка живёт в `~/.config/crewboard/slots/`: каждый занятый слот — это файл с pid, именем машины и временем держателя, та же идея, что и `plan.lock`; слот держателя, чей процесс исчез, перехватывается сразу же, так что упавшая проверка никогда не держит слот впустую.

## Файлы и переменные окружения

| Путь | Содержимое |
| --- | --- |
| `.orchestration/plan.json`, `.orchestration/plans/*.json` | Планы; `.orchestration/current` называет текущий. |
| `.orchestration/runs/<запуск>/evidence.json` | Доказательства, сохранённые по завершении запуска. |
| `.orchestration/preset.json` | Пресет, выбранный для репозитория. |
| `.orchestration/recipes.json` | Необязательный [рецепт рабочей копии](#рецепт-рабочей-копии). |
| `~/.config/crewboard/profiles.json` | Профили воркеров, псевдонимы, общий порядок классов, отключённые воркеры. |
| `~/.config/crewboard/workers.json` | Реестр воркеров. |
| `~/.config/crewboard/presets.json` | Сохранённые пресеты. |
| `~/.config/crewboard/repos.json` | Список репозиториев Crewboard: места, которые экран показывает помимо воркспейсов dsh и `repos` плагина. |
| `~/.config/crewboard/slots/` | Блокировка [слотов проверки](#слоты-проверки): по одному файлу на занятый слот. |
| `~/.config/crewboard/slots.json` | Настроенное число слотов проверки (`crewboard slot --set`). |

`CREWBOARD_PROFILES_FILE`, `CREWBOARD_WORKERS_FILE`, `CREWBOARD_PRESETS_FILE`, `CREWBOARD_REPOS_FILE`, `CREWBOARD_SLOTS_DIR` и `CREWBOARD_SLOTS_CONFIG` задают другое расположение этих файлов; старые имена `ORCH_*` тоже читаются. `CREWBOARD_CHECK_SLOTS` переопределяет само число слотов проверки. При первом запуске существующий `~/.config/dsh-orchestra/` копируется в `~/.config/crewboard/`; оригинал не меняется.
