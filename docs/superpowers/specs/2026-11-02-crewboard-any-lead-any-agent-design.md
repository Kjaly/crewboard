# Crewboard: любой ведущий, любой исполнитель

Дата: 2026-11-02. Статус: черновик на утверждение. Продолжает [дизайн 1.0](2026-11-02-crewboard-lead-chat-design.md).

## Зачем

Crewboard 1.0 на деле привязан к одной связке: ведущий — Claude Code, исполнители — закрытый список из Codex, Claude и DeepSeek через dsh. Владелец хочет другого:

- **Ведущим может быть любой агент**, который умеет подключаться к MCP-серверу: Codex, DeepSeek через dsh, Claude Code и всё, что появится дальше.
- **Исполнителем может быть любой агент**: через собственный CLI или как модель через API внутри dsh (Kimi, GLM, Qwen и другие).
- **Инструмент остаётся максимально простым** и встраивается в привычную работу человека, который каждый день пользуется Claude Code или Codex.

Анализ рынка (Codex на GPT-6 Astra, 2026-11-02) показал: объединять нескольких агентов уже умеют многие (Claude Code Agent Teams, субагенты Codex, Vibe Kanban, Conductor, PAL MCP, Agent Deck, GitHub Copilot Projects, OpenHands). Число поддерживаемых моделей нас не выделит.

## Позиционирование (решено владельцем)

> Crewboard — локальный диспетчер поручений для привычного агентного чата: сохраняет контекст, критерии и контроль, когда меняются исполнители и даже сам ведущий.

Отсюда приоритет: сначала надёжность поручений и контроль владельца, потом любой ведущий, потом реестр агентов как средство и простой первый запуск.

## Цели

1. Поручение не теряет смысла и состояния: реплика владельца, критерии, исполнитель, вопросы, решения и итог переживают смену исполнителя, смену ведущего и сбой.
2. Владелец всегда может остановить работу.
3. Любой MCP-клиент подключается ведущим без особой поддержки с нашей стороны.
4. Нового исполнителя добавляют записью в конфиге, без правки кода Crewboard.
5. Человек с установленным Claude Code или Codex запускает Crewboard и подключает ведущего за несколько минут.

## Не цели

- Свой чат или IDE. Человек разговаривает в своём агенте.
- Собственный агентный цикл с инструментами для моделей через API. Эту обвязку даёт dsh или CLI агента.
- Облачная командная платформа, маркетплейс ролей, конструктор процессов, автоматический выбор «лучшей модели».
- Обязательная ручная приёмка работы владельцем.

## Анти-цели (провал, даже если работает)

- Каталог агентов превращается в набор несовместимых исключений под каждого провайдера.
- Подключение нового ведущего или исполнителя требует от пользователя читать наш код.
- Экран показывает «Готово» или «Идёт» там, где этого не происходит.

## Решения владельца

### Аварийная остановка доступна всегда

Обычная остановка остаётся просьбой, которую решает ведущий. «Аварийная остановка» видна на любом работающем узле, независимо от того, на связи ли ведущий. Она требует подтверждения вторым нажатием, останавливает узел и всё под ним сразу. В журнал она пишется как решение владельца в обход ведущего, а ведущий узнаёт о ней из входящих.

Сейчас остановка разрешена только при молчании ведущего дольше `LEAD_OFFLINE_MS` (`model/project.ts`, `availableActions`; `requests.ts`, `emergencyStop`). Это ограничение снимается. Код системного текста `emergency_stop` и его формулировки в словарях меняются: «аварийная остановка владельцем», без упоминания, что ведущий был не на связи.

### Claude-исполнитель работает с настройками пользователя

Сейчас Claude Code запускается с `--bare` (`core/src/runs/cli-runner.ts`) и не видит CLAUDE.md, навыки, хуки и MCP пользователя. По умолчанию это убирается: Claude работает как Codex и dsh, со своими обычными настройками. Изолированный режим остаётся флагом в описании агента (см. реестр) для тех, кому нужна чистая среда.

### Claude-исполнитель работает по обычному входу пользователя, включая подписку

Вместе с `--bare` уходит правило «только API-ключ» (`core/src/routing/anthropic-policy.ts`, ревизия `anthropic-api-only-2026-09-28`). Владелец ввёл его из осторожности, пока статус оплаты `claude -p` был неясен. Проверено 2026-11-02 по первоисточникам:

- статья поддержки Anthropic 15036540 (обновление 2026-10-07): при входе по плану Claude `claude -p` и Agent SDK списываются с лимитов подписки; летнее изменение оплаты приостановлено, новой даты нет;
- страница Claude Code «Legal and compliance»: пользователь может входить в немодифицированный Claude Code своей подпиской; лимиты рассчитаны на «обычное индивидуальное использование»; стороннему инструменту нельзя собирать, хранить или пропускать через себя чужие учётные данные.

Новое правило:

- По умолчанию Crewboard запускает официальный бинарник Claude Code так, что тот сам выбирает вход пользователя: подписку, API-ключ из окружения или настроек — как при ручном запуске.
- Crewboard никогда не читает, не хранит и не передаёт учётные данные Claude. Он только запускает бинарник на машине пользователя.
- Запись агента в реестре может требовать API-ключ (прежнее поведение) для тех, кто хочет оплату только через Console.
- Экран и аналитика показывают, по какому каналу прошёл запуск, если Claude Code это сообщает: подписка или API-ключ. Стоимость запуска по подписке показывается как «по подписке», не как деньги.
- Документация честно предупреждает: много параллельных Claude-исполнителей может выйти за «обычное индивидуальное использование», а приостановленное изменение оплаты Anthropic может вернуть.

### «Доложено» отдельно от «Готово» у частей работы

Части, которые исполнитель сам выделил разбиением, сейчас закрываются автоматически по итогу (`supervisor.ts`, `closed` от `system`). Вместо этого вводится состояние **«Доложено»**: итог части уходит родителю, родитель продолжает работу, а узел показывает «Доложено, проверит родитель». В «Готово» такие части переходят, когда ведущий закрывает родителя: его проверка покрывает всё, что под ним. Ведущий не закрывает каждую часть отдельно.

## Что строим

Порядок частей — порядок поставки. Каждая часть — отдельный план и отдельный набор коммитов.

### Часть 1. Надёжность и контроль

1. Аварийная остановка всегда (выше).
2. Состояние «Доложено» (выше). Новый статус в модели и обоих словарях, дерево и сводка учитывают его. Статусы по-прежнему выводятся из журнала, не хранятся.
3. **Входящие ведущего доставляются хотя бы один раз.** Сейчас `crewboard_inbox` подтверждает события сразу при чтении (`lead/commands.ts`). Если ведущий упал, не обработав их, они потеряны. Нужно, чтобы событие оставалось во входящих, пока ведущий явно его не подтвердил. Как именно подтверждать (отдельный инструмент, параметр с номером последнего обработанного события), решает разработчик. Важно, чтобы ведущий без поддержки этого механизма не застревал на одних и тех же событиях бесконечно.
4. Claude с настройками и обычным входом пользователя, включая подписку (выше).

Уже исправлено в main (a5c018a) и сюда не входит: уточнения для поручений в очереди, запуск «ответа» и «решения» только на чтение.

### Часть 2. Реестр агентов

Закрытый список `PROVIDERS = ['claude', 'codex', 'deepseek']` (`model/types.ts`) и таблицы в `workers/providers.ts` заменяются реестром.

- **Запись агента**: имя (идентификатор в журнале и в инструментах ведущего), подпись и цвет на экране, способ запуска, модель по умолчанию, флаг изоляции для Claude.
- **Способы запуска**: адаптеры, которые уже есть в core (`core/src/orchestration/backends.ts`): claude, codex, opencode, cursor, gemini, grok, devin, dsh. Для dsh запись указывает маршрут и модель профиля dsh. Так подключаются Kimi, GLM, Qwen: модель описывают в профиле dsh (модуль `dsh-llm-pi-ai` умеет OpenAI-совместимые адреса), а в реестре Crewboard — одной записью.
- **Где лежит**: файл в `~/.crewboard` рядом со списком проектов. Встроенные записи для Claude, Codex и DeepSeek работают без файла.
- **Журнал** хранит имя агента строкой. Цели со старыми или удалёнными из реестра агентами продолжают читаться и показываться, только запустить по ним новую работу нельзя.
- **Ведущий видит реестр**: инструмент со списком доступных агентов и их возможностями (умеет ли запуск только на чтение, продолжение сессии, остановку). Описание `crewboard_assign` больше не перечисляет провайдеров жёстко.
- Учёт затрат и аналитика работают по любому агенту. Если цена неизвестна, показывается «нет данных».

### Часть 3. Любой ведущий

- **Нейтральные тексты**: экран и документация говорят «ведущий», а не «Claude Code», там, где имеется в виду любой ведущий.
- **Подключение**: пустой экран и документация дают готовые команды подключения для известных клиентов (как минимум Claude Code, Codex, dsh) и общий адрес MCP для остальных.
- **История из транскриптов, автоматически.** Для известных клиентов Crewboard сам находит и читает журналы разговоров: Claude Code уже поддержан (`history/`), добавляются Codex (`~/.codex/sessions`) и dsh. Читатель транскриптов — сменный модуль на каждый клиент.
- **Без транскрипта история не пустая.** Для ведущего, чьи журналы мы читать не умеем, вкладка «История» показывает ход работы из нашего журнала: поручения, вопросы, ответы, решения, просьбы владельца. Для этого ведущий передаёт в инструментах, кто он (имя клиента и идентификатор сессии), и Crewboard запоминает это у цели.
- **Передача цели другому ведущему** остаётся через `crewboard_adopt_goal`. История показывает смену ведущего.

### Часть 4. Простой первый запуск

- Готовый пакет: `npx crewboard` или установка одной командой без клонирования и сборки. Публикация в npm — отдельное решение владельца в момент релиза.
- Проверка окружения при запуске: какие CLI агентов установлены, их версии и вход, видно ли dsh. Результат — понятная сводка в терминале и на пустом экране.
- Подключение ведущего одной командой для известных клиентов.
- Внятная ошибка, если порт занят.

## Ограничения

- Всё локальное: сервер слушает только loopback и проверяет имя хоста (сделано в 1.0).
- Журнал только дописывается, события проверяются схемой. Новые поля и статусы совместимы со старыми журналами: старая цель открывается без миграции.
- Интерфейс на английском и русском; каждый новый текст — в обоих словарях.
- Политика тестов проекта: мало тестов, про поведение; новая ветка поведения — строка в существующей таблице.

## Оставлено разработчику

- Формат файла реестра и его проверка.
- Механизм подтверждения входящих в части 1.3.
- Как ведущий сообщает, кто он, и где Crewboard это хранит.
- Форматы транскриптов Codex и dsh: изучить по месту, версии клиентов зафиксировать в тестовых образцах.
- Порядок задач внутри каждой части.

## Решения, которые я принял сам (проверьте)

- **Исполнители не получают инструменты Crewboard.** Раздавать, закрывать и подтверждать может только ведущий. Если исполнитель Claude или Codex видит MCP Crewboard в своих настройках, Crewboard исключает себя из окружения исполнителя или отказывает вызовам из запусков, которые он сам начал. Способ выбирает разработчик, результат проверяется тестом.
- **У цели один ведущий в каждый момент.** Ведущий видит во входящих только события своих целей. Подтверждения хранятся по цели. Смена ведущего — только через `crewboard_adopt_goal`. До части 3, пока ведущий не сообщает, кто он, ведущий проекта считается одним.
- **«Доложено» следует за родителем.** Ведущий закрыл родителя: доложенные части под ним, на любой глубине, становятся «Готово». Родителя отменили, включая аварийную остановку: доложенные части становятся «Брошено», как сейчас незавершённая работа под отменённым узлом. Родителя передали другому исполнителю, вернули на доработку или его запуск упал: части остаются «Доложено».
- **Обычная остановка не меняется.** Просьба «Остановить» по-прежнему ждёт ведущего, а аварийная показывается рядом всегда. Если ведущий не на связи, подсказка у просьбы говорит, что ответа может не быть, и предлагает аварийную.
- Порядок частей: надёжность, реестр, любой ведущий, первый запуск.
- Реестр — файл в `~/.crewboard`, встроенные агенты работают без него.
- Агенты через API подключаются только через dsh, своего агентного цикла нет.
- История для «неизвестного» ведущего строится из нашего журнала, без требования присылать реплики разговора.
