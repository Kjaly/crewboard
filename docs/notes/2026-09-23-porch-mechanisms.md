# Porch: механизмы, которые надо заменить

23 сентября 2026. Снято с vendored `packages/porch` в этом worktree. Номера строк ниже относятся к текущим файлам. Это исследовательская заметка: она описывает совместимость, нужную после удаления porch, включая чтение уже созданных записей.

## 1. Devin через ACP

Основной адаптер — `packages/porch/skills/pragmatic-orchestration/scripts/lib/steer/adapters/devin.py`.

- **Запуск и рукопожатие** (`devin.py:77–81,173–215`): дочерняя команда `[devin, acp]`, опционально `--model <id>`, `cwd` = рабочий каталог запуска. Копируется окружение, но из него удаляется `ACP_BACKEND` (внутри Devin Desktop это наследуется как `windsurf` и способно дать ложное `Not logged in`). По NDJSON stdio посылается JSON-RPC 2.0 `initialize` с `protocolVersion:1`, capabilities `{fs:{readTextFile:false,writeTextFile:false},terminal:false}`, `clientInfo:{name:"pragmatic-orchestration",version:"1.0.0"}`; затем `session/new` с `{cwd,mcpServers:[]}`. Обязателен `result.sessionId`, иначе запуск падает. После этого `session/set_mode` с `{sessionId,modeId:"bypass"}` — ошибка только превращается в progress, запуск продолжается. Это yolo-режим. Для начальной задачи уходит `session/prompt` с `{sessionId,prompt:[{type:"text",text:<task>}]}`.
- **Поток** (`devin.py:98–141`): сервер шлёт notification `session/update`, в `params.update.sessionUpdate` адаптер распознаёт `agent_message_chunk` (контент попадает в текст результата и отдельные `text` events), `agent_thought_chunk` (только наблюдаемый thought, не final), `tool_call` (tool event по `title`/`kind`); прочие типы — progress. Также наблюдается `_cognition.ai/agent_stopped`. Текстовый extractor принимает строку, `{type:"text",text}`, вложенное `content` и список таких элементов.
- **Ответы, завершение, ошибки** (`devin.py:234–324,282–308,413–418`): каждый вызов prompt сопоставляется по JSON-RPC `id`, поскольку Devin не возвращает promptId. Ответ с JSON-RPC `error`, закрытие процесса до ответа, неизвестный/пустой stop reason создают `error`/`failed`; `stopReason=end_turn|endturn` означает `completed`, `cancelled|canceled` — cancelled. Только когда нет prompt in-flight и не ждёт interrupt, адаптер завершает весь run по последнему разрешившемуся запросу; отмена даёт exit 130, end-turn 0, остальное 1. Final text — конкатенация только agent message chunks. Процесс, завершившийся сам, тоже даёт done; ненулевой exit фиксируется как ошибка. Транспортный успех не считается доказательством, что steer семантически применён.
- **Поправка и режимы** (`devin.py:326–385`): `auto` и `queue` переводятся в `DeliveryClass.SAME_TURN`: второй `session/prompt` во время активного turn сливается Devin в тот же turn, оба RPC ждут завершения; очередь отдельного следующего turn не гарантируется. `interrupt` — `session/cancel` notification, ожидание разрешения старых prompt до 30 секунд с шагом 50 ms, затем новый prompt. Запрос ответа steer даёт `request_sent`, позже ack становится completed/cancelled/failed по его stopReason; для auto/queue это `acp_concurrent_prompt`, для interrupt — `acp_cancel_then_prompt`. При busy timeout код всё равно пытается послать successor prompt, что может снова попасть в активный turn.
- **Cancel и серверные запросы** (`devin.py:143–169,390–412`): `session/cancel:{sessionId}`; затем terminate и kill process group (таймаут 3 s). На `session/request_permission` автоматически выбирается `allow_once`, иначе первый option с kind `allow*`; на `elicitation/create` ответ cancel. Для остальных server request ответа нет. При старте `devin.py:64` пишет сырые JSON-RPC записи в `<artifacts_dir>/raw/<agent_id>.jsonl`.
- **One-shot path**: `scripts/lib/devin_acp_oneshot.py:113–180` использует то же initialize/session/new/session/prompt семейство. Документация `references/configuration.md:58–65` уточняет, что review запускается `devin acp --agent-type review` (без инструментов записи), а делегирование — default agent type + bypass. Профиль `devin` — модель `swe-2-high`, effort закодирован моделью.
- **Auth**: preflight — уже вызывающая сторона Orchestra, `packages/core/src/preflight/preflight.ts:54–66`: `devin --version`, затем `devin auth status`, успешным считается stdout со строкой `Logged in`. В ACP адаптере отдельной надёжной auth-probe нет: ошибка запуска/session negotiation должна быть сохранена и показана как ошибка, а не трактоваться как prompt failure. Не переносить проверку на одно наличие бинарника.

Для прямой замены нужна ACP 1.0 NDJSON JSON-RPC реализация, request-id корреляция параллельных prompt, event mapping, те же ограничения permission/auth, terminal lifecycle и protocol-ack steer. Основание протокольных деталей — заметки к probe непосредственно в `devin.py:3–17`; версия Devin в них 3000.10.27.

## 2. Codex subscription quota

Источник находится в `scripts/lib/quota.py:78–127`; это не файл кэша и не SQLite: porch запускает `codex app-server` и спрашивает локально авторизованный app-server по stdio. После JSON-RPC `initialize` (id 1, clientInfo `pragmatic-orchestration-quota`), отвечает notification `initialized` и отправляет запрос `account/rateLimits/read` (id 2). Это чтение не расходует turn/reset credit (`references/configuration.md:98–115`). Бинарник можно заменить `PORCH_BIN_CODEX`, timeout по умолчанию 15 секунд.

Нормализованная оболочка (`quota.py:26–60`) — JSON `{ok:true,source:"codex-app-server:account/rateLimits/read",planType,limits,resetCreditsAvailable}`. `limits` — map limitId → `{name,primary,secondary}`; окно — `{usedPercent,remainingPercent,windowDurationMins,resetsAt}`. Значение `usedPercent` берётся из ответа `rateLimits` либо каждого элемента `rateLimitsByLimitId`; `remainingPercent=max(0,100-used)`, epoch reset преобразуется в UTC ISO с `Z`. Часто отображаемое «subscription percent» — primary/secondary соответствующего Codex rate-limit bucket, не стоимость в долларах.

Porch не сохраняет процент как долговечный снимок и не добавляет возраст измерения: это свежий ответ запроса. Ошибка JSON-RPC, отсутствие ответа/запуск дольше timeout, завершение процесса, невалидный/неподдерживаемый app-server протокол дают failure (exit 5/обёртка quota). Читающая сторона должна выводить unknown/error, не 0%; форматтер CLI и общий CLI envelope см. `scripts/lib/quota.py:260–330` и entrypoint `scripts/porch:102–105`. Для замены: запрос к app-server + аналогичная нормализация; если это нельзя сделать, явно unknown без ложного stale/fresh процента.

## 3. Run state, события и mailbox

Основные файлы: `scripts/lib/steer/registry.py:30–47,55–136`, `mailbox.py:30–137`, `events.py:130–230`, `supervisor.py:140–216,294–390`.

- Корень по умолчанию: macOS `~/Library/Caches/pragmatic-orchestration/steer`; Linux `XDG_CACHE_HOME/pragmatic-orchestration/steer` либо `~/.cache/pragmatic-orchestration/steer`; Windows `%LOCALAPPDATA%/pragmatic-orchestration/steer`; `PORCH_STEER_DIR` переопределяет (`registry.py:30–47`). Runs в `runs/<run_id>/`. ID обычно читаемый `run_<word>-<word>-<hex>` (например `run_amber-otter-4f21`); если генератор слов недоступен — `run_` + UUID hex (`util.py:61–82`).
- `meta.json` — атомарный UTF-8 JSON. Минимальные поля: `run_id,agent_id,backend,model,cwd,artifacts_dir,status,pid,owner_uid,started_at,updated_at,version`; позднее добавляются `effort,task_hash_prefix,persist_session,continued_from,backend_binary,child_pid`, timestamps и поля сессии (`registry.py:84–136`, `supervisor.py:151–216`). `state.json` — атомарный JSON snapshot `{run_id,status,active_turn,steers,updated_at}`, обновляется supervisor. В run dir есть `audit.jsonl`; полный нормализованный поток адаптера пишется в `<artifacts_dir>/normalized/<agent_id>.jsonl`, по одному JSON object на строку (`events.py:130–230`, `supervisor.py:425–504`). `events.jsonl` — имя файла прямых Orchestra runners, не porch.
- В run dir предусмотрены `mailbox/`, `control/`, `steers/`, `turns/` и часто `artifacts/` (`registry.py:100–135`). `control/run.lock` сериализует контрольные операции; control/cancel request — файловый маркер. Artifacts содержат `raw/`, `normalized/`, `final/`, `turns/`, `control/`; у Devin сырой ACP JSONL — `raw/devin.jsonl`. Terminal run закрывает mailbox.
- `mailbox/msg-NNNNNN.json` — отдельный JSON с монотонным seq, `client_id`, безопасным hashed filename, `kind` (`steer|cancel`), `content`, sha256 `content_hash`, `mode` (`auto|queue|interrupt`), `status`, timestamps, `delivery_class`, `backend_ack`, `error`, optional `meta` (`mailbox.py:63–137`). `mailbox/seq` — JSON `{next:n}`, `mailbox/lock` — lock file, `mailbox/closed` — JSON `{closed_at,reason}`. Steer дублируется в `steers/cid_<sha256(client_id)>.json`; ID сообщения по умолчанию `steer_` + UUID hex (`util.py:61–95`). Atomic replace, file mode 0600, directory 0700; эти детали важны, чтобы не прочитать частичную запись.
- Старые данные можно читать без исполняемого porch: сделать read-only reader этих директорий/JSON/JSONL и отображать неизвестные будущие event types как generic progress. В актуальном Orchestra прямые runs лежат отдельно в `<repo>/.orchestra/runs/<runId>/state.json`, `events.jsonl`, `mailbox/` (`core/src/runs/cli-runner.ts:25,194–223`); это другой формат/state shape, их нельзя смешать без нормализации. Не удалять porch reader вместе с запуском.

## 4. Жизненный цикл steer

Клиентская запись в mailbox — лишь статус `accepted`, не доказательство передачи модели (`steer/control.py:29–99`). Под lock проверяются active run/закрытый mailbox; запись получает seq и идемпотентный `client_id`, повтор с тем же содержимым/mode/kind отдаёт ту же запись, конфликтующий повтор отвергается (`mailbox.py:63–137`). Supervisor — единственный consumer: читает seq-порядке только accepted сообщения, помечает `delivering`, вызывает backend adapter, потом сохраняет delivery class, backend ack/error и последующий terminal status; terminal transition закрывает mailbox и помечает оставшиеся открытые сообщения failed (`supervisor.py:354–390`, `mailbox.py:194–245`, `registry.py:22`). Подробные reconcile-события в state/audit; есть и `steer_ack` событийная корреляция по client ID (`control.py:394–502`).

Различать как минимум: **written/accepted → delivering → queued/request_sent/acknowledged → completed/applied либо failed/rejected/cancelled/dropped/abandoned**. Конкретные adapter evidence статусы не равны семантическому выполнению; Devin прямо не заявляет `applied`. Очередь, same-turn доставка и cancel-and-send зависят от адаптера. Прямые Claude/Codex Orchestra (`core/src/runs/cli-runner.ts:41–50,96–113,167–189`; `runs/cli-backend.ts:65–88`) сейчас пишут steer Markdown-файл в mailbox и подтверждают запись/отправку runner'у, но не фиксируют durable per-message `accepted/delivering/ack/completed` и не могут подтвердить, что модель прочла или учла указание. Нужны идентификатор и durable lifecycle/event correlation плюс честное различие доставки и эффекта.

## 5. `~/.config/porch/config.json`: реально используемая схема

Путь Orchestra задаётся `PORCH_CONFIG` или `~/.config/porch/config.json` (`packages/core/src/routing/routing.ts:26`). Верхние ключи, читаемые сейчас Orchestra: `routing` и `agents` (`routing.ts:35–79`; `presets.ts:131–132`; `plugin/src/host/actions.ts:192–224`). `routing` — наше расширение поверх porch profile config.

- `routing.classes`: объект со списками ID работников в порядке приоритета для `code`, `design`, `review`, `research`. Пустое/некорректное значение класса оставляет default список. Отбор кандидата исключает disabled и использует первый подходящий (`routing.ts:13–46,78–79`; `orchestration/launch.ts:142–169`).
- `routing.disabled`: map `worker-id → reason string`; наличие ключа отключает id. Пустая причина допустима. Alias сравнения идут через `PORCH_DIRECT` (`routing/identity.ts:1–15`).
- `agents`: map произвольного profile ID → profile object. Orchestra читает ключи как список известных/extra профилей; из объектов берёт `backend`, `model`, `enabled`, `label`, `effort` при описании/launch fallback (`preflight/preflight.ts:18–23`; `plugin/src/host/actions.ts:192–291`; `orchestration/backends.ts:68–82`). Porch schema docs (`references/configuration.md:12–25`) также определяют `role`, `review_instructions`, `supports_delegate`; это porch runtime fields, Orchestra сейчас не маршрутизирует по ним. Профильные поля: `enabled` — участие по умолчанию в review pool; `backend` — исполнитель (codex-cli, claude-code, opencode, grok-build, gemini-cli, devin-cli); `model`; `effort`; `label`; `role` analyst/lateral/specialist; `review_instructions`; `supports_delegate:false` — review-only. Per-invocation env overrides описаны в `configuration.md:33–40`.
- Отдельного top-level `aliases` ключа в используемой porch schema нет. Алиасы `codex`, `codex-gpt-6-*`, `claude-opus`, `claude-fable` определены приложением Orchestra в `routing/identity.ts:1–12`; дополнительные `agents` keys — profile IDs, а не автоматические алиасы. Порядок `agents` сохраняется при показе дополнительных профилей; список прямых workers хранится отдельно в `~/.config/dsh-orchestra/workers.json`.

Читающий мигратор должен сохранить все эти читаемые поля, не путать id-псевдоним с профилем backend, и оставить неизвестные profile fields нетронутыми либо сохранить исходный объект.

## 6. Profile IDs и что можно удалить

Жёстко поддерживаемые Orchestra ID сегодня: direct registry `dsh/deepseek-flash`, `claude/opus`, `claude/fable`, несколько `codex/<model>` (`core/src/routing/registry.ts:8–18`); плагин также показывает `devin` (`plugin/src/client/workers.ts:7–8`). Default routing ссылается на `devin`, dsh и Codex (`routing.ts:15–21`). `PORCH_DIRECT` алиасы codex и Claude отображает как прямые CLI workers, но backend IDs сохраняет (`identity.ts:1–15`). `orchestration/backends.ts:68–82` прямо исполняет dsh/claude/codex; Devin и любой прочий профиль попадают в porch fallback. Следовательно Devin — единственный не-porch профиль, который надо реализовать адаптером для сохранения текущего UX.

Другие ID не являются встроенными Orchestra workers: `grok`, `grok-fast`, `gemini-cli`, `opencode`, `opencode-*`, `claude-code`, `claude-sonnet`, `codex-gpt-5.6` и любые локальные `agents` могут появляться только как динамические extra profiles/config entries. Для настройки UI они перечисляются из `agents`; если пользователь действительно поместил такой id в `routing.classes`/preset, его удаление без миграции было бы потерей настроенного поведения. Однако реестр, default routing и run menu не требуют поддержки этих профилей. Их можно прекратить поддерживать в 0.2.0 без потери встроенной функциональности; мигратор/reader должен оставить их как unsupported/unknown и не запускать через porch скрытым fallback.

| ID/backend | Сейчас есть ссылка в продукте? | Решение 0.2.0 |
| --- | --- | --- |
| dsh, claude, codex | Registry, direct launch, default routing/menu | Поддерживать direct; не писать отдельные porch adapters |
| Devin (`devin-cli`) | Default routing, menu, preflight | Поддержать прямым ACP adapter |
| Grok (`grok-build`), Gemini (`gemini-cli`), OpenCode (`opencode`) и все profile IDs | Preflight/runtime porch adapter, только динамические porch profiles; нет в builtin registry/default routing/menu | Честно остановить: не предлагать как runnable workers, не скрыто запускать; старые записи и routing показывать как unsupported |

## Рекомендованный набор адаптеров

Для 0.2.0 обязательны только **dsh ACP**, **Claude CLI**, **Codex CLI** и **Devin ACP**. Claude/Codex/dsh уже запускаются напрямую. Реализовать Devin по ACP описанию выше; перенести Codex quota reader или показывать quota `unknown`; добавить read-only porch run reader и новый steer lifecycle для своих runs. Честно прекратить поддержку Grok, Gemini, OpenCode и произвольных porch profiles: сохранить их старые данные/ID для отображения и ручной миграции, но не обещать их запуск и не использовать porch fallback.
