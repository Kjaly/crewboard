## 1. README practice and comparable first screens

GitHub says a README should quickly explain **what the project does, why it is useful, how to get started, where to get help, and who maintains it**; keep lengthy reference material in deeper documentation. GitHub renders relative links correctly across branches and supplies a heading table of contents. [GitHub README guidance](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes). [Make a README](https://www.makeareadme.com/) recommends the smallest useful usage example inline, with links to longer examples. The [Google documentation guide](https://github.com/google/styleguide/blob/gh-pages/docguide/READMEs.md) argues for current, local README files in code packages. For a 2025–2026 developer-tool launch, this suggests a first screen with a plain promise, explicit audience, actual product visual, and a short install route; this is an editorial recommendation based on those guides and the examples below, not a platform rule.

## 3. Positioning copy

The copy below follows the owner’s stated problem. “Models” means the supported coding workers/providers, not an unverified promise of arbitrary model routing. Existing README and [architecture](../architecture.md) support the plan, worker, and human-decision parts.

### English

**Taglines — choose one:**

1. **See your coding agents at work, across projects.**
2. **One board for plans, runs, costs, and decisions.**
3. **Keep several coding workers in view.**

**Problem statement:** I work on several projects at once and often use orchestrators, but too much of the work happens out of sight. It is hard to see what each worker is doing and where I need to step in, or to combine coding workers from different providers in one workflow. Crewboard gives me one place to follow plans, runs, costs, and decisions while workers do the work and I accept the result.

**For:** Developers juggling several repositories and several AI coding workers—such as Codex, Claude Code, DeepSeek through dsh, and Devin—who want to supervise their work and make the final acceptance decision. **Not for:** Someone making a single small change with one agent, or anyone wanting an agent to accept its own work automatically.

### Русский

**Варианты слогана — выбрать один:**

1. **Видеть работу кодовых агентов во всех проектах.**
2. **Планы, запуски, затраты и решения — в одном месте.**
3. **Держать работу нескольких кодовых агентов перед глазами.**

**Проблема:** Я постоянно работаю над несколькими проектами и часто пользуюсь разными оркестраторами, но многое происходит где-то под капотом: мне не хватает наглядного контроля и понимания происходящего. Кроме того, трудно объединить в одном рабочем процессе кодовых агентов от разных провайдеров. Crewboard помогает видеть планы, запуски, затраты и то, что ждёт моего решения, пока агенты работают, а результат принимаю я сам.

**Для кого:** Для разработчиков, которые ведут несколько репозиториев и используют нескольких кодовых агентов — например, Codex, Claude Code, DeepSeek через dsh и Devin — и хотят видеть их работу и сами принимать результат. **Не для кого:** Для тех, кому нужен один агент для небольшой правки, или автоматическая приёмка результата агентом без решения человека.

## 7. npm release checklist for this pnpm workspace

The following is a **checklist**, not a completed publish procedure. The public names `crewboard` and `dsh-crewboard` and dsh registry installation must be checked on npm and in a real dsh host before README commands are asserted as tested.

1. **Names and dependency graph.** Root stays `private: true`. Rename CLI package to `crewboard` and plugin to `dsh-crewboard`; set `private: false` or remove it only on packages actually published. npm refuses a package marked private. The CLI currently has a runtime `@dsh-orchestra/core: workspace:*` dependency while core is private: publish core under an agreed public name/version **or** bundle it into the CLI and remove the runtime dependency. Do not publish a broken `workspace:*` consumer; pnpm rewrites workspace references when **pnpm** packs/publishes, but that cannot make an unpublished dependency installable. [npm package fields](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/), [pnpm workspace publishing](https://pnpm.io/workspaces).
2. **Manifest fields.** Set each published package’s `repository` to `{ "type": "git", "url": "git+https://github.com/Kjaly/crewboard.git", "directory": "packages/cli" }` (or `packages/plugin`; core if published), `homepage` to `https://github.com/Kjaly/crewboard#readme`, `bugs.url` to `https://github.com/Kjaly/crewboard/issues`, and accurate description/keywords/license. npm documents `repository.directory`; npm trusted publishing requires the repository URL to match the GitHub repository, so validate the chosen URL form in CI. [npm package fields](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/), [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/).
3. **Tarball surface.** CLI needs `files: ["dist", "README.md", "LICENSE"]`, an explicit public `bin: { "crewboard": "./dist/main.js", "orch": "./dist/main.js" }`, and a built executable with the Node shebang (source already has it; verify emitted file). Plugin `files` must include every built `lib` chunk, `cordis.patch.yml`, README and license; retain dsh metadata and verify the installed host/client loads. Keep `exports`/`main` pointed only at included, existing files; CLI needs no library `exports` unless consumers are meant to import it. Keep `engines.node >=24` if actually required and test on Node 24. npm documents `files`, automatically included README/LICENSE and bin targets, `exports`, and `engines`. [npm package fields](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/).
4. **Versioning.** Pick first public versions for all published packages and coordinate dependency bumps. Changesets is a reasonable monorepo option: `changeset version` updates versions/dependencies/changelogs and `changeset publish` publishes unpublished versions; configure ignored private packages deliberately. A simpler manual single-version release is viable for two public packages, provided the CI release gate checks manifest/dependency versions. Do not present the reconstructed changelog milestones as already published versions. [Changesets commands](https://github.com/changesets/changesets/blob/main/docs/command-line-options.md), [current changelog](../../CHANGELOG.md).
5. **Readme per package.** Add `packages/cli/README.md` with CLI install, prerequisites, minimal working invocation, and docs link; `packages/plugin/README.md` with the dsh `--profile` install command, compatible host version (once known), setup, and screenshot. If core is published, add a core README explaining whether it is supported as a public API. npm includes each package-local README in its package tarball and displays it on npm. [npm package fields](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/).
6. **Pack and smoke test before publishing.** From a clean build, run `pnpm --filter crewboard pack --pack-destination /tmp/...` and the equivalent for plugin (plus core if published); also use `npm pack --dry-run --json` in each package for the file list. Inspect manifests inside the **actual pnpm tarballs** for rewritten workspace versions, all `bin` and `exports` files, plugin bundle/patch, README/license, and no source secrets/dev assets. Install tarballs into a clean temporary project, run `crewboard --help` and `orch --help`, then install plugin into a disposable dsh profile and open the screen. `npm pack --dry-run` reports without writing a tarball; pnpm documents its workspace rewrite at pack time. [npm pack](https://docs.npmjs.com/cli/v11/commands/npm-pack/), [pnpm workspace publishing](https://pnpm.io/workspaces).
7. **Publish and provenance.** Add a release CI job with quality gates, GitHub-hosted runner, `permissions: { contents: read, id-token: write }`, Node 24 plus npm >=11.5.1, and one npm trusted-publisher configuration per public package matched to `Kjaly/crewboard` and the workflow filename. Publish public packages in dependency order. If using `npm publish --provenance`, first verify npm packs the same rewritten dependency graph as the pnpm tarball; otherwise use the appropriate pnpm publish path with OIDC and check provenance afterward. npm says trusted publishing on GitHub Actions **automatically** emits provenance for a public package from a public repo, so `--provenance` is optional in that route; private repositories do not get provenance. Configure `publishConfig.access: "public"` where needed and verify the resulting npm page and attestation. [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/), [npm publish](https://docs.npmjs.com/cli/v11/commands/npm-publish), [scoped public packages](https://docs.npmjs.com/creating-and-publishing-scoped-public-packages/).
