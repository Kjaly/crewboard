# Настройки Orchestra: право выбора там, где меняется смысл работы

23 сентября 2026. Это проект решения, не спецификация готовой функции. Отправная точка: работник может завершить запуск, но `syncRuns` переводит удачный запуск в `in_review`, а зависимость открывается только после `accepted` ([`graph.ts:45–76`](../../packages/core/src/plan/graph.ts#L45), [`graph.ts:103–119`](../../packages/core/src/plan/graph.ts#L103)). Приёмка остаётся действием владельца: API требует его подтверждения, агентский инструмент отвергает `accepted`/`rejected` ([`actions.ts:455–490`](../../packages/plugin/src/host/actions.ts#L455), [`tools.ts:135–153`](../../packages/plugin/src/host/tools.ts#L135), [`review.ts:5–13`](../../packages/core/src/orchestration/review.ts#L5)). Настройка «принимать автоматически» противоречила бы этой модели.

## Три области и одно правило

**Правило:** хранить решение в самом узком контексте, где оно сохраняет один смысл на всём сроке действия; проверять его в месте исполнения. Машина отвечает за наличие и запреты ресурсов (реестр, доступ, сохранение локальных копий). Репозиторий отвечает за повторяемую подготовку и общие допустимые способы работы. План отвечает за конкретную цель, выбранных работников, порядок классов и предел запуска без участия владельца. Задача внутри плана может явно закрепить работника и контракт; это уже предусмотрено схемой ([`schema.ts:28–51`](../../packages/core/src/plan/schema.ts#L28)).

Сегодня реестр лежит в домашнем каталоге ([`registry.ts:20–29`](../../packages/core/src/routing/registry.ts#L20)), политика копий — тоже ([`gc.ts:41–68`](../../packages/core/src/worktree/gc.ts#L41)), а порядок классов записан в общий конфиг porch ([`routing.ts:26–26`](../../packages/core/src/routing/routing.ts#L26), [`routing.ts:58–72`](../../packages/core/src/routing/routing.ts#L58)). UI одновременно показывает всё это на одном экране ([`settings.tsx:534–633`](../../packages/plugin/src/client/settings.tsx#L534)). Рецепт подготовки уже живёт в репозитории, `.orchestration/recipes.json`, с `setup`, `env`, `baseline`, `timeoutSec` ([`recipe.ts:6–23`](../../packages/core/src/worktree/recipe.ts#L6)). План сохраняется отдельно, а не в домашнем конфиге ([`store.ts:7–26`](../../packages/core/src/plan/store.ts#L7)).

При расхождении областей действует пересечение, а не свободное переопределение: локально отключённый или недоступный работник не запускается даже при явном выборе в плане; репозиторий может сузить допустимые профили, план выбирает и упорядочивает оставшихся, задача закрепляет один из них. Явный выбор, который не проходит ограничения или preflight, даёт ошибку и видимую причину; молчаливой замены нет. Это продолжает поведение [`launch.ts:126–150`](../../packages/core/src/orchestration/launch.ts#L126). Ограничение автономности плана также может только сужаться репозиторием. Политика уборки копий остаётся локальной и не задаётся планом.

## Предложения (шесть, в порядке внедрения)

### 1. Развести экран настроек и параметры плана

**UI:** в «Настройках» оставить «Эта машина»: реестр, доступ и уборку. В репозитории — раздел «Правила репозитория» рядом с рецептом подготовки. В заголовке открытого плана — «Параметры этого плана» с кратким резюме эффективных ограничений. **Core:** отдельная проверяемая конфигурация репозитория в `.orchestration` (разрешённые профили и верхняя граница автономности), новые поля в `PlanSchema` для плана; один resolver возвращает эффективные значения и источник каждого. Миграция не меняет старые планы: отсутствующие поля означают нынешнее поведение. Домашний porch routing пока остаётся запасным источником. **Проверка:** тест загрузки старого плана, precedence и отказа при локальном запрете. **Против:** ещё один конфигурационный файл и проблема расхождения с CLI; поэтому resolver обязателен для UI, CLI и host.

### 2. Выбор работников и порядка внутри плана

**UI:** в параметрах плана — допустимые работники и четыре упорядоченных списка классов; в карточке задачи — явное назначение. Рядом показывать источник умолчания и недоступность. **Core:** `launchTask` берёт порядок плана, затем репозитория, затем нынешний `DEFAULT_ROUTING`; фильтрует машинные запреты и разрешённые профили, запускает первый прошедший preflight. Явно назначенный недоступный работник остаётся ошибкой, а не заменяется. Нынешняя задача уже может хранить `worker`, но автоматический выбор сейчас читает домашний porch config ([`launch.ts:71–78`](../../packages/core/src/orchestration/launch.ts#L71), [`schema.ts:35–37`](../../packages/core/src/plan/schema.ts#L35)). **Проверка:** приоритеты, отсутствие работника, падение preflight, закреплённый работник. **Против:** копия порядка устаревает при смене доступных моделей; показывать недействительные строки, не подменять их скрыто.

### 3. Запуск готовых задач в пределах плана

**UI:** параметр плана «Запускать готовые задачи»: вручную / автоматически после человеческой приёмки зависимости; рядом максимум одновременных запусков и список задач, которые будут запущены. Для независимых задач тот же режим может стартовать их, когда план открыт и одобрен владельцем. **Core:** реакция на сохранённое `accepted` и `readySet` запускает только `ready` задачи с контрактом, через обычный `launchTask`, с preflight и baseline; записывает причину запуска в историю. Повторные снимки идемпотентны; failed, rejected, decision, in_review и отсутствующий контракт никогда не запускаются сами. **Проверка:** цепочка после accept, независимые задачи, гонка двух снимков, лимит параллельности, отказ baseline. **Против:** расходы и неожиданные параллельные изменения; начальный режим — вручную, лимит виден до включения. Это сокращает ожидание *после* суждения владельца, не заменяет его.

### 4. Закрытие задачи без результата, без приёмки

**UI:** в параметрах плана — разрешение «Закрывать исследования без результата»; в очереди — отдельная группа «Закрыто без результата» с причиной и кнопкой вернуть в работу. Только `research` без изменённых файлов, с явно отрицательным/заблокированным отчётом и без заявленного результата. **Core:** новый терминальный статус вроде `closed_no_result` и note с проверенными фактами. Это **не** `accepted`: зависимости остаются заблокированы и показывают причину; положительный вывод исследования даже без файлов идёт на человеческую приёмку. Проверка отсутствия изменений должна учитывать worktree и diff, а не одну строку отчёта; текущий verdict по умолчанию считает результатом даже отчёт без явного claim ([`verdict.ts:9–16`](../../packages/core/src/orchestration/verdict.ts#L9), [`verdict.ts:24–57`](../../packages/core/src/orchestration/verdict.ts#L24)). **Проверка:** отрицательное исследование без diff закрывается; положительное, неясное или с diff — нет; зависимости не открываются; заметка сохраняется. **Против:** можно ошибочно закрыть ценное исследование с выводом в отчёте; поэтому нужен явный отрицательный claim, сохранённый отчёт и обратимое возвращение в работу. Если надёжно доказать отсутствие изменений нельзя, функция не срабатывает.

### 5. Приёмка с графа за одну клавишу

**UI:** фокус на ожидающей карточке графа показывает краткий verdict, diff summary, проверки, отклонения и зависимые задачи; одна клавиша принимает обычный `result` после просмотра, «Вернуть» требует причину. Сохранить видимую кнопку для мыши. Для `disputed`, `negative` и `decision` оставить отдельное подтверждение. Сейчас граф отмечает очередь кольцом, а список уже загружает отчёт и изменённые файлы ([`graph-view.tsx:311–313`](../../packages/plugin/src/client/views/graph/graph-view.tsx#L311), [`queue.tsx:40–98`](../../packages/plugin/src/client/queue.tsx#L40)); одиночная приёмка показывает native confirm по типу verdict ([`actions.ts:455–469`](../../packages/plugin/src/host/actions.ts#L455)). **Core:** новый статус не нужен; отдельный маршрут для явного клавиатурного действия человека проверяет свежий `in_review` и обычный verdict, затем пишет ту же человеческую note. При смене состояния возвращает карточку на просмотр; агентские инструменты маршрута не получают. **Проверка:** клавиатурная навигация, stale карточка, disputed/negative/decision, фокус после действия. **Против:** лаконичный обзор может скрыть риск; ссылка на полный diff обязательна, спорный verdict нельзя визуально приравнять к обычному.

### 6. Пачка только с согласованными вердиктами

**UI:** очередь предлагает группу одинакового типа verdict (`result`, `negative`, `disputed`) с краткими фактами каждой задачи; по умолчанию выбирать лишь обычные согласованные `result`, остальные — вручную. Решения человека (`decision`) отдельно. Пользователь отмечает конкретные задачи и подтверждает одну пачку. Нынешний поповер выбирает все reviewable задачи, а сервер проверяет только статус ([`accept-batch.tsx:11–17`](../../packages/plugin/src/client/views/accept-batch.tsx#L11), [`accept-batch.tsx:159–192`](../../packages/plugin/src/client/views/accept-batch.tsx#L159), [`actions.ts:474–490`](../../packages/plugin/src/host/actions.ts#L474)). **Core:** сервер пересчитывает verdict каждого ID непосредственно перед подтверждением; смешанную или изменившуюся пачку отклоняет и возвращает состав на повторный просмотр. `acceptTasks` остаётся атомарной человеческой операцией ([`review.ts:38–53`](../../packages/core/src/orchestration/review.ts#L38)). **Проверка:** однородная пачка, разные verdict, смена diff/статуса между показом и отправкой, ошибка одного ID без частичной приёмки. **Против:** одинаковый verdict не доказывает одинаковый риск; поэтому факты и ссылки на diff видны по каждой задаче, а включение в пачку остаётся явным выбором человека.

## Чего не добавлять

- `autoAccept`, «принять, если тесты зелёные», «принять по доверию к модели», «принять исследование без diff». Нулевой diff не доказывает верный вывод; зелёные тесты не доказывают соответствие контракту. Особенно недопустимо одинаково оценивать исследование и рефакторинг ядра. Для рефакторинга даже пачку следует предлагать осторожно; verdict — подсказка, не разрешение.
- Настраиваемые `KEEP_RECENT`, миллисекунды burst/чат окна, пороги свёртки, таймауты cache и «число попыток до успеха». Это внутренние механизмы, их ошибки исправляются в продукте, а не перекладываются на владельца.
- Глобальную «автономность» на все будущие планы, режим, который позволяет плану снять машинный запрет, и скрытые исключения для отдельных поставщиков. Полномочие запуска относится к конкретной цели, а доступность — к машине.
- Флаг, который отменяет review при failed run, спорном verdict, отсутствующем отчёте или человеческом `decision`. Завершение запуска и согласие с результатом остаются разными событиями.

**С чего начать:** сначала разделение областей и единый resolver; затем приёмка с графа и безопасная группировка очереди. По измеренному времени ожидания внедрять автоматический запуск после приёмки. Закрытие без результата выпускать лишь после тестов на ложноположительные случаи и с отдельным терминальным статусом.
