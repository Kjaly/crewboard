# Продуктовый аудит dsh-orchestra по следам собственной работы

Дата: 2026-09-23. Код: `6f097ab` в этом worktree. Исходники не изменялись.

Главный недостаток инструмента — он регистрирует действия и завершения, но недостаточно надёжно сообщает, **состоялась ли передача работы следующему участнику**. Поправка записана, но исполнитель уже ушёл. Работа принята, но отрицательный результат потерялся. Клиентская задача закончена, но необходимого поля хост так и не отдаёт. Владелец становится транспортом между этими состояниями: читает журналы, замечает расхождения на экране, дописывает задания и склеивает изменения.

Это не аргумент против человеческой приёмки. Наоборот: инструмент должен отдавать человеку достоверные материалы для решения, освобождая его от восстановления того, что машина уже могла знать.

Проверено исполнением чистых функций текущего исходника на реальных ответах `t3d`, `t4`, `t3b`, `t1`:

Строка «Результат: …» перед заголовком исчезает. `claimOf` ищет её только в первой строке уже извлечённого текста (`packages/core/src/orchestration/verdict.ts:9`). У корректно оформленного отрицательного `t4` claim теряется. У `t3b` ещё и собственное нарушение формата: отсутствует префикс «Результат:».
2. `requiredChecks` снимает маркер списка, но сохраняет стрелку и объяснения; затем нужен буквальный `report.includes(check)` хотя бы одной полной строки (`verdict.ts:19`, `:51`). В `t3d` команда `pnpm --filter @dsh-orchestra/core build && pnpm --filter dsh-orchestra test` и 267 успешных тестов указаны явно (`events.jsonl:334`), но в контракте к ней приписано `→ green` (`O/contracts/t3d-notify.md:29`). Получается disputed. Это конкретный ложный сигнал о неупоминании, а не доказательство правильности всех изменений t3d.
3. Факт «проверки не запускались» выводится из отсутствия слов `pnpm/npm/.../test` в тексте (`verdict.ts:45`), не из событий выполнения. `t1` действительно требовал только `git status --short` (`O/contracts/t1-i18n-research.md:18`), сообщил его, но получает предупреждение. Это две одновременно плохие стороны: человек вынужден разбирать ложную тревогу, а существенный отрицательный результат получает ту же мелкую формальную причину. Расчёт выше не подставлял нынешний Git diff вместо исторического: для проверки парсера changedFiles задавался искусственно и не использовался как доказательство состава работы.

## 2. Повторяющиеся признания работников

Журнал отклонений — не список проступков. В нём есть хорошие возражения против невозможного плана, честные границы доступа и осмысленные компромиссы. Ошибка продукта начинается там, где одна и та же оговорка снова требует ручного решения владельца.

### 2.1. Противоречивые проверки заставляют оптимизировать не тот результат

`j2` (Devin) фиксирует 300 КБ в плане против 360 КБ в проверке задачи и уже превышенный исходный размер (журнал задачи j2). `k1` и `k2` (DeepSeek) независимо описывают то же противоречие и невозможность исправить чужой клиент в разрешённом scope (журналы задач k1 и k2). Оно повторяется у `l1` и `u3` (журналы задач l1 и u3). На следующий день `o3` (Codex Sol) буквально минифицирует исходник ради порога; владелец отменяет это. `r10` оставляет запас **9 байт**, при упрощении теряет используемые стили и факт про незапущенные проверки; оркестратор возвращает их и поднимает порог до 340 KiB (журналы задач o3 и r10).

Здесь повтор есть у трёх разных исполнителей/бэкендов — Devin, DeepSeek, Codex Sol — и в журналах двух дат. Проблема не в недостаточной дисциплине «ещё раз прочитать план»: машина не различает текущий проверяемый контракт, унаследованное пожелание и уже опровергнутое ограничение. Похожее буквальное противоречие: g1 разделяет поведение исходника и сборки, чтобы не менять тесты, хотя план требует новый порядок поиска porch (журнал задачи g1); o2 приходится выбирать между «сохранить последние три» и «сразу удалить только что принятую» (журнал задачи o2).

### 2.2. Деление по каталогам оставляет владельцу недоделанные пользовательские действия

Работник заканчивает разрешённый слой, а обещанная функция требует другого:

- `g2` дублирует CLASS_LABEL и kind→class, потому что клиенту нельзя runtime-import core; `g4` добавляет ещё карту алиасов рядом с существующей (журналы задач g2 и g4).
- `j2` ради одной строки отчёта сразу грузит полную task detail с Git diff для каждой строки очереди; batch-экран оставлен другому работнику (журнал задачи j2). `k3` повторяет eager GET для строк приёмки (журнал задачи k3). Это доказанная дополнительная работа API, но замера задержки пользователя нет.
- `l3` не может проверить вход Codex или удалить алиасы на хосте; план 2o снова поручает это клиенту, и `o3` снова оставляет вход неподтверждённым. Алиасы удаляются вторым запросом, который может упасть после удаления записи (журналы задач l3 и o3; план 2o).
- `r7`, `u4`, `o3` опять копируют риск-слова, имена моделей, причины сохранения копий: нужные значения не проходят через пригодную браузеру границу (журналы задач r7, u4 и o3). В переводе `t3d` это превращается в получение протокольных значений из русского словаря (журнал задачи t3d).

Это не повод запретить параллельную работу. Нужно контрактовать **стык**: какое поле/действие приходит от другого слоя и кто завершает целый сценарий. Иначе «не трогал по scope» каждый раз переезжает к владельцу. Его план 2s это прямо признаёт: «часть правил я склеивал вручную при мерже» (план 2s).

### 2.3. Зелёные тесты закрывают совсем другой вопрос, чем тот, который задал владелец

У `l3`, `m1`, `m1c`, `m4`, `n1` зафиксированы реальные отказы среды: Chromium/порт/file URL, снимков нет (журналы задач l3, m1, m1c, m4 и n1). Это пять задач, преимущественно одного Codex Sol; **не пять разных моделей**. Добавляются прямо отложенные живые проверки f2, q6, o3, t3b2. Честность этих журналов полезна, но запуск всё равно приходит человеку как completed.

Контрпример, который показывает цену пробела: `h1` на настоящем стенде обнаружил, что pointer capture съедает клики по всем чипам графа; синтетический dispatchEvent проходил и раньше (журнал задачи h1). `q6` оставил шесть вкладок и оценил вид по коду; поздняя поправка r9 снова требует убрать их перенос (журнал задачи q6; steer r9). Владелец тратит приёмку на первичное обнаружение того, что исполнитель не мог увидеть.

Ещё повторяется неисправный порядок проверок: `m1` и `n1` сначала не находят core/dist, затем проходят после сборки; `o2` прямо говорит, что предписанный порядок test→build не подходит (журналы задач m1, n1 и o2). В финальном ответе t2 тоже записана гонка параллельных test/build (`O/runs/run_codex-mud9qrqdzg2b/events.jsonl:89`). Это воспроизводимый дефект подготовки задания, а не необходимость ещё одного общего набора тестов.

### 2.4. «Маленькая оговорка» меняет обещание кнопки

В g4 выключенная direct-модель может продолжать назначаться через alias (журнал задачи g4). В k3 «Новая задача» открывает тот же экран, что «Открыть граф», потому что создания не предусмотрено (журнал задачи k3). В m4 одно пользовательское «навести порядок» — несколько последовательных POST и возможная половина операции (журнал задачи m4). В l2 удаление воркера — две файловые записи; o3 добавляет к этому два клиентских запроса. Это независимые задачи разных работников; локальное «реализовал кнопку» ещё не обеспечивает обещанную единицу действия.

### Где я не согласен с решениями владельца

1. **«Зелёный вердикт принимается почти не глядя» — плохой критерий** (`2r-verdict.md:76`). Сейчас отсутствие распознанного заявления превращается в result по умолчанию (`verdict.ts:57`), а корректное отрицательное заявление может исчезнуть при извлечении раздела. Зелёный должен означать только известное согласование конкретных фактов, а не разрешение не смотреть. Сама приёмка остаётся человеческой.
2. **4 ч 13 м ожидания не равны 4 ч 13 м потерянного внимания.** Задачи ждут параллельно, владелец мог заниматься другой работой. Мой дополнительный расчёт для 62 принятых продуктовых задач с completed и последующей приёмкой даёт около **7 ч 33 м суммарного ожидания**: последняя completed-попытка → первая последующая accept. Это тоже сумма task-time, не рабочий день человека. Batch-приёмка сокращает клики, но не доказывает сокращение проверки; сейчас она ещё и не сохраняет индивидуальные вердикты. Не развивал бы «Принять все» раньше достоверного материала приёмки.
3. **«Принято, но никуда не ведёт» не обязательно проблема.** Функция `deadEnds` показывает любой accepted не-decision без потомков (`packages/plugin/src/client/dead-ends.ts:5`). На снимке это **21 строка**, из них 20 продуктовых, включая законченные `n1`, `u4`, `m4` и неудачный `t3b`. Графовая степень не отличает забытый результат от нормального конца работы. Нужна явная отметка «результат использован / отдельный итог», а не обязательное придумывание новой задачи каждому листу.
4. **Страж кириллицы не доказывает полноту перевода.** t3b2 кодирует слова риска Unicode escapes (журнал задачи t3b2), t3d берёт протокольные значения из словаря, t3e честно оставляет приходящую из core диагностику (журнал задачи t3e). Не надо отменять перевод; надо перестать считать исчезновение букв доказательством правильного интерфейса. Граница «код состояния / подпись / данные» важнее запрета алфавита.

## 5. Что строить — в порядке возврата внимания

Оценки ниже — порядок величины для одного исполнителя с интеграцией и проверкой владельцем, не обещанный календарь. Ранжирование качественное: журнал позволяет считать случаи, но не позволяет честно обещать «сэкономим N часов».

### 1. Подтверждаемая доставка поправки и понятное продолжение

**Что:** различать «записано», «получено runner», «применён новый ход», «адресат завершён». Для последнего — конкретное действие «продолжить с этой поправкой» с прежним контекстом; не запускать платную работу молча. Идентификатор поправки связать с runId и ответным событием. Синхронизировать все незакрытые записи runs, не только последнюю; при попытке второго запуска показывать уже активный.

**Основание:** 3 из 5 поправок лежат у завершённых адресатов; k6 запущен дважды и оставил незакрытую запись. Уже есть relaunch с контекстом — не требуется изобретать новый механизм (план 2e).

**Цена:** средняя, примерно 2–4 рабочих дня: контракт событий backend-ов, CLI/host/UI, гонка завершения с отправкой и идемпотентность. **Что может сломать:** различающуюся семантику steer у Claude, Codex, dsh и porch; нельзя повторить одну поправку дважды. **Против:** два реальных вмешательства в полёте — небольшой объём; подтверждение применения не доказывает, что работник понял смысл. Однако отсутствие получателя известно механически, и сейчас именно оно скрыто.

### 2. Пакет доказательств результата, независимый от короткого пересказа

**Что:** при завершении сохранять полный final, исходное заявление, ссылки на артефакты, выполненные/невыполненные проверки и идентификатор версии контракта. Показывать «не сообщено» отдельно от «не выполнялось» и «не смогли прочитать». Сначала исправить потерю первой строки и literal matching; потом получать результаты проверок как структурированные записи с источником. Короткий отчёт — только представление. При человеческой приёмке сохранять показанный пакет и вердикт для каждой задачи, включая batch; после удаления копии он остаётся доступен.

**Основание:** 10 продуктовых disputed с одной формальной причиной; два явных отрицательных ответа; конкретные ошибки t3d/t4/t1/t3b; diff и report сейчас зависят от живых внешних ресурсов. Это возвращает владельцу время чтения и доверие к сигналу.

**Цена:** первая правка небольшая (около дня), полный путь средний/крупный (3–6 дней), включая совместимость старых запусков и лимиты хранения. **Что может сломать:** старые свободные формы отчёта, consumers TaskDetail, batch-подтверждение и очистку. Старым данным нельзя задним числом приписывать успешно выполненные проверки. **Против:** структурированный self-report всё равно может быть неверен; хранение полного diff стоит места. Поэтому оставлять источник и человеческую проверку, хранить ограниченные артефакты/ссылки, не выдавать новый формат за автоматическую оценку качества.

### 3. Исполнимый контракт со стыками и явным остатком работы

**Что:** при подготовке запуска разрешать пути плана/контракта из общего repo, фиксировать их версии; проверять доступность обязательного файла и инструмента проверки. Команды отделить от ожидаемых результатов и пояснений. Для совместной задачи объявлять поставщика нужного поля/API и задачу, которая замыкает весь сценарий. Отклонение «вне scope» превращать в связанный остаток с ответственным, а не автоматически закрывать и не автоматически создавать новую работу без решения владельца. Retry связывать с исходной задачей, даже если нужен новый id/worktree.

**Основание:** ритуал 300/360 КБ у трёх бэкендов; отсутствие реального контракта при разработке verdict (журнал задачи r1); t1 не нашёл план в worktree (`events.jsonl:36`); повторный незакрытый auth-пункт l3→o3; два повторных контракта m1/m1b и t3b/t3b2.

**Цена:** средняя/крупная, 3–5 дней для узкой версии на существующих контрактах; полноценный редактор не нужен первым шагом. **Что может сломать:** свободные Markdown-задания, запуск из старых worktree и привычные исключения владельца. Совместимость — предупреждение с конкретным конфликтом, не запрет любого отклонения. **Против:** формализация может съесть больше внимания, чем сэкономит на одиночной задаче. Поэтому начать с повторённых дорогих конфликтов: отсутствующий файл, команда/ожидание, межслойная зависимость, retry-связь.

### 4. Доступный работнику визуальный стенд как часть сдачи

**Что:** один поддерживаемый путь запуска текущего плагина в разрешённом тестовом профиле dsh, фикстура плана и артефакты проверки. При недоступном браузере явно передавать состояние «визуальная проверка не выполнена» и готовый сценарий для владельца. Проверять настоящие клики и переключения, а не только DOM. Это не отменяет окончательный просмотр человеком.

**Основание:** пять явных отказов среды; f2/q6/o3/t3b2 оставляют просмотр человеку; h1 только живым кликом нашёл неработающий тулбар; q3s проиграл из-за невидимой главной кнопки.

**Цена:** средняя, 2–4 дня; сопровождение профиля/фикстур при обновлении dsh. **Что может сломать:** несовпадение стенда с реальным dsh, конкурирующие сборки общего lib, права sandbox. Не обходить ограничения среды: стенд должен быть штатно доступным. **Против:** скриншот не подтверждает смысл работы и может устареть после merge; один профиль владельца не представляет всех пользователей. Но он снимает повторное строительство заведомо неработающих `/tmp`-стендов и делает пробел видимым до приёмки.

### 5. Одна семантика воркера на всём пути настройки → запуск → история

**Что:** отдельно хранить идентичность модели, путь запуска и профиль. Сервер отдаёт display name и причины доступности; отключение/удаление явно называет, что произойдёт с алиасами, и выполняет согласованное изменение routing/registry. «CLI найден», «вход подтверждён», «эта модель проверена» — разные факты с датой. Проверка модели остаётся по явной кнопке.

**Основание:** ручная цепочка g2→g4→g5→l3→o3, поздняя поправка u4 для экономики, одинаковая модель считается дважды, удалённый direct продолжает назначаться через alias. Реестр уже существует — предлагается завершить его смысл, а не добавить второй.

**Цена:** средняя, 2–4 дня с миграцией aliases и consumer-ов. **Что может сломать:** намеренное использование двух транспортов одной модели, старые id в историях и индивидуальное отключение профиля. Сохранять оригинальный id запуска и давать различить транспорт. **Против:** владелец может действительно хотеть два отдельных пути, а проверка доступа быстро устаревает. Поэтому не склеивать маршруты автоматически только по красивому имени.

### 6. Восстановление надзора после разрыва и завершение уборки

**Что:** показывать время последнего успешного снимка и доставки в чат; после старта сверять невыполненные обязательства с сохранённым журналом доставок. Очередь «нужен человек» должна считать решения одинаково в текущем и фоновом плане. Для копий — видеть «принято, ждёт merge», «можно убрать», «уборка не удалась» и повторять проверку после merge/по команде. Согласовать правило последних трёх копий с автоуборкой.

**Основание:** baseline i1 скрывает события простоя; h1 не считает фоновые решения; 81 копия / 43 ГБ и ручная уборка в плане 2o; приёмка вызывает GC только для своих задач, а в ответе теряются подробности отказа. Не предлагается удалять больше: предлагается объяснить и завершить разрешённую уборку.

**Цена:** средняя, 2–4 дня на две ограниченные цепочки восстановления; нужны сохранённые курсоры и backoff, чтобы восстановление не породило шторм. **Что может сломать:** дедупликацию уведомлений, порядок merge/accept и ожидание хранения свежих копий. **Против:** частота пропущенных wake по записи неизвестна; автоматический повтор может шуметь. Начать с видимого состояния и одной сводки недоставленного, не с настойчивых тостов.

Седьмое предложение не добавляю. Новые графовые режимы, новые настройки и развитие автоматического отпочкования сейчас хуже обоснованы, чем исправление этих шести цепочек. Сначала — доставленная поправка и достоверное основание для принятия; это устраняет уже наблюдённую ручную работу, а не предполагает нового пользователя.

## 7. Воспроизводимость и границы вывода

Основные счётчики воспроизводятся без запуска воркеров или изменения плана:

```python
import json
from collections import Counter
from pathlib import Path

p = json.loads(Path('/Users/kjaly/WebstormProjects/dsh-orchestra/.orchestration/plan.json').read_text())
tasks = p['tasks']  # Для тех же чисел нужен rev 410; живой файл может быть новее.
print(p['rev'], p['updatedAt'], len(tasks))
print(Counter(t['status'] for t in tasks))
print(Counter(r.get('outcome', 'open') for t in tasks for r in t['runs']))
print(Counter(n['type'] for t in tasks for n in t['notes']))
print([(t['id'], len(t['runs'])) for t in tasks if len(t['runs']) > 1])
for t in tasks:
    for n in t['notes']:
        if n['type'] == 'steer':
            live = [r['runId'] for r in t['runs']
                    if r.get('finishedAt')
                    and r['startedAt'] <= n['at'] <= r['finishedAt']]
            print(t['id'], n['at'], live)
```

Существенные ограничения: нет полного журнала действий владельца вне orch; нет причин большинства отмен; нет локальной сырой трассы всех backend-ов; typed verdict появился позже первых приёмок. Состояния нового t6 и параллельного v2 учтены в зафиксированном JSON, но их изменения исходников не подменяют проверяемый здесь commit. Не запускались приложение, модели, сборка или общий test suite: для одной заметки они не проверяют выводы. Проверены арифметика, реальные временные интервалы, содержимое mailbox и чистые функции извлечения/вердикта. Выводы о недоставленных поправках и ошибках парсера воспроизводимы; оценки сроков и приоритетов — суждение автора аудита.
