# Учёт контекста, prompt cache и стоимости оркестратора — 2026-09-28

## Вывод и граница измерения

Главная слепая зона — **сам bound dsh chat оркестратора**. Crewboard связывает plan с `sessionId`, добавляет system-prompt section, briefing, task briefs и wake prompts, а ответы `orchestra_*` идут через host tools. Его `sessionController` предоставляет `create/prompt/inspect`, без usage/cost или истории вызовов: [host/dsh.ts:22-29](../../../packages/plugin/src/host/dsh.ts), [host/index.ts:95-98](../../../packages/plugin/src/host/index.ts), [host/chat.ts:8-9,135-165,189-209,363-391](../../../packages/plugin/src/host/chat.ts). `chats.json` хранит binding/wake/boundAt, `chat-woken.json` — ключи доставленных уведомлений, но не количество модельных вызовов, токены, cache read/write, context size или деньги. `GET /cost` и CLI `cost` проходят task worker runs и отдельно draft/repair; host chat туда не включён ([host/actions.ts:785-807](../../../packages/plugin/src/host/actions.ts), [commands/runs.ts:472-536](../../../packages/cli/src/commands/runs.ts), [planning-cost.ts:9-33](../../../packages/core/src/cost/planning-cost.ts)). Tool output может менять следующий контекст, но для host chat нет связи `toolCallId → modelCallId → usage`.

Внешний **Codex chat этого исследования** — ещё одна отдельная область, не worker run Crewboard и не bound dsh chat. Предоставленный оркестратором безопасный агрегат `/tmp/crewboard-orchestrator-usage-summary.json` охватывает только эту нить: 1713 snapshots. Последний `last` на `gpt-6-sol`: input 577 976, cached input 577 280 (99,88% наблюдаемого input), output 1 263, в нём reasoning 1 166, cache-write field 0, contextWindow 828 400. Наблюдаемое большое повторное чтение контекста совместимо с высоким cache share; 577 976 — токены **одного последнего вызова**, не размер уникальной истории. `total` около 465,19 млн input / 458,76 млн cached — накопление за длинный чат и смену моделей; нельзя суммировать 1713 cumulative snapshots, оценивать весь total по последнему тарифу или выдавать его за cash bill. Ноль в `cache_write_input_tokens` — **поле наблюдаемого snapshot**, но нет доказательства, что провайдер сообщил именно нулевую запись: возможна семантика адаптера/неэкспонированное поле. Нужны raw provider receipt/schema и sentinel для missing, до этого состояние `unknown`, не `0`.

## Проверка текущего baseline и нормализации

Только агрегаты, без текстов чатов: `/tmp/crewboard-cache-baseline.json` (`cost --all-plans --since 2026-09-25`, предоставлен родителем) содержит **38 worker runs**, 0 planning attempts, 2 dsh pending; 32 completed, 4 incomplete, 1 failed, 1 cancelled. По 26 Claude runs сумма `cacheRead` = 647 390 104 и `cacheWrite` = 6 149 848 при `input` = 6 002; это согласуется с Claude-разделением uncached/cache-read/cache-create и длинными повторными запросами, но не доказывает ошибку double count. По 3 Codex runs `cacheRead` = 108 861 952 и normalized uncached input = 1 701 795; здесь parser **вычел** cached из reported input. Две dsh строки имеют `pending: true`, но availability `unavailable` — противоречие projection, не нулевая стоимость. Значения cash/API-equivalent/quota не суммировались в общий USD.

Нормализованный `Tokens.input` не имеет одной физической семантики: Claude — uncached input; Codex — total input minus cached; dsh-bill просто копирует `inputTokens`; OpenCode/Gemini/Grok переносят CLI поля без доказанного правила включения cache. Соответственно `input+cacheRead` — допустимый total prompt только для подтверждённого контракта конкретного backend. `reasoning` у Codex вложен в output; у прочих inclusion неизвестна, поэтому `output+reasoning` нельзя использовать как общий расход. CLI runner складывает turn counters в run state ([cli-runner.ts:769-800](../../../packages/core/src/runs/cli-runner.ts)); OpenCode складывает steps до границы turn. Для Claude `total_cost_usd` последнего `result` перезаписывает state USD; требуется fixture на два turns, чтобы подтвердить, является ли это session-cumulative или per-turn суммой. Для других turn CLI USD runner суммирует значения ([cli-runner.ts:673-676](../../../packages/core/src/runs/cli-runner.ts)). Snapshot counters внешнего Codex чата cumulative; применять к ним per-turn сложение недопустимо.

## Измеримая диагностика

Нужен **host-model call ledger** от фактического dsh host/provider adapter, а не вывод из `sessionController.prompt`: `callId`, `sessionId`, `planId`, optional `taskId`, actor=`orchestrator|worker|draft|repair|external`, model/provider/priceVersion, timestamp, attempt/review phase, `promptPrefixVersion` (hash стабильного system/developer/tool-schema префикса без текста), prefix token length, `inputTotal`, `cacheRead`, `cacheWrite`, `uncachedOrMiss` с backend-specific inclusion semantics, output и `reasoningIncludedInOutput`, context occupancy/window, receipt/source/finality. Хранить missing как unavailable/pending и отдельно время backfill. Wake ledger должен писать delivered event ID, `batchId`, число prompts, `callIds`; фиксировать cold/warm, session rebinding, context rebuild/compaction и model/effort/config changes. Session continuity — лишь covariate, не доказательство cache hit. Смена effort **может** менять модельные инструкции, но совместимое обновление конфигурации может сохранить прежний prefix; фиксировать hash фактически отправленного префикса. Compaction может ухудшить cache reuse и одновременно сократить общий input/cost; сравнивать оба результата.

Для cache diagnostics показывать два разных отношения: `observed_cached_share = ΣcacheRead / ΣinputTotal` только для calls с известным total и проверенной inclusion semantics; `eligible_hit_ratio = ΣcachedEligibleTokens / ΣeligiblePrefixTokens` только если provider/adapter знает eligible prefix (порог, prefix boundary, retention window) и reported hit/miss. Иначе eligible ratio = unavailable, даже при известном cached share. Разбивать по prefixVersion/model, cold→warm и compaction events; p50/p95 input/context, wake calls per accepted task. Для экономии API считать counterfactual **по сегментам** с тарифом/датой: uncached, read, write применяют свои ставки, cache write не дополнительная плата к тому же input segment. [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) на 2026-09-28 сообщает для GPT-5.6+ read 0.1×, write 1.25× uncached, cached tokens всё ещё входят в TPM. Это API-специфично; DeepSeek/Gemini/Claude не наследуют его семантику. DeepSeek kv-cache full page в текущей проверке родителя недоступна; snippet о default disk cache и hit/miss fields — неподтверждённое содержание полной страницы. [Gemini API caching](https://ai.google.dev/gemini-api/docs/caching) описывает implicit cache и model-specific minimum prefix, но это не подтверждение CLI-полей.

Итоговый `cost per accepted task`: отдельно (а) observed cash по API receipts, (б) API-equivalent для subscription runs, (в) provider quota windows как независимая ось; числитель включает все worker attempts, retry, draft/repair allocation по явному правилу, host orchestration/review calls, а знаменатель — число принятых задач за cohort. Pending/unavailable компоненты и coverage показываются рядом, не подменяются нулём. Экономия API ≠ экономия подписочного лимита: последняя остаётся неизвестной без provider receipts или контролируемого эксперимента на той же квоте, модели и типе задач. Не отправлять диагностические данные новому внешнему провайдеру.
