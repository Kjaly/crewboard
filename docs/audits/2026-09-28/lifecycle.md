**Объём.** Read-only разбор core, CLI, dsh host/tools, UI consumers и тестов. Проверено 15 переходов и 10 сложных сценариев. Источник истины для результата — plan + immutable `evidence.json`, отдельные `checks.json` и attestation; UI строит представление из них. Реальные планы, статусы, рабочие копии и конфигурация не менялись. Единственный исполняемый эксперимент создал временный Git fixture в системном tmp; временный тестовый файл удалён после запуска.

## Карта переходов

`task/contract → ready → worktree/baseline → run → terminal report/evidence → in_review → checks/attestation → accepted → merged → release deps`. Ответвления: `incomplete → continue | takeover`, `blocked/negative → return | human negative closure`, `failed/cancelled → repair/relaunch`, `restart → sync + chat wake`. Stored status и derived view status различаются: `accepted` с отрицательным verdict показывается как `closed`; `accepted` с рабочей копией без merge ещё не освобождает зависимые задачи ([graph.ts:143](../../../packages/core/src/plan/graph.ts#L143), [graph.ts:158](../../../packages/core/src/plan/graph.ts#L158)).

## Сложные ситуации: факт, защита или дефект

1. **`no_claim` / `left_uncommitted` — ожидаемая защита с legacy caveat.** При uncommitted и отсутствии Result получается `no_claim`; после `commit_nudge` и всё ещё dirty при заявленном Result — `left_uncommitted`, review не открывается. `continue` запускает того же worker в той же копии; `takeover` сохраняет старый outcome и требует commit + positive orchestrator report + checks. Legacy run без `commitNudged` может попасть в review с dirty copy, но auto-close требует clean. [sync.ts:24](../../../packages/core/src/orchestration/sync.ts#L24), [incomplete.test.ts:89](../../../packages/core/test/incomplete.test.ts#L89), [incomplete.test.ts:150](../../../packages/core/test/incomplete.test.ts#L150), [cli-auto-close.test.ts:55](../../../packages/cli/test/cli-auto-close.test.ts#L55).
2. **Worker sandbox `EPERM` и shared slot — разные механизмы.** Отказ sandbox в browser tool остаётся worker claim `NOT RUN`, не подменяет успешные Typecheck/`git diff --check`; запись `sandbox_denied` нормализуется как event. Это environment blocker, не автоматический признак провала остальных проверок. `EPERM` в `pidAlive` slot, напротив, означает живой чужой процесс и удерживает слот; stale holder очищается. Baseline и `verify --run-checks` используют тот же slot; worker должен запускать свои тяжёлые команды через CLI slot. [evidence.test.ts:44](../../../packages/core/test/evidence.test.ts#L44), [verdict-golden.test.ts:38](../../../packages/core/test/verdict-golden.test.ts#L38), [slots.ts:69](../../../packages/core/src/slots/slots.ts#L69), [slots-integration.test.ts:16](../../../packages/core/test/slots-integration.test.ts#L16). **Ограничение тестирования:** широкий параллельный прогон через внешний slot упёрся в 5 s timeout у тестов, которые сами берут slot; это не сигнал о product regression.
3. **Stale HEAD/contract/proof/receipts при явной attestation — ожидаемая защита.** `inspectAttestation` проверяет hash proof, latest run, HEAD, текущий hash contract, clean и receipt.commit/revision для positive. Positive accept и merge отклоняются; explicit negative closure остаётся возможным. [attestation.ts:15](../../../packages/core/src/orchestration/attestation.ts#L15), [attestation.test.ts:71](../../../packages/core/test/attestation.test.ts#L71), [attestation.test.ts:99](../../../packages/core/test/attestation.test.ts#L99).
4. **Обычный completed run: stale receipt.commit после нового чистого commit — подтверждённый дефект, высокий приоритет.** Ниже отдельная воспроизводимая трасса. В [auto-close.ts:40](../../../packages/core/src/orchestration/auto-close.ts#L40) ветка `attestation ? receipts : ran` сравнивает `receipt.commit` с HEAD только для `handoff` или `attestation`; обычный completed run минует обе проверки. `currentRevision` берётся из `run.contractRevision`, а не текущего hash контракта. [review.ts:16](../../../packages/core/src/orchestration/review.ts#L16) проверяет rev/evidence/run, но не HEAD. [auto-close.ts:52](../../../packages/core/src/orchestration/auto-close.ts#L52) перед auto-merge требует checked latest run, но HEAD для обычного completed не сравнивает. [merge-task.ts:92](../../../packages/core/src/worktree/merge-task.ts#L92) проверяет clean/conflicts/attestation, но если attestation отсутствует, не проверяет receipt.commit. Поэтому это путь к ложному успеху, а не только недостающий UI warning.
5. **Worker blocked → later root positive (READY03, без изменения cabinet) — ожидаемый путь при независимом proof, с важным различием.** Старый worker claim и `browser NOT RUN, EPERM` остаются в evidence; новый proof с `Result: received` и зелёными receipts на текущем HEAD получает структурную positive attestation. Detail, manual acceptance, merge и snapshot показывают positive без переписывания worker run или файлов cabinet. Тест использует fixture `src/feature.ts`, а не фактический cabinet: это проверка механизма READY03, не утверждение о конкретном реальном плане. [evidence.test.ts:44](../../../packages/core/test/evidence.test.ts#L44), [attestation.test.ts:22](../../../packages/core/test/attestation.test.ts#L22), [attestation.test.ts:49](../../../packages/core/test/attestation.test.ts#L49).
6. **Отрицательная приёмка и deps — ожидаемая защита.** Отрицательный accept закрывает без merge и не удовлетворяет зависимость implementation task. Отрицательный report сам по себе оставляет возможность `return`; человек нужен только для решения закрыть без результата. [graph.ts:143](../../../packages/core/src/plan/graph.ts#L143), [plan-graph.test.ts:37](../../../packages/core/test/plan-graph.test.ts#L37), [attestation.test.ts:71](../../../packages/core/test/attestation.test.ts#L71).
7. **Cancelled dialog — ожидаемая защита.** Host сначала вызывает native confirm, затем `acceptTask`/`mergeTask`; отмена даёт 409 `declined` и не меняет plan. Core повторно проверяет rev/evidence после диалога. [actions.ts:1192](../../../packages/plugin/src/host/actions.ts#L1192), [actions.test.ts:150](../../../packages/plugin/test/actions.test.ts#L150), [review.ts:29](../../../packages/core/src/orchestration/review.ts#L29).
8. **Pending auto-close/merge после restart — частично восстановлено.** Host на первом snapshot специально повторно будит `close_due`/`merge_due`; persisted wake key предотвращает дубль, failed prompt пробуется снова. Это cue для чата, не durable job queue: без binding/wake или при отсутствии нового full snapshot автоматическое закрытие не происходит. [chat.ts:303](../../../packages/plugin/src/host/chat.ts#L303), [chat.ts:316](../../../packages/plugin/src/host/chat.ts#L316), [chat.test.ts:322](../../../packages/plugin/test/chat.test.ts#L322), [chat.test.ts:338](../../../packages/plugin/test/chat.test.ts#L338).
9. **Маршрутизация пресетов — ожидаемая authority protection.** Plan override сильнее repo preset, repo сильнее builtin; disabled worker исключается. Agent tool отказывает explicit worker вне preset, человек может выбрать и это записывается; устаревший agent assignment сбрасывается в пользу preset. [presets.test.ts:28](../../../packages/core/test/presets.test.ts#L28), [routing.test.ts:102](../../../packages/core/test/routing.test.ts#L102), [preset-authority.test.ts:62](../../../packages/plugin/test/preset-authority.test.ts#L62), [launch.ts:232](../../../packages/core/src/orchestration/launch.ts#L232).

Это ожидаемое восстановление работы, однако контекст решения мог быть только в потерянной session; он не переносится автоматически. `planOfSession` и tool targeting не дают чужому чату писать в другой план. ### Воспроизведение stale commit gap (временный fixture, без product changes)

Команда: `CREWBOARD_CHECK_SLOTS=2 crewboard slot -- pnpm exec vitest run packages/cli/test/lifecycle-stale-fixture.test.ts --testTimeout=30000 --reporter=verbose`. Существенная строка stdout (плюс `1 passed (1)`, 1.45 s):

Полный вывод локального прогона: `/tmp/crewboard-stale-fixture.log` (временный артефакт, не часть репозитория).

Минимальный сценарий: completed worker run с `Result: received`, `check.state=checked/by=orchestrator`, контракт `<checks>test ! -e b.ts</checks>`; на A `verify --run-checks` записывает зелёный receipt с `commit=A`; затем в task copy коммитится `b.ts` как B, и та же команда на B возвращает nonzero. `verify --attest --verdict result` отказывает без нового receipt. При отсутствии attestation `accept a --auto` возвращает 0, затем `merge a --auto` возвращает 0 и переносит B в base. Временный тест `lifecycle-stale-fixture.test.ts` удалён; это сохраняет audit branch без source/test изменений.

**Серьёзность: высокая (P1 для доверия к автоматическому merge).** Доказательство не утверждает о внешней эксплуатации: нужен новый чистый commit между checks и closure. Но при нём автоматизация может положительно принять и влить код, для которого обязательная проверка не проходила. **Acceptance test для исправления:** такой же A→B fixture должен давать отказ `accept --auto`; если B добавлен после accept, `merge --auto` также должен отказать, пока checks на B не повторены. Контракт, изменённый после receipt, тоже должен требовать новых checks. Явная positive attestation уже обеспечивает это и должна остаться положительным контрольным тестом.

## Ручная работа, ожидание, дублирование

- Routine happy path требует **0 действий человека** при включённом orchestrator check, чистом positive, зелёных checks и безопасном merge. У оркестратора минимум 3 содержательных шага после run: проверка/detail, `verify --run-checks`/`done` или `attest`, `close`; host может дать два отдельных wake (`check_due`, `close_due`) и третий `merge_due` при принятии без merge. Окно batching wake по умолчанию 5 s; это кодовая нижняя добавка, не измеренная end-to-end latency. [chat.ts:303](../../../packages/plugin/src/host/chat.ts#L303).
- Проверки worker в отчёте — утверждения; `verify --run-checks` повторно исполняет `<checks>` и сохраняет receipts. Независимая positive attestation затем повторно проверяет receipt/HEAD/contract при записи, detail/accept и merge. Это осознанное дублирование свежести; самый дорогой шаг — повторный запуск команд. Количество и длительность checks зависят от контракта; код пишет `durationMs`, поэтому медиану/очередь можно измерить по receipts, но в этом read-only аудите реальные планы/логи не агрегировались.
- Если slot занят, baseline и checks ждут без запуска команд; `slot` по умолчанию даёт `max(1, floor(cores/4))`, настройка/ENV может изменить число. `runContractChecks` запускает команды по одной и timeout берёт из recipe. [slots.ts:17](../../../packages/core/src/slots/slots.ts#L17), [checks-run.ts:82](../../../packages/core/src/runs/checks-run.ts#L82). Широкий локальный прогон `crewboard slot -- pnpm exec vitest run …` дал 80 passed / 9 timeout при 5 s per test из-за конкуренции и вложенного slot; эти timeouts не использованы как verdict. Узкий fixture с двумя slot и 30 s timeout прошёл.
- Наибольший риск ложного успеха сейчас не дублирование worker claim, а **разрыв привязки зелёного receipt к commit/contract на ordinary auto path**. Отдельный риск человеческого override существует намеренно: UI/CLI позволяет принять unchecked/dirty, но диалог и note это называют; это exception gate, не автоматический success.

## Приоритетные изменения (предложения, product code не менялся)

| Приоритет / уверенность | Наблюдаемое состояние → desired contract | Минимальное изменение → тест/метрика |
|---|---|---|
| P1 / высокая | Completed A receipt, clean B → auto-accept/merge B; каждый auto-merge должен иметь зелёный receipt на влитом HEAD и текущем contract. | В `automaticAcceptance` и `assertAutomaticMerge`/`checkMerge` сверить `receipt.commit === current task HEAD`, current contract hash, runId/worktree; при mismatch отказ. A→B acceptance test выше; метрика `auto_close_refusal{reason=stale_receipt}`. |
| P1 / высокая | Auto path с текущими checks, но изменённым текстом контракта может опираться на `run.contractRevision` → требовать revision актуального файла. | Переиспользовать проверку freshness из attestation или единый helper для receipts; тест изменения только contract после checks. |
| P2 / средняя | Auto-close и auto-merge в двух шагах; crash между ними оставляет accepted/unmerged до следующего wake. | Durable `close_due`/`merge_due` intent или reconcile accepted checked task при full sync, с теми же gates; тест restart до/после accept и идемпотентность. |
| P2 / высокая | Исторический blocked worker claim требует независимого proof, но `done` визуально похож на promotion. | UI/CLI явно различать check note и attestation, показывать bound HEAD/revision и stale reason; тест READY03 в host/client плюс core. |
| P2 / средняя | Чат при потере session пересоздаётся только с briefing; решения из старого чата не включены. | Краткий persisted handoff последних структурированных decisions/open exceptions из plan notes; тест rebind/open после unknown session, без переноса неподтверждённых chat quotes как фактов. |
| P2 / средняя | Начальный snapshot гасит большинство старых alerts как baseline; после restart close/merge специально пробуждаются. | Применить тот же durable reconciling принцип к `check_due`, но с ledger, чтобы не спамить; тест pending до restart и первый full snapshot. |
| P3 / высокая | Legacy claimed dirty run без commit nudge идёт в review; ручное принятие возможно с предупреждением. | В review/attention показывать commit status и выбор `continue/takeover` рядом; тест старого evidence и запрета auto-close. |
| P3 / средняя | Очередь slot и повторные проверки дают ожидание, но нет общей lifecycle метрики. | Из существующих `durationMs`, review intervals и wake timestamps построить p50/p95 wait, checks/run и auto-close attempts; метрики без нового status. |

**Можно автоматизировать без человека:** preset selection в разрешённом списке, preflight/baseline, запуск ready с контрактом, sync/evidence, чтение verdict, contract checks, независимую attestation при реальном proof, routine positive acceptance и clean merge, dependency release, retry transient sync/wake. **Реальные exception gates:** decision с выбором, `<human_review>`, отрицательное закрытие/accept disputed или caution, конфликт или смена target/base, worker вне preset, dirty copy с выбором keep/reset, manual mark-merged/drop/supersede. Автоматизация не должна выдавать человеческое согласие за recorded result.
